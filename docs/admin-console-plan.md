## 1. Что просил владелец

Одна веб-админка, в которой удобно:

- видеть геймпассы и контролировать их состояние;
- вести заказы (все источники: WB, прямые, Авито, сайт);
- **выгружать данные для выкупа — ID геймпассов**;
- работать с прямыми заказами;
- вести партнёрский контур «Антон»;
- работать втроём: **три админских аккаунта**, вход по Telegram без пароля;
- всё это — эргономично, логично и стильно, в духе Apple.

## 3. Три админа и вход через Telegram — да, и это правильный путь

**Ответ: да, привязка Telegram может выдавать админку автоматически.** Механизм уже есть,
собирать почти нечего:

- провайдер `telegram-login` в `src/auth.ts:97` уже проверяет подпись Telegram на сервере
  (`verifyTelegramLogin`, HMAC от токена бота) и гасит одноразовый challenge;
- `UserIdentity` уже хранит **проверенную** TG-личность;
- `ADMIN_IDS` уже содержит список админов и уже используется ботом и TWA.

### Предлагаемая модель: роль **выводится**, а не хранится

Единственный источник правды — `ADMIN_IDS` (список Telegram ID). Гейт админки отвечает на
вопрос: *«есть ли у этого пользователя проверенная TG-личность, чей ID входит в `ADMIN_IDS`?»*

```
Админ жмёт «Войти через Telegram» → подпись Telegram проверена сервером
  → UserIdentity(TG, subject) → subject ∈ ADMIN_IDS ?
      да  → доступ в /admin, роль в сессии, действия пишутся на его TG ID
      нет → обычный личный кабинет
```

Что это даёт:

| Свойство | Почему важно |
|---|---|
| Три админа = три ID в одной переменной | Она уже есть и уже используется ботом/TWA — второй список не заводим |
| Пароли не нужны | Нечего терять, нечего ротировать, нечего фишить |
| Отзыв доступа мгновенный | Убрали ID → следующий запрос уже без прав (**A0.2 чинится здесь же**) |
| Единая атрибуция | Desktop и TWA пишут действия под одним и тем же TG ID |
| Совпадает с TWA | В TWA уже есть `adminSetVersion()`, обесценивающий токен при смене состава — переносим тот же приём в веб |

**Break-glass:** вход по email+паролю остаётся **только для владельца** — на случай, когда
Telegram недоступен. Отдельная строка в `docs/security.md`.

**Обязательное условие:** роль проверяется **на каждом запросе**, а не берётся из JWT.
Иначе A0.2 переезжает в новую админку вместе с кодом.

**Риск, который надо зафиксировать:** слияние аккаунтов (`AccountMergeAudit`) не должно
приводить к наследованию админских прав. Проверка при реализации обязательна.

## 5. Дизайн-язык: «в духе Apple» конкретно, а не на словах

Не «сделаем красиво», а проверяемые правила. Опора — существующие токены `--rb-*`
(светлая и тёмная темы уже есть) и правило «шрифт ≥14 px», закреплённое контракт-тестом D8.

| Принцип | Как выглядит здесь |
|---|---|
| **Список + деталь, а не переходы** | Как в Mail.app: очередь слева, досье справа. Работа с заказом не уводит со страницы и не теряет позицию в списке |
| **Клавиатура — первый класс** | `⌘K` — командная палитра (поиск заказа/ника/кода/действия). `J`/`K` — по очереди, `Enter` — открыть, `E` — в работу, `⌘↩` — подтвердить. Триаж 40 заказов мышью — это не работа |
| **Спокойная плотность** | Данных много, шума мало: один акцентный цвет, статусы — цветом точки, а не заливкой строки |
| **Постепенное раскрытие** | Карточка → досье → полный журнал. Три уровня, не десять модалок |
| **Честная обратная связь** | Оптимистичный UI с откатом, а не спиннер на весь экран. Необратимое (возврат, отклонение) — inline-подтверждение с суммой прописью |
| **Одна сетка** | Общие компоненты таблицы/карточки/статуса. Сегодня desktop и TWA рисуют статусы по-разному |
| **Обе темы** | Только токены `--rb-*`. Литеральные цвета запрещены — правило №4 из `launch-roadmap.md` §6 |

Отдельно: **это не копия TWA на большом экране.** TWA оптимизирована под один палец и один
экран; десктоп должен показывать очередь и досье одновременно и работать с клавиатуры.

## 6. Ключевое техническое решение — единый гейт, а не вторая дверь

Сейчас `/api/twa/*` защищены Bearer-JWT, а `/admin` — сессией. Соблазн — научить desktop
дергать TWA-роуты «как-нибудь». **Так делать нельзя:** это ровно та «вторая, более слабая
дверь к деньгам», о которой предупреждает риск в плане ботов.

Предлагается:

1. Один helper `requireAdmin(req)` — **единственное** место, где решается «админ или нет».
   Принимает оба доказательства: сессию next-auth и Bearer-JWT TWA. Оба пути обязаны
   сойтись к одному ответу: TG ID + `ADMIN_IDS`.
2. Роуты переезжают в `/api/admin/*` по смыслу (заказы, выкуп, партнёры, аналитика).
3. `/api/twa/*` остаются тонкими алиасами на время миграции, чтобы TWA не сломалась
   ни на один день. Удаляются последним шагом.
4. Ни одна проверка прав не пишется внутри роута руками.

Это же решает и «три админа»: атрибуция действия берётся из `requireAdmin`, а не из тела
запроса.

### Как завести админский аккаунт с нуля (проверено по коду 28.07)

Регистрация по почте → привязка Telegram → админ **автоматически**, роль ставить руками не
надо. Привязка вызывает `linkOrMergeVerifiedIdentity`: если этот Telegram уже привязан к
другому профилю, произойдёт **слияние** — заказы, коды, прямые заявки и привязки переедут на
новый аккаунт, балансы сложатся записью в `BonusLedger`, след останется в `AccountMergeAudit`.

⚠️ Слияние **отказывает**, если у любой из сторон `role = "ADMIN"` в базе
(`"Privileged accounts cannot be merged"`, `src/lib/user-identity.ts:157,179`). Поэтому
новому аккаунту нельзя заранее проставлять `ADMIN` руками — и не нужно.

Восстановление доступа, если Telegram недоступен: поставить `role=ADMIN` нужному `User` и
указать его почту в `ADMIN_BREAKGLASS_EMAILS` — работает только связка из двух условий.

### A3. Заказы — ядро переезда

Очередь с теми же вкладками и той же семантикой, что в TWA (`buildTabWhere` — общий, не
копия), split-view досье, все 21 действие, клавиатурный триаж.
**Приёмка:** каждое действие TWA имеет эквивалент в вебе и пишет тот же `OrderEvent`;
вкладка «К выкупу» на обоих экранах даёт **одинаковый список**.

**Ключевое решение:** границы очередей вынесены из TWA-роута в `src/lib/order-queue.ts`
(`buildTabWhere`, `orderByForTab`, `loadGamepassExport`). TWA-роут теперь импортирует их,
а не держит свою копию — «К выкупу» на двух экранах не может разойтись физически.

**Реальный порядок работы (владелец, 29.07): выкуп ручной — берут выгрузку и покупают
сами.** Поэтому экран построен вокруг ручного пути, а не автопокупки:

```
выгрузка ID → «Скрипт» (покупка в браузере донора, ожидаемая цена зашита)
            → «Куплено» (закрыть заказ + уведомить клиента)
```

Главная кнопка панели — **«Отметить купленными (N)»**; авто-выкуп ушёл вторым действием
под разделитель. Это закрывает узкое место потока: до 29.07 массового закрытия заказов не
было **нигде** — ни в вебе, ни в TWA, и после ручной пачки заказы закрывались по одному.

Отметка вызывает серверный `complete`: COMPLETED + снапшот себестоимости по текущему курсу
+ **уведомление клиенту о выдаче робуксов**. Поэтому массовая отметка спрашивает
подтверждение с числом заказов и прямо предупреждает про рассылку.

**Чем ещё шире TWA:** в TWA пачка считается автоматически (knapsack по бюджету донора), в
вебе закупщик выбирает строки сам — плюс кнопка «сколько влезает в баланс» как быстрый
набор. Результат виден построчно с причиной отказа, а не только в итоговом отчёте.

API: `GET /api/admin/buyout?tab=…` (выгрузка + счётчики + пачки + сливы) и
`GET /api/admin/buyout/donor` отдельно — `getBrowserSession` ждёт серверный браузер до 70 с,
и выгрузка не должна стоять в этой очереди.

**Покупка не дублируется.** Веб дёргает те же `POST /api/twa/orders` (`purchase`,
`purchase-script`) и `POST /api/twa/purchase-batch`, что и TWA: денежная логика со всеми
гардами осталась ровно одна. Изменилась только дверь — эти роуты переведены с
`extractTwaUser` на **`requireAdmin`**, то есть принимают и Bearer-пропуск TWA, и веб-сессию,
сводя оба доказательства к `ADMIN_IDS` (§6). Это не «вторая, более слабая дверь»: правило
одно и то же, проверено прогоном (см. приёмку). Отчёт пачки в Telegram теперь адресуется по
`actor.telegramId`, а не по внутреннему `User.id` — при запасном входе отчёт просто не шлётся.

Условия остановки пачки и пауза между покупками вынесены в `src/lib/buyout-batch.ts`
(`shouldStopBatch`, `bulkPause`) — общие с TWA: два экрана не должны расходиться в том,
когда пачку пора прекращать.

**Задеплоено 29.07** (`8831f97` + `6237469`). **Приёмка на боевом домене:**

**Обзор и аудитория — 🟢 реализовано 29.07.2026.** `/admin` теперь не рисует условные

`/admin/users` разделяет три разные сущности, которые раньше смешивались:

- профиль в нашей БД с Telegram/VK/email-каналом;
- каноническую подтверждённую `UserIdentity` и legacy `User.tgId`/`User.vkId`;
- живой размер публичных сообществ из Telegram Bot API и VK API.

Контрольный production-срез 29.07.2026: 597 профилей; Telegram — 372, VK — 220,
email — 5; с заказами — 564, повторных покупателей — 61. В публичном Telegram-канале
было 310 подписчиков, в VK-сообществе — 218 участников. Эти числа не складываются:
один профиль может иметь несколько каналов, а подписчик сообщества может не иметь профиля.
Внешние API читаются сервером с коротким timeout и graceful fallback — недоступность Telegram
или VK не роняет админку и не превращается в выдуманный ноль.

Production-проверка выявила инфраструктурную границу: RF Web не достигает
`api.telegram.org` напрямую. Telegram read-only метрики поэтому идут через уже защищённый
`VALIDATOR_SOURCE_URL`/`x-validator-key` мост в SG; мост возвращает `result` только для
`getChat`/`getChatMemberCount`, а send-методы сохраняют прежний минимальный `{ok:true}`.
Токен бота из Web в запросе к мосту не передаётся.

Аудит обнаружил реальный migration debt: у 170 социальных профилей хотя бы один канал
есть только в legacy-поле (TG — 128, VK — 42), без соответствующей канонической
`UserIdentity`. Такие профили включены в общие цифры, но помечены в таблице; риск и правило
устранения зафиксированы в `security.md` и `database.md`.

Повторный аудит качества профиля уточнил причину «плохих VK-данных»: реально пустое или
fallback-имя было только у 3 из 220 VK-профилей, зато `screen_name` ранее не сохранялся
ботом как отдельное provider-поле. У Telegram аналогично `ctx.from` не создавал identity.
С 29.07 оба бота лениво синхронизируют подтверждённый actor, VK читает `screen_name`/аватар
через `users.get` v5.199, а таблица показывает отдельные TG/VK ID и handles. Отсутствие
handle не считается ошибкой: пользователь мог не назначить публичный username.

- **Правило представления — одно на два экрана.** «Какой бейдж, какое главное действие, что

  `OrdersScreen` больше не держит вторую копию правил, а делегирует в общий модуль.
- **Отмена обещается только там, где есть обратное действие.** Заморозка ↔ разморозка,

  чаще, чем на шапку смотрят. Рубли остались там, где они факт: оплата в досье.
- **Целевые устройства.** MacBook Pro 16″ (1728×1117): страница не центрируется в 1440,
  таблица получает всю ширину, две панели — 400 px очередь + остальное досье.

  панель, панель пачки и тост подняты над нижней навигацией с учётом safe-area.

### Что осталось за рамками

### Разбиение выкупа на сайте (03.09.2026)

Раньше разбить заказ на несколько геймпассов можно было только в TWA. Теперь это
есть и на сайте — и намеренно **не копией телефонного листа**: на телефоне это
один список со счётчиками, потому что больше туда не влезает.

`split-dialog.tsx` — две колонки: слева витрина покупателя, справа **собранный
заказ в порядке выкупа**. Держать в голове, что уже набрано, не нужно.

| Что даёт десктоп | Зачем |
|---|---|
| **«Набрать под заказ»** (`planSplitFor`) | Точный размен номинала. Руками неочевидно: на витрине 1000/2000/802/499 заказ на 1301 закрывается только парой 802+499, а заказ на 2000 — двумя частями по 1000 на ОДНОМ пассе. ДП, а не жадность: жадность на таких номиналах промахивается мимо точной суммы, а допуска здесь нет |
| Степперы «− N +» | Мышь попадает точно; на телефоне вместо них тап по строке |
| Правая колонка с порядком | Удаляется КОНКРЕТНАЯ часть (✕), а не последняя |
| Клавиатура `1…9` / `⌫` / `⌘↵` / `Esc` | Как во всём рабочем месте |
| Полоса прогресса суммы | Видно, сколько ещё добрать, до нажатия |

Вход: кнопка «🧩 Разбить выкуп» в досье, клавиша **`S`**, команда в палитре `⌘K`.
Кнопка показывает прогресс (`Разбивка 1/3`), если разбиение уже есть.

Одинаковые номиналы подбор раздаёт по **разным** пассам, пока разные есть: два
пасса по 1000 лучше, чем один и тот же дважды — меньше возни с донорами. Когда
разных нет, повтор законен, и об этом предупреждает оранжевая плашка (детали —
[twa-admin.md](twa-admin.md#один-и-тот-же-пасс-несколько-раз-03092026)).

### ⚡ «Вперёд очереди» и блок «Первым делом» (03.09.2026)

Порядок в ленте — это порядок работы, и до сих пор его целиком определял возраст.
Кнопка `⚡` (строка, карточка, досье, клавиша **`P`**, палитра `⌘K`) поднимает заказ
наверх, не трогая ни статус, ни срез; отмена — `⌘Z`, у действия есть обратное.
Поднятый виден жёлтой полосой слева и значком у кода — иначе его не отличить от
просто самого старого, который стоит там же.

На «Обзоре» появилась полоса **«⚡ Первым делом»** между «сколько тратим» и
«дорожками»: поднятые руками и **прямые** заказы (за прямой клиент заплатил лично, поэтому в
общей очереди «К выкупу» прямые идут сразу за поднятыми). У каждой строки — причина
попадания, **заметка** («почему этот заказ первым», правится по клику; машинный аудит
заметки при этом сохраняется), сумма грязными, возраст и две кнопки: «⧉ ID» (пассы этого
заказа) и «выкуплено». В шапке `⧉ ID · N` — ID всей пачки; копируются невыкупленные части,
повтор пасса не схлопывается. Кнопки разнесены щелью и разной формой: «выкуплено»
необратимо и пишет клиенту, а копирование жмут в десять раз чаще — на 8 px и одинаковых
квадратах это был промах ценой сообщения покупателю. Пусто — блока нет вовсе.
Источник тот же, что у Главной TWA (`src/lib/first-in-line.ts`), правило сортировки —
общее в `order-queue.ts`; детали и ловушка `NULLS LAST` —
[twa-admin.md](twa-admin.md#-вперёд-очереди-ручной-приоритет-заказа-03092026).

## 12. «Обзор» — начало смены (этапы Г1–Г4), сделано 03.09.2026

Замер перед работой: первым и самым крупным числом на `/admin` стоял **«Чистый оборот»
7 547 ₽** — это только эквайринг сайта, 14 подтверждённых платежей за всё время. Блок
«Требуют внимания» показывал `0 · 0 · 0 · 1`. В тот же момент очередь выкупа стоила
**31 000 R$ грязными**, старейший заказ ждал **четвёртые сутки**, а за 30 дней через WB
прошло 326 заказов на 261 906 R$ — мимо банка и мимо экрана.

Экран не был сломан, он отвечал не на тот вопрос: «как дела у бизнеса» вместо «что делать
сейчас». Ниже — что встало на его место.

### Что сделано

| Этап | Что | Где |
|---|---|---|
| **Г1** | Один роут `/api/admin/overview` + сборщик `getAdminOverview()`: очередь, доставка, диф, здоровье, витрина | `lib/admin-overview.ts`, `app/api/admin/overview/route.ts` |
| **Г2** | Экран: ответ → дорожки работы → диф → тихая строка → витрина | `components/admin/overview/overview-screen.tsx` |
| **Г3** | Отметка присутствия админа `AdminPresence` (Telegram ID, `lastSeenAt`, `windowStartAt`, `currentOrderId`) | `lib/admin-presence.ts`, миграция `20260903_admin_presence` |
| **Г4** | «Пока вас не было» на её основе + витрина одной полосой со спарклайном | `overview-screen.tsx` |
| **Г5** | Набор заказов под баланс выкупного аккаунта — **в «Выкупе»**, не на обзоре | `lib/buyout-packing.ts`, `components/admin/buyout-client.tsx` |

### Решения, которые стоит помнить

- **Порядок экрана — это порядок вопросов.** Крупный кегль на странице ровно один, и он
  принадлежит грязным робуксам очереди: это то, что сейчас предстоит потратить. Дальше
  плотность растёт, а размер падает; витрина внизу набрана кеглем подписи.
- **Витрина не удалена, а понижена.** «Чистый оборот», источники, профили остались — но одной
  строкой со спарклайном, где их размер честен. Разбивка по источникам считается **за 30
  дней своим запросом**: `sourceBreakdown` дашборда считает за всё время, и в одной строке
  «30 дней · 326 заказов» соседствовало с «Wildberries 755» — числа из разных эпох под одной
  подписью.
- **«Последних заказов» на обзоре нет вовсе.** Это были первые пять строк `/admin/orders`,
  из которых нельзя было ничего сделать. Вместо них — три старейших прямо в дорожке выкупа,
  с кнопкой «Выкуплено» и копированием ID.
- **Пустая дорожка сжимается в строку.** «Ошибок выкупа нет · заморозки нет» — одна серая
  строка вместо четырёх нулей в четверть экрана.
- **Окно «Пока вас не было» у каждого админа своё и не схлопывается.** Двух полей времени
  хватает, но нужны именно два: `lastSeenAt` двигается на каждой загрузке, `windowStartAt` —
  только после перерыва (`ADMIN_AWAY_GAP_MINUTES = 30`). С одним полем три обновления
  страницы подряд съели бы весь диф ровно тогда, когда его читают. Потолок окна — 7 дней.
- **Присутствие отмечает только загрузка страницы.** Клиентское обновление ходит в
  `/api/admin/overview?since=…` и отметку не двигает — иначе автообновление сдвигало бы окно
  само. Роут ограничивает пришедший `since` тем же потолком: параметр приходит из браузера.
- **Второй правды о числах не появилось.** Очередь — `loadOrderSlices()` (тот же предикат
  `BUYOUT_QUEUE_SQL`, что во вкладке «Выкупить»), доставка — `loadWbDeliveryQueueSnapshot()`,
  витрина — `getAdminDashboardData()`. Кэш общий, 30 секунд.
- **`AdminPresence.currentOrderId` заведён сразу**, хотя пока только пишется: на нём вырастет
  «в работе у другого админа» — это одна запись, а не две задачи.

### Набор под баланс аккаунта — в «Выкупе», а не на обзоре

Донора как одной большой кассы больше нет: с 30.08.2026 выкуп идёт с мелких аккаунтов под
фиксированное пополнение. Поэтому в панели «Выгрузка ID геймпассов» появился ввод **баланса
аккаунта** (пресеты 2 000 / 3 000 / 5 000 / 10 000, значение запоминается в браузере). Кнопка
«Набрать под баланс» выделяет заказы, которые в него помещаются, **сверху вниз по очереди** —
то есть самые старые первыми, — и рядом появляются «ID выбранных» и «Ссылки на ГП».

Правила набора вынесены в чистый `src/lib/buyout-packing.ts`:

- **Порядок по старшинству, а не по цене.** First-fit-decreasing набил бы аккаунт плотнее, но
  увёз бы старейший заказ в следующий; очередь упорядочена по возрасту именно затем, чтобы он
  шёл первым. Аккаунт стоит копейки, покупатель на четвёртых сутках — нет.
- **Заказ дороже баланса не режется и не прячется.** Заказ на 2 000 R$ стоит 2 858 грязными и
  в аккаунт на 2 000 не влезет никогда — такие выносятся отдельной строкой с кодами и ценой.
- **Считается, сколько ещё таких же аккаунтов нужно** на остаток очереди — тем же правилом,
  чтобы число не расходилось с тем, что наберёт кнопка.

Боевой прогон 02.09: очередь из 19 заказов, баланс 2 000 → помещается 1 заказ на 1 429 R$,
остаток 571 R$, ещё 14 таких же аккаунтов на очередь, 3 заказа не влезают вовсе. Это и есть
ответ на вопрос «сколько аккаунтов заводить сегодня».

### Что осталось за рамками

| Что | Почему |
|---|---|
| Отметка «в работе у другого админа» | Поле `currentOrderId` есть, UI и запись — следующий шаг |
| Выкуп пачкой с обзора | У «Выкуплено» нет обратного действия; пачка живёт в «Заказах» и спрашивает подтверждение с суммой |
| Диф по конкретному админу («это сделал N») | `OrderEvent` не хранит автора действия — отдельная задача |
