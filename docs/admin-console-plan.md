# Админка на сайте — план реализации

> Решение владельца 28.07.2026: **сначала запускаем сайт, ботов подделываем позже.**
> Параллельно переезжаем с админкой в веб — там удобнее и нагляднее, чем в мобильной TWA.
>
> Этот документ — план на согласование. Реализация **не начата**.
> Открытые вопросы владельца — §9, без них старт не имеет смысла.

---

## 1. Что просил владелец

Одна веб-админка, в которой удобно:

- видеть геймпассы и контролировать их состояние;
- вести заказы (все источники: WB, прямые, Авито, сайт);
- **выгружать данные для выкупа — ID геймпассов**;
- работать с прямыми заказами;
- вести партнёрский контур «Антон»;
- работать втроём: **три админских аккаунта**, вход по Telegram без пароля;
- всё это — эргономично, логично и стильно, в духе Apple.

## 2. Где мы сейчас — замер по коду 28.07.2026

Сегодня админка живёт **в двух местах с разной аутентификацией и очень разной силой**.

| | Desktop `/admin` | Telegram TWA `/twa` |
|---|---|---|
| Объём UI | **493 строки**, 7 файлов | **12 665 строк**, 19 файлов |
| Вход | сессия next-auth, `User.role === "ADMIN"`, email+пароль | отдельный JWT `twa-admin`, Telegram ID в `ADMIN_IDS` |
| Заказы | **только просмотр** | **21 действие** (`POST /api/twa/orders`) |
| Выкуп | нет | есть: скрипт, батч, прайс-гард, слив |
| Выгрузка ID геймпассов | нет | есть (`?export=gamepass-ids`) |
| «Антон» (B2B) | нет | есть — `BossrobuxScreen.tsx`, **4979 строк** |
| Аналитика, коды, остатки | нет | есть |
| API-роутов | 7 (`/api/admin/*`) | 34 (`/api/twa/*`) |

Вывод: **desktop-админка сегодня — витрина, а не рабочее место.** Вся настоящая работа
делается с телефона. Именно поэтому переезд оправдан: экран выкупа, очередь заказов и
таблица «Антона» — это работа с плотными данными, для которой мобильный формат тесен.

## 3. Три админа и вход через Telegram — да, и это правильный путь

**Ответ: да, привязка Telegram может выдавать админку автоматически.** Механизм уже есть,
собирать почти нечего:

- провайдер `telegram-login` в `src/auth.ts:97` уже проверяет подпись Telegram на сервере
  (`verifyTelegramLogin`, HMAC от токена бота) и гасит одноразовый challenge;
- `UserIdentity` уже хранит **проверенную** TG-личность;
- `ADMIN_IDS` уже содержит список админов и уже используется ботом и TWA.

### Предлагаемая модель: роль **выводится**, а не хранится

Единственный источник правды — `ADMIN_IDS` (список Telegram ID). Гейт админки отвечает на
вопрос: *«есть ли у этого пользователя проверенная TG-личность, чей ID входит в `ADMIN_IDS`?»*

```
Админ жмёт «Войти через Telegram» → подпись Telegram проверена сервером
  → UserIdentity(TG, subject) → subject ∈ ADMIN_IDS ?
      да  → доступ в /admin, роль в сессии, действия пишутся на его TG ID
      нет → обычный личный кабинет
```

Что это даёт:

| Свойство | Почему важно |
|---|---|
| Три админа = три ID в одной переменной | Она уже есть и уже используется ботом/TWA — второй список не заводим |
| Пароли не нужны | Нечего терять, нечего ротировать, нечего фишить |
| Отзыв доступа мгновенный | Убрали ID → следующий запрос уже без прав (**A0.2 чинится здесь же**) |
| Единая атрибуция | Desktop и TWA пишут действия под одним и тем же TG ID |
| Совпадает с TWA | В TWA уже есть `adminSetVersion()`, обесценивающий токен при смене состава — переносим тот же приём в веб |

**Break-glass:** вход по email+паролю остаётся **только для владельца** — на случай, когда
Telegram недоступен. Отдельная строка в `docs/security.md`.

**Обязательное условие:** роль проверяется **на каждом запросе**, а не берётся из JWT.
Иначе A0.2 переезжает в новую админку вместе с кодом.

**Риск, который надо зафиксировать:** слияние аккаунтов (`AccountMergeAudit`) не должно
приводить к наследованию админских прав. Проверка при реализации обязательна.

## 5. Дизайн-язык: «в духе Apple» конкретно, а не на словах

Не «сделаем красиво», а проверяемые правила. Опора — существующие токены `--rb-*`
(светлая и тёмная темы уже есть) и правило «шрифт ≥14 px», закреплённое контракт-тестом D8.

| Принцип | Как выглядит здесь |
|---|---|
| **Список + деталь, а не переходы** | Как в Mail.app: очередь слева, досье справа. Работа с заказом не уводит со страницы и не теряет позицию в списке |
| **Клавиатура — первый класс** | `⌘K` — командная палитра (поиск заказа/ника/кода/действия). `J`/`K` — по очереди, `Enter` — открыть, `E` — в работу, `⌘↩` — подтвердить. Триаж 40 заказов мышью — это не работа |
| **Спокойная плотность** | Данных много, шума мало: один акцентный цвет, статусы — цветом точки, а не заливкой строки |
| **Постепенное раскрытие** | Карточка → досье → полный журнал. Три уровня, не десять модалок |
| **Честная обратная связь** | Оптимистичный UI с откатом, а не спиннер на весь экран. Необратимое (возврат, отклонение) — inline-подтверждение с суммой прописью |
| **Одна сетка** | Общие компоненты таблицы/карточки/статуса. Сегодня desktop и TWA рисуют статусы по-разному |
| **Обе темы** | Только токены `--rb-*`. Литеральные цвета запрещены — правило №4 из `launch-roadmap.md` §6 |

Отдельно: **это не копия TWA на большом экране.** TWA оптимизирована под один палец и один
экран; десктоп должен показывать очередь и досье одновременно и работать с клавиатуры.

## 6. Ключевое техническое решение — единый гейт, а не вторая дверь

Сейчас `/api/twa/*` защищены Bearer-JWT, а `/admin` — сессией. Соблазн — научить desktop
дергать TWA-роуты «как-нибудь». **Так делать нельзя:** это ровно та «вторая, более слабая
дверь к деньгам», о которой предупреждает риск в плане ботов.

Предлагается:

1. Один helper `requireAdmin(req)` — **единственное** место, где решается «админ или нет».
   Принимает оба доказательства: сессию next-auth и Bearer-JWT TWA. Оба пути обязаны
   сойтись к одному ответу: TG ID + `ADMIN_IDS`.
2. Роуты переезжают в `/api/admin/*` по смыслу (заказы, выкуп, партнёры, аналитика).
3. `/api/twa/*` остаются тонкими алиасами на время миграции, чтобы TWA не сломалась
   ни на один день. Удаляются последним шагом.
4. Ни одна проверка прав не пишется внутри роута руками.

Это же решает и «три админа»: атрибуция действия берётся из `requireAdmin`, а не из тела
запроса.

## 7. Этапы

Строго последовательно. Каждый этап оставляет систему рабочей — TWA не отключается, пока
веб не закроет её функции.

### A1. Фундамент доступа — 3 админа и вход по Telegram

| Что | Приёмка |
|---|---|
| `requireAdmin` с двумя доказательствами и одним ответом | Тест: сессия без TG-личности в `ADMIN_IDS` → 403; TWA-JWT снятого админа → 401 |
| Роль выводится из `ADMIN_IDS` на каждом запросе (чиним A0.2) | Удалили ID из `ADMIN_IDS` → следующий запрос уже без прав, **без перелогина** |
| Кнопка «Войти через Telegram» на `/admin/login` | Три админа входят со своих TG, у каждого своя атрибуция в журнале |
| Break-glass email+пароль только для владельца | Второй админ с паролем, но без TG в списке, в `/admin` не попадает |
| Слияние аккаунтов не наследует админку | Тест на `AccountMergeAudit` |
| Убрать мёртвую ссылку `/admin/products` (A0.1) | В сайдбаре нет ссылок, отдающих 404 |

### A2. Оболочка и дизайн-система

Шелл, навигация 9 разделов, командная палитра `⌘K`, общие компоненты таблицы/статуса/
карточки на токенах `--rb-*`, светлая и тёмная темы.
**Приёмка:** контракт-тест на отсутствие литеральных цветов и шрифтов <14 px; горизонтального
вылета нет на 1280/1440/1920.

### A3. Заказы — ядро переезда

Очередь с теми же вкладками и той же семантикой, что в TWA (`buildTabWhere` — общий, не
копия), split-view досье, все 21 действие, клавиатурный триаж.
**Приёмка:** каждое действие TWA имеет эквивалент в вебе и пишет тот же `OrderEvent`;
вкладка «К выкупу» на обоих экранах даёт **одинаковый список**.

### A4. Выкуп и выгрузка ID геймпассов

Рабочее место закупщика: выгрузка ID (уже есть на сервере — `?export=gamepass-ids`, лимит
500, пропуск неоплаченных прямых), копирование списком/CSV, пачка, прайс-гард
(`[ЦЕНА-СТОП]`/`[ПРОДАВЕЦ-СТОП]` остаются обязательными), состояние донора, история батчей.
**Приёмка:** выгрузка совпадает с очередью один в один; заказ без ГП и неоплаченный прямой
в неё не попадают и показаны числом.

### A5. Геймпассы

Живая проверка цены/продавца/sale-state, привязка ГП к заказу, GP-watch.
**Приёмка:** чужой/снятый/подороженный ГП по-прежнему fail-closed.

### A6. Партнёр «Антон»

Перенос B2B-контура **с разбором** 4979-строчного компонента на модули (дашборд, задачи,
ledger, сверка). Правила Антона не меняются — только поверхность.
**Приёмка:** суммы сходятся с эталоном (таблица = эталон); переименование таба листа не
приводит к двойному списанию — **этот баг известен и до сих пор не исправлен**, переезд его
не чинит и не должен маскировать.

### A7. Аналитика, коды, клиенты, журнал

Оставшиеся разделы. Журнал получает фильтр «по админу» — это и есть ответ на «нас трое».

### A8. Роль TWA после переезда

Решение владельца (§9, вопрос О2). Технически TWA остаётся работоспособной на всех этапах.

## 8. Риски

| Риск | Митигация |
|---|---|
| Вторая, более слабая дверь к деньгам | Единственный `requireAdmin`; ни одной проверки прав внутри роутов |
| Расхождение семантики очередей между веб и TWA | Общий `buildTabWhere`, а не копия; контракт-тест на равенство списков |
| Разбор `BossrobuxScreen` (4979 строк) ломает контур Антона | A6 идёт последним; сверка с таблицей до и после |
| Двойная поддержка двух админок | Осознанная плата за безопасный переезд; снимается на A8 |
| Админ теряет доступ при недоступности Telegram | Break-glass email+пароль у владельца |
| Компрометация TG-аккаунта админа = админка | Та же экспозиция, что у TWA сегодня; при желании — второй фактор, обсуждаемо |
| Переезд отвлечёт от запуска сайта | A1 (2–3 дня) можно делать параллельно; A3+ — после волны 2 и открытия |

## 9. Решения владельца — приняты 28.07.2026

| # | Вопрос | **Решение** |
|---|---|---|
| **О1** | Источник списка админов | ✅ **env `ADMIN_IDS`.** Он уже есть и уже используется ботом и TWA; экран управления ролями для троих людей — лишняя сущность |
| **О2** | Судьба TWA после переезда | ✅ **Ужать до срочного.** В телефоне остаются просмотр очереди и срочные действия, плотная работа — в вебе |
| **О3** | Разные права у троих админов | ✅ **Все трое равны.** Матрица прав не нужна; «кто что сделал» видно в журнале по TG ID |
| **О4** | Когда делать A1 | ✅ **Сразу, параллельно запуску.** A1 не трогает платёжный контур; A3+ — после открытия сайта |
| **О5** | Три Telegram ID для `ADMIN_IDS` | 🔴 **ждём от владельца** — единственное, что блокирует старт A1. Только в env, в публичный репозиторий не попадёт |

Следствия принятых решений для плана:

- роль выводится из `ADMIN_IDS`, роли в БД не заводим (`User.role` остаётся только для
  break-glass владельца);
- в A8 TWA ужимается: оставляем очередь на просмотр и срочные действия, остальные экраны
  снимаются после того, как веб закроет их функции;
- A1 стартует немедленно по получении О5; A2 (оболочка) — следом, A3+ после открытия сайта.

## 10. Что в план не входит

- Изменение правил Антона, прайс-гарда и логики выкупа — переносится поверхность, не правила.
- Исправление известного бага двойного списания при переименовании таба листа (`b2b-saas.md`).
- Автовыкуп геймпассов — отдельное направление (`roblox-plus-buyout-plan.md`).
- Эквайринг в ботах — отложен владельцем (`bot-acquiring-plan.md`).
- Внешние гейты запуска (ККТ, категория Т‑Банка, 152-ФЗ) — не связаны с админкой.
