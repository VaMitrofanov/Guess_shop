# DBS: ультра-ревью раздела и план доводки (20.08.2026)

Ревью раздела WB DBS целиком: воронка покупателя, консоль оператора (desktop `/admin` и
TWA), рабочий контур worker'а и язык уведомлений. Основано на живых данных прода на
20.08.2026 06:42 МСК, не на предположениях: 46 DBS-заказов, 36 выпущенных гейтов,
27 сообщений одного проблемного чата, аудит-трейл и живой ответ WB `status/info`.

Базовый документ контура — `wb-dbs-delivery-plan.md`. Здесь только то, что найдено
сверху него, и что предлагается менять.

## 2. Критические находки (деньги и дедлайны)

### F1 · Авто-закрытие доставки проиграло гонку собственному автоответу — замечание №4

**Корневая причина найдена.** `tryAutoReceive` вызывается ровно один раз — в момент
захвата кода (`captureDeliveryCode`), — и первым делом проверяет `canReceiveWbOrder`,
которому нужен `supplierStatus ~ /deliver/`. А **в системе нет ничего, что переводит
DBS-заказ `new → confirm → deliver`**: `confirmDbsOrder` и `deliverDbsOrder` вызываются
только из ручных кнопок консоли. Значит закрытие доставки работает лишь тогда, когда
владелец успел прожать «Сборка» и «В доставку» в кабинете WB раньше, чем покупатель
прислал код.

Что сломало баланс — **наш же `WB_DBS_AUTO_REPLY`**. До него покупатель отвечал через
час-два, и владелец успевал. После него автоответ уходит через ~90 секунд после заказа, и
код прилетает через 3 минуты. Хронология двух заказов 19.08:

```
5535102507  17:17:14 заказ → 17:18:04 запрос кода ИЗ КАБИНЕТА (владелец был в WB руками)
            → 17:18:39 код → 17:18:40 WB_RECEIVE_SUCCEEDED ✅   (заказ успел стать deliver)
5536140025  22:48:28 заказ → 22:50:05 АВТООТВЕТ → 22:51:50 код → тишина ❌
            → 23:06:18 ORDER_SYNCED: supplierStatus всё ещё «confirm»
```

Во втором случае в аудите **нет ни `WB_RECEIVE_SUCCEEDED`, ни `WB_STATUS_MUTATION_FAILED`** —
`tryAutoReceive` вышел по `return` до всякой попытки. Тихо. Без уведомления.

**Следствие:** комиссия WB выше на каждом таком заказе, а оператор узнаёт об этом только
если сам заметит отсутствие второго сообщения в TG.

### F2 · `lastErrorCode` — билет в один конец

`canReceiveWbOrder` требует `!order.lastErrorCode`. Любая посторонняя ошибка — истёкший
секрет, отказ чата, 500 от WB — навсегда выключает авто-закрытие для этого заказа: ничего
в системе `lastErrorCode` автоматически не снимает. `applyWbStatus` пишет
`lastErrorCode: undefined` при здоровом опросе, а Prisma трактует `undefined` как «не
трогать», так что поле живёт до ручного действия оператора.

### F3 · Ручной выкуп из DBS вешает покупателя на служебный аккаунт — замечание №1

`createInternalOrder` привязывает заказ так:

```ts
user: order.wbCode?.userId
  ? { connect: { id: order.wbCode.userId } }
  : { connectOrCreate: { where: { tgId: "admin" }, create: { tgId: "admin", … } } }
```

К моменту ручного создания гейт-код по определению **ещё не активирован**, значит
`wbCode.userId` всегда `null`, значит ветка всегда падает в `admin`. Покупатель после
этого невидим: ни «Мой заказ», ни уведомление «выкуплено», ни возможность написать ему.

И даже когда покупатель приходит позже: в `bots/tg/handlers.ts` провизорная транзакция
делает `if (existingOrder) return existingOrder` — заказ есть, значит `WbCode.userId` и
`WbOrder.userId` **не переписываются**. Человек проходит весь путь, а заказ остаётся на
`Admin (Avito)`.

Ровно это и произошло с `CAA4BR9`. Плюс покупатель прислал в бот **код доставки WB**
(`781526`) вместо гейт-кода и получил «У тебя сейчас нет активных заявок» — тупик там, где
у нас есть точное совпадение: `WbDeliverySecret.codeHmac`.

### F4 · Скидка 60 ₽ самовозобновляется бесконечно — замечание №3

`directPrice(100) = 144 ₽`. `144 − 60 = 84 ₽` — ровно та цена из уведомления владельца.

Источник — два одинаковых куска кода:

- `bots/tg/handlers.ts:5495` (`notifyUserCompleted`)
- `src/lib/twa-notify.ts:216` (`notifyOrderCompleted`)

```ts
const discountGranted = isDirectOrder && amount < 500;
if (discountGranted) await user.update({ data: { rubleDiscount: 60 } });
```

Это не «один раз при сгорании бонуса», а **начисление 60 ₽ после каждого завершённого
прямого заказа меньше 500 R$**. Заказ на 100 R$ как раз меньше 500 — петля замкнута:
скидка → заказ за 84 ₽ → завершение → снова скидка. Ни срока, ни счётчика, ни связи со
сгоревшим бонусом.

Факт по конкретному клиенту (`leertsss`, ник Roblox `SonyaSyperKotik`):

| Дата | Сумма | Оплачено | Скидка |
|------|-------|----------|--------|
| 28.07 | 500 R$ | 390 ₽ | 60 ₽ |
| 10.08 | 100 R$ | 84 ₽ | 60 ₽ |
| 13.08 | 100 R$ | 84 ₽ | 60 ₽ |
| 18.08 | 100 R$ | 84 ₽ | 60 ₽ |
| 19.08 | 100 R$ | 84 ₽ | 60 ₽ (заказ ещё `PENDING`) |

Утечка по этому клиенту — 300 ₽; сейчас скидку держат ещё 4 аккаунта. Это немного в
рублях, но правило неверно на уровне политики и масштабируется вместе с прямыми заказами.

Отдельно: `promoExpiresAt` в схеме `User` есть, но политика скидки его не читает —
в `price-quote.ts` это прямо зафиксировано комментарием «The bot policy has no promo
expiry gate».

### F5 · Чистка истёкших секретов ломает живые заказы

`purgeExpiredDeliverySecrets` для любого секрета с истёкшим TTL и `gateState != NOT_ISSUED`
ставит `lastErrorCode: "DELIVERY_CODE_EXPIRED"` — **без проверки `completedAt`**. Заказ,
который уже закрыт и по которому делать нечего, уезжает в стадию `attention` и кричит
оператору. А в связке с F2 это ещё и навсегда выключает авто-закрытие.

В проде такие события уже были: `DELIVERY_CODE_EXPIRED` по заказам `5507223980`,
`5508907054`, `5511394074`, `5513683685`. Сейчас на очереди 6 неиспользованных секретов,
5 из них — по уже закрытым заказам.

## 3. UX оператора

### F6 · Хиро-цифра «активных DBS» не совпадает с вкладкой «В работе» (desktop)

`metrics.active` считается по стадиям (`!WB_TERMINAL_STAGES`), а фильтр «В работе» —
по таймстампам: `(!completedAt && !cancelledAt) || stage === "in_bot"`. Заказ в стадии
`attention` из-за `isWbBuyerUnserved` имеет `completedAt` — он входит в счётчик, но
**выпадает из списка**. Самое громкое состояние контура не видно на вкладке по умолчанию.

### F7 · Рельса этапов не знает половину стадий

`stageIndex` в desktop-консоли не различает `attention`, `in_bot`, `cancelled` — все три
дают `0`, то есть «Заказ». Открыв заказ, который давно в боте, оператор видит прогресс
в самом начале.

### F8 · Две консоли разошлись поколениями

TWA-экран уже умеет: секции «Наш ход / Ждём покупателя / В нашем боте`, фокус-плитки с
теми же предикатами, что и счётчики, подпись по шагу воронки. Desktop остался на плоском
списке и шести фильтрах. Словарь общий (`wb-delivery-labels.ts`), а раскладка — нет.
Оператор, переходя с телефона на десктоп, теряет структуру.

### F9 · Уведомление о коде доставки говорит неправду

`notifyDbsCodeCaptured` пишет «Покупатель прислал код доставки — можно выпускать гейт».
С включённым `WB_DBS_AUTO_GATE` гейт выпускается сам через полсекунды. Оператор читает
подсказку к действию, которого делать не надо.

### F10 · Тихий пропуск авто-receive нигде не виден

Уведомления есть на успех (`notifyDbsAutoReceived`) и на ошибку
(`notifyDbsAutoReceiveFailed`), но **не на «не выполнилось, потому что предусловие не
сошлось»**. Именно этот случай и происходит (F1). Молчание неотличимо от того, что
сообщение просто не дошло.

### F11 · Неактивированный гейт никого не будит

14 % кодов не открыты. В WB-чате после отправки гейта не уходит ни одного напоминания,
в консоли `funnelStep: not_activated` — просто подпись.

### F12 · Очередь жёстко обрезана на 150

`loadOrders` берёт `take: 150` и грузит их вместе с чатами и секретами каждые 20 секунд,
на двух поверхностях. При ~10 DBS-заказах в день лимит выберется за две недели, и вкладка
«Готово» начнёт молча терять историю. Метрики при этом считаются в JS по уже загруженным
DTO, хотя это агрегат, который умеет БД.

Кейс `5522171657` показывает цену этого: покупатель застрял, дальше **пять с половиной
часов переписки в WB-чате за два дня**, ручной разбор скриншотов, ручное создание выкупа
и просьба «напишите нам в телеграм, чтобы привязать заказ».

### F14 · Код доставки, отправленный в бот, — тупик

Покупатель отправляет боту 5–6 цифр из приложения WB (естественная ошибка: ему только что
велели прислать «код» в чат). Бот отвечает «У тебя сейчас нет активных заявок». При этом
у нас есть `WbDeliverySecret.codeHmac` — точный, дешёвый и однозначный ключ поиска.

### F15 · «Не нашли геймпасс» не лечится самим покупателем

В боте ветка `no_gamepasses` написана хорошо (объясняет закрытый плейс, даёт кнопку
«Уже сделал — проверить»). На странице гейта такого разбора нет, а покупатель до бота
не доходит (F13). В разобранном чате причина была именно эта — скрытые настройками
геймпассы, — и лечил её оператор вручную.

## 5. Замечание №2 — язык уведомлений

Сейчас в TG-админку пишут ~25 разных мест (`bots/shared/admin.ts`,
`wb-delivery-admin-notify.ts`, `bots/tg/handlers.ts`, `bots/vk/handlers.ts`, кроны,
авто-воркеры). Эмодзи выбраны по вкусу: 📦 🔑 🤖 ✅ ⚠️ 🚫 💬 🔷 📥. По одному сообщению
нельзя понять, надо ли что-то делать, и один DBS-заказ порождает 4–5 отдельных сообщений.

### Предложение A — единый префикс стадии (дёшево, везде)

Один глиф = одно значение, никогда не переиспользуется:

| Маркер | Значит | Оператору |
|--------|--------|-----------|
| 🔵 `ИДЁТ` | промежуточный этап, автоматика работает | ничего |
| 🟡 `ЖДЁМ` | мяч у клиента | ничего |
| 🟠 `НУЖЕН ТЫ` | требуется ручное действие | да |
| 🔴 `СРОЧНО` | деньги или дедлайн под угрозой | немедленно |
| 🟢 `ГОТОВО` | этап закрыт | ничего |
| ⚫️ `ОТМЕНА` | заказ умер | проверить хвосты |

Формат: `<маркер> <ЗОНА> · <что произошло>` + строка `Дальше: …`.
Зоны: `DBS`, `ПРЯМОЙ`, `WB`, `САЙТ`, `ВЫКУП`, `ОТЗЫВ`, `СИСТЕМА`.

Цепочка DBS в новом языке:

```
🔵 DBS · заказ принят
WB #5536140025 · 500 R$ · 1 090 ₽
Дальше: авто-запрос кода доставки

🟡 DBS · ждём код доставки
WB #5536140025 · Елена
Дальше: покупатель пришлёт 5–6 цифр в чат WB

🟢 DBS · доставка закрыта, гейт отправлен
WB #5536140025 · код 66TFQTZ · 500 R$
Дальше: покупатель активирует код в боте

🟠 DBS · доставка не закрылась
WB #5536140025 · WB держит статус «На сборке»
Дальше: кабинет WB → «Передать в доставку». Окно WB истекает в 23:51
```

### Предложение B — одна живая карточка на заказ (для DBS)

Вместо 4–5 сообщений на заказ — **одно, которое редактируется** (`editMessageText`).
Сверху текущее состояние, снизу свёрнутая история этапов:

```
🟢 DBS · WB #5536140025 · 500 R$ · Елена
Гейт 66TFQTZ отправлен, доставка закрыта.
Дальше: покупатель активирует код

├ 22:48 заказ принят
├ 22:50 запрошен код
├ 22:51 код получен
├ 22:51 доставка закрыта
└ 22:51 гейт отправлен
                       [Открыть в консоли]
```

10 заказов в день дают 10 карточек вместо ~50 сообщений. Требует хранить `messageId`
на пару «админ × DBS-заказ».

**Рекомендация:** A — на все зоны сразу (дёшево, ломать нечего). B — только для DBS,
где цепочка длинная и предсказуемая.

## 6. План реализации

Порядок — по стоимости ошибки, не по сложности. Все этапы независимы и деплоятся
по отдельности.

### Э1 · Доставка закрывается сама, всегда — P0 (замечание №4)

1. **Авто-`confirm` и авто-`deliver`.** Новый флаг `WB_DBS_AUTO_SHIP`. Отдельный проход
   в цикле worker'а: `supplierStatus = new → confirmDbsOrder`, `confirm → deliverDbsOrder`.
   Заказ доходит до `deliver` за считанные секунды после появления, задолго до кода.
   Пишутся `WB_CONFIRM_SUCCEEDED` / `WB_DELIVER_SUCCEEDED` в аудит.
2. **Ретрай авто-receive.** `tryAutoReceive` перестаёт быть одноразовым: каждый цикл
   выбирает заказы с живым секретом в статусе `deliver` и добивает их. Пропуск в момент
   захвата больше не фатален.
3. **`lastErrorCode` больше не блокирует навсегда.** Убрать его из `canReceiveWbOrder`,
   ограничить повторы через `WbDeliverySecret.failedAttempts < 3`; `applyWbStatus`
   явно чистит `lastErrorCode`, когда WB отдаёт здоровый статус.
4. **F5:** `purgeExpiredDeliverySecrets` не ставит ошибку заказам с `completedAt`.
5. **Тихий пропуск озвучен.** `tryAutoReceive` возвращает причину; уведомление о полученном
   коде говорит, закрылась доставка или нет и что мешает (**F9 + F10**).
6. **SLA-алерт.** Живой секрет старше 20 минут по незакрытому заказу → одно 🔴-сообщение
   с остатком окна WB.

*Готово когда:* по 10 подряд реальным заказам `WB_RECEIVE_SUCCEEDED` есть у каждого, а
любой пропуск сопровождается 🟠-сообщением с названием причины.

### Э2 · Покупатель всегда привязан к своему аккаунту — P0 (замечание №1)

1. **Усыновление при активации.** В TG и VK: если по коду уже есть заказ и он висит на
   служебном `admin` (или у `WbCode` нет `userId`) — перевесить заказ и код на пришедшего
   человека, записать аудит и уведомить админов.
2. **Код доставки как мост (F14).** 5–6 цифр от пользователя, не подошедшие под гейт-код,
   ищутся по `WbDeliverySecret.codeHmac`. Совпало — привязываем покупателя к DBS-заказу и
   сразу отвечаем статусом и персональной инструкцией.
   *Требует:* хранить `codeHmac` после закрытия доставки (сейчас строка удаляется по TTL),
   лимит 3 попытки в час на пользователя, **окно авто-привязки 3 часа** (О5), только
   неактивированный гейт. За пределами окна — нейтральный ответ и пинг оператору, см. §7.
   Плюс `WbDeliverySecret` перестаёт удаляться — обнуляется `encryptedValue`, остаётся хеш.
3. **Кнопка «Привязать покупателя»** в консоли DBS: `@username`, tgId или vkId → та же
   операция, что делает скрипт, но без SSH.
4. `createInternalOrder` перестаёт молча ронять заказ на `admin`: помечает его как
   «покупатель не привязан» и показывает это в консоли отдельным чипом.

*Готово когда:* ни один `WB_DBS`-заказ не висит на служебном пользователе; отправленный
в бот код доставки открывает заказ покупателя.

### Э3 · Скидка 60 ₽ выдаётся один раз — P0 (замечание №3)

1. Обе точки начисления (`bots/tg/handlers.ts`, `src/lib/twa-notify.ts`) заменяются одним
   общим модулем политики — расхождение каналов больше невозможно.
2. Новое правило: начисляется **однократно за всё время**, срок жизни 14 дней
   (`promoExpiresAt`), и все три поверхности (бот, TWA, сайт) этот срок читают.
3. Триггер — **решение владельца** (см. §7 О1): либо «сгорел бонус за отзыв», либо
   текущий «первый прямой заказ < 500 R$», но с флагом «уже выдавали».
4. Миграция: `User.discountGrantCount`, бэкофилл по истории `discountAppliedKopecks`.
5. Данные: сейчас 60 ₽ держат 4 аккаунта — оставить или обнулить (**О2**).
6. Контрактный тест: два завершённых прямых заказа подряд дают ровно одну скидку.

*Готово когда:* повторный прямой заказ на 100 R$ стоит 144 ₽.

### Э4 · Контакты до инструкции — P1 (замечание №5) · решения О4 приняты

Ссылку в WB-чате **не меняем**: WB штрафует за увод в мессенджеры, а `/guide` нейтрален.
Меняется первый экран после проверки кода.

```
WB-чат ──► /guide?code=…  ──► [Экран 0: куда прислать заказ?]
                                  │  Telegram / ВКонтакте          │ «Продолжить без привязки»
                                  ▼                                ▼
                              бот привязывает заказ            инструкция как сейчас,
                              и открывает инструкцию           мессенджеры повторно в конце
                              кнопкой web_app — ВНУТРИ
                              Telegram, назад в браузер
                              возвращаться не надо
```

Ключ к «не выглядит тупо»: браузер покупатель покидает **ровно один раз и навсегда**.
Инструкция переоткрывается как Telegram WebApp внутри того же чата, а рядом — кнопка
«Пройти прямо здесь» (бот уже умеет ник → поиск геймпасса → подтверждение).
Для VK — существующий виджет VK ID (`VKAuthButton mode="order"`).

Дополнительно:
- Кнопки «продолжить без привязки» нет (О4): инструкция не открывается без привязки.
  Мессенджер и так обязателен на шагах 05–06, экран лишь переносит требование в начало.
  Под кнопками — только канал связи, не обход: поддержка `@RobloxBank_PA` и чат WB по
  заказу. Дальше ведёт живой человек, оператор при необходимости открывает выкуп руками.
- События `guide_contact_shown / picked_tg / picked_vk / skipped` — без них мы не узнаем,
  стало ли лучше.
- **F15:** на странице гейта появляется тот же разбор «не видим твой геймпасс», что уже
  написан в боте, но с призывом **«Пиши в поддержку»** вместо кнопки «Проверить ещё раз» —
  страница не умеет перезапускать поиск, это работа бота.

*Готово когда:* доля DBS-заказов с привязанным мессенджером до входа в инструкцию ≥ 80 %,
а «код не активирован» падает с текущих 14 %.

## 7. Решения владельца — приняты 20.08.2026

| | Вопрос | Решение |
|---|--------|---------|
| **О1** | Триггер скидки 60 ₽ | **Отложен.** «Позже закроем» — Э3 не начинаем |
| **О2** | 4 аккаунта со скидкой | **Оставить как есть**, не обнулять |
| **О3** | Авто-перевод в «доставку» | **Да, обязательно** — `WB_DBS_AUTO_SHIP` включаем |
| **О4** | Экран 0 | **Жёсткий: только TG или VK.** Кнопки «продолжить без привязки» нет |
| **О5** | Привязка по коду доставки | **Да**, но окно авто-привязки — **3 часа**, дальше вручную |
| **О6** | Язык уведомлений | **A + B**: маркеры на все зоны, живая карточка — для DBS |

### Что означает О1 «отложен»

Пока решение не принято, петля работает: каждый выполненный прямой заказ меньше 500 R$
снова начисляет 60 ₽. Э3 стоит целиком — это осознанное решение владельца, не забытый
хвост. Единственное, что можно сделать без О1, — свести две копии начисления
(`bots/tg/handlers.ts:5495` и `src/lib/twa-notify.ts:216`) в один модуль политики без
изменения поведения. Тогда, когда О1 придёт, правило меняется в одном месте.

### Что означает О4 «строго TG или VK»

Жёсткий экран **никого не запирает дополнительно**, и это важно: мессенджер уже сегодня
обязателен, чтобы довести WB-заказ до конца — шаги 05–06 инструкции прямо требуют прислать
ссылку на геймпасс в Telegram или ВКонтакте. Экран 0 не добавляет требование, а переносит
уже существующее в начало пути, где от него есть польза.

Привязка обязательна без исключений: **инструкция не открывается, пока покупатель не выбрал
Telegram или ВКонтакте.** Запасной выход есть, но это **канал связи, а не обход** — мелкой
строкой под кнопками: «Не получается? Напишите в поддержку `@RobloxBank_PA` или прямо в чат
Wildberries по этому заказу». Оттуда покупателя ведёт живой человек, и оператор при
необходимости открывает выкуп руками из консоли DBS — ровно так и был обслужен `CAA4BR9`.

Разница принципиальная: кнопки, которая пускает дальше по инструкции без привязки, на
экране нет вообще. Есть только два способа продолжить самому (TG, VK) и два способа
позвать человека (поддержка TG, чат WB).

Разбор «не видим твой геймпасс» на странице инструкции **остаётся** (это отдельное решение
владельца при уточнении). Меняется только призыв: вместо кнопки «Проверить ещё раз» —
**«Пиши в поддержку»**, потому что страница не умеет перезапускать поиск геймпасса, это
работа бота, и кнопка-обманка там хуже честной ссылки. Адрес поддержки выбирается по тому
мессенджеру, к которому покупатель уже привязан: `https://t.me/RobloxBank_PA` или
`https://vk.me/club237309399`.

### Что означает О5 «после 3 часов вручную»

Окно авто-привязки по коду доставки — 3 часа с момента получения кода:

- **внутри окна** совпадение по `codeHmac` привязывает покупателя и сразу отвечает ему
  статусом заказа;
- **вне окна** привязки не происходит. Бот отвечает нейтрально — «похоже на код доставки
  Wildberries, зову менеджера» — и **тот же самый текст показывается при несовпадении**,
  иначе бот превращается в оракул для подбора пятизначного кода. При реальном совпадении
  уходит уведомление админам с кнопкой привязки;
- лимит в обоих случаях — 3 попытки в час на пользователя.

Оговорка, которую надо знать заранее: случай, с которого всё началось, в 3-часовое окно
**не попал бы** — Лера написала боту через сутки. Он попадает в ручную ветку: оператор
получает пинг и привязывает в один клик. Цель достигается, просто через человека — как
владелец и решил.
