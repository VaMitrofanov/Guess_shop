### D4 — блок кодов активации больше не главный CTA

Решение владельца: тизер оставить, но сделать тише и легче; главный CTA — геймпасс.
Сделано в `src/app/page.tsx` и `src/app/storefront.module.css`:

- **Первый экран.** Единственная кнопка героя — «Купить через геймпасс» → `#calculator`.
  Вход в блок кодов — тихая ссылка `.heroTextLink` «Коды активации — скоро». Кнопок,
  ведущих в невключённый сценарий, на первом экране нет.
- **Карточка способа.** Крупная градиентная карточка теперь про геймпасс
  (`.gamepassHeroCard`, бывшая `.codeMethodCard`), коды — компактная строка `.codeTeaser`
  под ней. Макет «билета» (`.codeTicket`) удалён.
- **Цены нет.** «от 309 ₽» убрано из героя, рубли убраны из плитки номиналов, бейдж
  «Популярный» снят: цена и «популярность» товара, который нельзя купить, — вопрос и к
  конверсии, и к проверке банка. `page.tsx` больше не импортирует `CODE_PRICES`.
- **Блок `#codes`.** Вместо трёх уровней текста подряд — один заголовок + одна строка
  описания. `disabled`-кнопка «Скоро в продаже» и дублирующая подпись заменены на строку
  состояния `.codesStatus` со ссылкой на работающий способ.
- **Порядок в `productsGrid`.** Калькулятор идёт первым и получает больше места, витрина
  кодов — справа.
- **Ниже по странице.** Плитка преимуществ больше не обещает три вещи про коды; виджет
  статуса «Код мгновенной активации» убран (он показывал несуществующий поток); нижний CTA
  ведёт на калькулятор, коды остались текстовой ссылкой.

Сбор интереса («Сообщить, когда появится») сознательно не делался: это отдельная фича с
API, хранением адресов и согласием — она относится к этапам K0–K9
([roblox-codes-plan.md](roblox-codes-plan.md)), а не к разгрузке витрины.

### D12 — шапка вылезала за экран на 768 px (найдено при приёмке волны 3)

Волна 1 вернула вход в ЛК на планшеты (`md:flex` вместо `lg:flex`), но ссылки секций
остались `md:flex` — и на 768 px шапка перестала помещаться: `scrollWidth` **928** при
`clientWidth` 768. На витрине симптом маскировал `overflow-x:hidden` в `storefront.module.css`,
поэтому вылет был виден только на `/login`, `/faq` и в ЛК.

Ссылки секций показываются с `lg`, бургер прячется тоже с `lg`, дублирующая пара кнопок
внутри выпадающего меню скрыта с `md`. Итог по ширинам: до 1023 px — бургер с секциями плюс
иконка ЛК и CTA в шапке; с 1024 px — горизонтальное меню без бургера. Вход в ЛК доступен
на **каждой** ширине.

Инвариант закреплён `src/__tests__/navbar-breakpoints.test.ts`: бургер обязан прятаться ровно
на том брейкпоинте, где появляются ссылки секций (разъехались — значит либо дыра, где секций
нет нигде, либо перегруз). Тест заодно стережёт D1 (никаких литеральных цветов, кроме знака
`R$`), D2 (ЛК не позже `md`) и D7 (подпись «Войти»/«Кабинет»). Проверен негативно.

Измерено headless-Chrome на 360/390/414/640/768/820/834/1024/1280/1440 для `/`, `/login`,
`/faq`, `/dashboard`: горизонтального вылета нет нигде.

## Site hardening и наблюдаемость (16.07.2026)

- Добавлены фирменные App Router surfaces `not-found.tsx`, `error.tsx` и
  `global-error.tsx`: 404 действительно возвращает HTTP 404, неожиданный render error даёт
  безопасный retry и показывает только диагностический digest без текста исключения/ПД.
- Root layout передаёт Core Web Vitals (`CLS/FCP/INP/LCP/TTFB`) и fingerprint клиентских
  ошибок в `/api/observability/client`. Контракт не принимает query string, raw message,
  email или произвольный payload. С 18.07.2026 endpoint пишет принятые сигналы только в
  структурированные server logs и **никогда не пересылает их в операционный Telegram**:
  отдельные browser-error/LCP не являются заказными событиями и создавали шум/повторы.
  Диагностика релиза ведётся по логам и агрегатам, а бот остаётся каналом действий.
  `SiteObservability` использует стабильный callback (требование Next.js) и session-level
  dedup по `metric.id`/`route+fingerprint`, поэтому повторный render/navigation одного tab
  не размножает одинаковый сигнал; новый page load остаётся отдельным измерением.
- Checkout, login/register, payment-status и незавершённые legal pages отдают
  `noindex,nofollow`. Оферта/политика исключены из sitemap, пока владелец не передаст
  реквизиты и документы не пройдут приёмку. Public FAQ/guarantees/reviews получили
  собственные title/description/canonical.
- Из видимого сайта удалены неподтверждённые обещания `Apple Pay / Google Pay`,
  «мгновенно», «авто-выдача», «поддержка 24/7». Пока acquiring закрыт, guide/FAQ прямо
  говорят, что платёжная кнопка появится только после внешних launch gates.
- `/api/wb-code/select-gamepass` и `/api/orders/[id]` получили отдельные per-IP buckets;
  статус заказа по-прежнему раскрывается только владельцу сессии или по случайному token.
- Web и Guide отдают `X-RobloxBank-Guide-Release`: fingerprint общих guide-исходников,
  компонентов, libs и assets. `scripts/smoke-corridor.mjs` сравнивает значения SITE/Web и
  WB/Guide и падает при отставшем контейнере; это минимальная автоматическая защита, пока
  последовательный автодеплой двух Coolify applications не настроен.
- Read-only `npm run smoke:site` проверяет health/security headers, custom 404,
  robots/sitemap, SITE guide, maintenance/public root и OpenGraph. Локальный production
  build 16.07: `15/15`; browser QA `1440×1000` и `390×844`, overflow отсутствует,
  checkout/legal `noindex` подтверждён, console errors = 0.

## Фазы гейта — `GuideClient.tsx`

`intro → gate → instruction`. Стартовая фаза выбирается по props из `page.tsx`:

| Query | Смысл |
|-------|-------|
| `?source=wb` | WB-коридор: intro/gate, затем единый gamepass guide |
| `?source=site&amount=1000&username=Nick` | единый gamepass guide в режиме SITE; сумма и ник сохраняются до checkout |
| `?source=direct` | тот же актуальный gamepass guide с CTA бота |
| `&skip=1&code=XXXX` | открыть инструкцию напрямую (ссылка от бота; работает в Telegram WebView, где localStorage изолирован) |
| `&test=1` или `code=TESTDEV` | тихий QA-просмотр: без резерва/бота/БД/алертов, кнопки TG/VK **инертны** |
| `&preview=1` | как test, но кнопки **рабочие** («как будто код уже активирован») |
| `&nom=1000` | номинал для test/preview |

Восстановление сессии (`useEffect` при монтировании): `loadWBSession()` из localStorage →
`?code=` из URL → `GET /api/wb-code?code=` → если `claimed` показывает фазу instruction.
Таймаут 10 с на восстановление. Экран восстановления оформлен как дверца цифрового сейфа:
фиолетово-мятная анимация, короткая пасхалка и `prefers-reduced-motion`. CSS-фолбэк через
12 с показывает обновление страницы и прямые TG/VK-ссылки даже без гидрации. Для SITE и
тихих QA-режимов экран не мелькает: восстановление включается только для реального WB flow.

### RobloxBank как цифровой сейф — финальный проход редизайна

- Фирменная метафора — **цифровой сейф для Robux**: на главной появился крупный фоновой
  vault-door, банковский штамп RobloxBank и единая фиолетово-мятная система статусов.
  Иконка вкладки (`app/icon.svg`) и Apple icon используют ту же дверцу сейфа с `R$`.
- После выбора пакета калькулятор сразу просит ник Roblox. Для авторизованного клиента
  `/api/account/me` подставляет сохранённый ник, но поле остаётся редактируемым. Главный CTA
  ведёт сразу в `/checkout?amount=…&username=…`: инструкция больше не является обязательной
  остановкой до проверки уже готовых геймпассов.

## Инструкции WB и сайта

- `WB`, `SITE` и `BOT` обслуживает один `GuideClient → WBInstructionV2`. Девять шагов,
  assets, Managed pricing warning, расчёт и поиск больше не копируются; различаются только
  заголовок, фиксированный/редактируемый номинал и финальный handoff.
- В режиме SITE желаемая сумма редактируется только в расчёте шага 7 и ограничена единым
  диапазоном `CUSTOM_MIN=100` / `CUSTOM_MAX=100 000`. Финал ведёт в
  `/checkout?amount=…&username=…&gamepassId=…`, поэтому выбранный пасс не нужно искать снова.
- Checkout реализует search-first: по нику вызывает агрегирующий
  `/api/roblox/gamepasses`, показывает **все** публичные пассы на продажу, сортирует ближайшие
  к ожидаемой gross-цене наверх и автоматически выбирает единственное совпадение. Состояния
  `user not found`, `no gamepasses`, `wrong price` сохраняют сумму/ник и дают явный fallback
  в инструкцию. Выбор промежуточной игры из пользовательского пути удалён.
- Калькулятор главной выполняет тот же lookup с debounce уже после ввода валидного ника:
  показывает Roblox headshot, display name/username и состояние пассов. При точном готовом
  пассе ведёт в checkout с preselect; при существующих пассах другой цены — в активный
  выбор; при отсутствии/ошибке — в сохранённую инструкцию.
- Выбор продаваемого пасса другой цены не заставляет возвращаться к калькулятору: checkout
  вычисляет чистые R$ из gross-цены пасса, обновляет рублёвую стоимость и повторно
  подтверждает пару «аккаунт → пасс». Диапазон остаётся `100–100 000 R$`; owner, sale-state
  и цена повторно проверяются сервером.
- `src/lib/gamepass-search-view.ts` фиксирует общую сортировку и channel-specific match:
  SITE/WB/BOT используют общий безопасный допуск buyout ±2 R$ (нужен из-за целочисленного
  округления 30% комиссии); произвольная большая подмена цены по-прежнему блокируется.
  Contract-тест защищает от скрытия неподходящих, но полезных для диагностики пассов.
- Инициализация темы теперь детерминирована (`auto/light` на SSR и первом client render),
  а `localStorage`/`matchMedia` читаются после mount — SITE guide больше не получает
  hydration mismatch `Sun ↔ Moon`.

## WBGate — ввод кода

- Поле нормализует ввод: `[^a-zA-Z0-9] → ""`, upper-case, 7 символов.
- `validateAndPersist()` → `POST /api/wb-code` (резерв) → сохраняет сессию + cookie `wb_code`.
- Обе кнопки (TG/VK) вызываются с `guide=true`:
  - **TG:** редирект `t.me/RobloxBankBot?start=wbg_КОД_SESSIONID` (`wbg_` = guide-режим).
  - **VK:** показывает `VKAuthButton` с `wbCode = GD+КОД` (`GD` = guide-режим).
- Fallback-контакт менеджера `@RobloxBank_PA` на ошибках и внизу карточки.

> Замечание: в текущей вёрстке «чистый» `wb_`-префикс (не guide) с гейта не отправляется —
> обе кнопки всегда guide. Обработчик `wb_` в боте остаётся для прямых/старых ссылок.

### VK-кнопка и CSP — обязательная сверка хостов

VK-кнопка работает через официальный bundled npm SDK `@vkid/sdk@2.6.6` и прямой
`Auth.login` в отдельном окне, без скрытого OneTap iframe. SDK строит свои эндпоинты от
домена **`vk.ru`** (`id.vk.ru`, `oauth.vk.ru`,
`api.vk.ru`, `login.vk.ru`), а не `vk.com`. Content-Security-Policy сайта и Guide-сборки
(`next-security.ts`, общий для обоих контейнеров) обязан включать эти хосты в
`connect-src` и `frame-src` — иначе обмен OAuth-кода блокируется браузером молча, и
клиент после окна VK видит «Ошибка авторизации», хотя все серверные роуты здоровы.
При обновлении SDK или правке CSP сверять список хостов (риск №16 в
[security.md](security.md)). Диагностика: ошибки видны только в браузерной консоли
(CSP violation), на сервере следов нет; страница и `/api/wb-code` при этом отвечают 200.

Смежная эксплуатационная деталь: HTML гейта отдаёт Guide-контейнер, статика идёт через
префикс `/_next-guide` (Traefik → Guide), поэтому смоук «страница 200» не доказывает
работоспособность JS — проверять нужно и чанки из HTML, и фактический VK-вход.

Оба класса поломок ловятся автоматически: контракт-тест
`src/__tests__/csp-vk-hosts.test.ts` (CI) и синтетический смоук
`node scripts/smoke-corridor.mjs` (страница+чанки+SDK+CSP+API; флаги `--reserve`,
`--alert`, `--base=`) — прогонять после каждого деплоя Web/Guide.

## API коридора

### `POST /api/wb-code` — резерв кода
Атомарно в транзакции: находит код (case-insensitive), проверяет статус и возвращает
`denomination`. Логика:
- `isUsed && userId` → 409 «уже активирован».
- `CLAIMED && !isUsed` → 409 `BOT_CLAIMED` («продолжай в боте»).
- `RESERVED` тем же sessionId → продлевает бронь; другим sessionId → **перехватывает**
  (клиент держит физическую карту — он «выигрывает»).
- `AVAILABLE` → `RESERVED` на +60 мин.

### `GET /api/wb-code?code=` — статус
Возвращает `{ claimed, denomination, platform, orderStatus, robloxUsername }`. `claimed`
= есть `userId` или статус `CLAIMED`. Данные заказа — чтобы инструкция показала один
правильный канал и статус «заказ уже оформлен».

### `POST /api/wb-code/select-gamepass` — материализация заказа (one-tap с сайта)
Пользователь выбрал геймпасс в поиске по нику на шаге 9. Роут промотирует provisional-заказ
`AWAITING_GAMEPASS → PENDING` прямо здесь (не дожидаясь возврата в бота) и шлёт админ-карточку
«🌐 ONE-TAP С САЙТА». Идемпотентно (guard по статусу в транзакции → карточка ровно раз).
Серверная ре-валидация: цена ±2 R$ и `isActive`; если Roblox недоступен — принимает
(`validationSkipped`), как бот.

Карточка использует исходный `WbOrder.createdAt`, а не время one-tap-промоушена, и показывает
`⏳ Возраст заказа` с приоритетом: 🟢 до суток, 🟡 1–2 дня, 🟠 3–6 дней, 🔴 от 7 дней.
Поэтому заказ, который неделю ждал геймпасс и только сейчас стал готов к выкупу, помечается
`🔴 … · недельный`. Web и боты используют зеркальные `order-age` formatter + contract test.

### `GET /api/roblox/gamepasses?query=&code=` — поиск по нику/ID
`extractGamepassId()` парсит URL/чистый ID → прямой lookup; иначе `getUserGamepasses(nick)`.
Если пусто — доп. `getRobloxUser` чтобы отличить «нет такого юзера» от «есть, но нет
публичных геймпассов на продаже» (зеркалит ветвление бота).

Опциональный `code` (гайд передаёт его при поиске с шага 9): если ник подтверждён Roblox'ом,
роут сразу отмечает его на заказе — `noteProbableNickByCode` (`src/lib/capture-nick.ts`)
дописывает `[НИК? дата] ник (site-search)` в `adminNote`. Ранний захват ника: менеджер видит
вероятный ник ещё до того, как клиент дошлёт геймпасс (кейс VFNCQMT). В основное поле
`robloxUsername` вероятный ник **не** пишется — только подтверждённые пути (валидация
геймпасса, one-tap выбор).

### `GET /api/wb-link` — коридор сайт → VK
Читает `wb_code` из JWT-сессии (записан при VK-логине в `auth.ts`), линкует `userId`
к `WbCode` (если ещё не CLAIMED), редиректит в `vk.me/club237309399?ref=КОД` (или `GD+КОД`).

## Целевой WB flow после решения 18.07.2026

Владелец хочет перенести выбор ника/геймпасса и статус на сайт, не потеряв накопление
аудитории в TG/VK. Принято проектное разделение: сайт — control surface, бот/сообщество —
обязательный подтверждённый identity/notification channel. Публичная подписка поощряется и
проверяется, но не блокирует выдачу уже оплаченного WB-номинала.

Новый порядок строится поверх текущего коридора:

1. WB-код на сайте сначала только `RESERVED` с TTL.
2. До материализации `WbOrder` клиент обязательно выбирает TG/VK и нажимает Start/Начать.
3. Сайт передаёт не raw code как auth credential, а одноразовый opaque handoff challenge;
   бот серверно связывает `UserIdentity` и подтверждает возврат.
4. Выбор ника/геймпасса выполняется на сайте, заказ создаётся idempotent по code+user,
   а статус одновременно отображается в ЛК и боте.
5. TG `getChatMember` / VK membership check используются для аналитики и бонуса за подписку;
   канал диалога уже даёт достижимость клиента и возможность повторной продажи.

Старый поток не удаляется одним переключением: rollout идёт на тестовых кодах, затем
`5% → 25% → 100%` новых кодов с funnel-событиями и recovery незавершённой reservation.
Детальная модель, stop conditions и DoD:
[site-launch-implementation-plan.md](site-launch-implementation-plan.md#4-wb-выдача-на-сайте-без-потери-аудитории).

## TG-уведомления при VK-логине на сайте (`src/auth.ts`, провайдер `vk-id`)

Каждый успешный VK ID-логин на сайте шлёт карточку во все `TG_CHAT_ID`. Какая карточка —
зависит от контекста:

| Карточка | Когда |
|----------|-------|
| `📦 ЗАКАЗ #…` (полная, с кнопкой дашборда) | только «живая» активация: передан `wb_code`, код существует и заказ ещё `AWAITING_GAMEPASS` |
| `🆕 Новый пользователь` | первый VK-логин (юзер только что создан) без активной активации |
| `🔑 Вход` | повторный VK-логин без активной активации |

`🔑 Вход` — **штатное информационное уведомление**, не ошибка и не атака. Типичный источник:
клиент с заказом в `PENDING`/`COMPLETED` возвращается на сайт проверить статус (в т.ч. заново
открывает `/guide` со старым cookie `wb_code` — раз заказ уже не `AWAITING_GAMEPASS`, вместо
карточки заказа уходит именно короткая карточка входа). По VK ID из карточки юзер ищется в БД:
`SELECT … FROM "User" WHERE "vkId" = '<id>'` → его заказы в `WbOrder.userId`.

**Имя «VK User»** — исторически клиентский fallback из `VKAuthButton.tsx` (декод JWT
`id_token` на клиенте; при неудаче — `VK User`, и `authorize()` затирал реальное имя в БД).
**Исправлено 2026-07-03** (риск #5 в `docs/security.md`): личность теперь резолвится на
сервере через VK `user_info`/`public_info` (`src/lib/vk-id.ts`), имя берётся из ответа VK, а
`User.name`/`image` обновляются только непустыми значениями — пустой ответ VK больше не
затирает имя. Ранее «застрявшие» как `VK User` (~3 из 120) перезапишутся при следующем входе.

**Личный кабинет:** `/dashboard` читает legacy `Order` и `WbOrder` всех источников. Вход
доступен через server-verified VK и TG; свежая web-сессия может привязать TG, а если subject
уже владеет legacy-профилем — безопасно объединить его заказы и бонусы с audit trail.

## Изменения 26.07.2026 (ultra-review)

### VK-логин с уже занятым кодом больше не «успешен» молча (U8)

`src/auth.ts`: обновление `WbCode` шло с условием `status: { not: "CLAIMED" }`, и если код
уже был занят, Prisma бросала P2025 — исключение ловилось, логировалось, **и выполнение
продолжалось**. Дальше `provisionalOrder` подхватывал существующий (чужой) заказ, а
`wb_code` всё равно клался в сессию: клиент уходил в коридор с ощущением успешной
активации, работая с чужим заказом.

Теперь различаются «код наш» и «код занят другим аккаунтом». Во втором случае:

- `wb_code` в сессию **не кладётся**, провизорный заказ не создаётся и не подхватывается;
- сессия помечается флагом `wb_code_conflict`, кнопка VK-входа показывает клиенту
  «Этот код уже активирован в другом аккаунте» со ссылкой в поддержку;
- админам уходит алерт в TG — это одновременно индикатор ПВЗ-фрода (риск №15).

### IP согласия с офертой (U9)

`api/orders/create` объявлял собственный `resolveClientIp` с приоритетом левого (то есть
подделываемого) hop'а `x-forwarded-for`, тогда как весь остальной код использовал
`clientIp()`. Значение уходило в `termsIpAddress` как юридическое доказательство согласия.
Локальная функция удалена, используется общий `clientIp()` после фикса U2; дополнительно
сохраняется `termsUserAgent`, а в `ConsentEvidence` добавлены `userAgent` и `deploymentId`.

### Смоук коридора перестал давать ложный зелёный (U15)

`scripts/smoke-corridor.mjs` проверял наличие `public/vendor/vkid-sdk-2.6.5.js` и бодро
рапортовал ✅, хотя приложение использует npm-пакет `@vkid/sdk` **2.6.6**, а этот файл
(170 КБ) не подключён нигде. Файл удалён; смоук теперь проверяет реально используемый
`/vendor/telegram-web-app.js`, падает при появлении неиспользуемых файлов в `public/vendor`
и отдельно требует следов бандла VK ID в сборке гейта. Добавлен режим `--drift-only` для
крона (см. `docs/deploy.md`).
