## 1. Вердикт

**Открывать сайт в текущем состоянии нельзя.** Не из-за платёжного ядра — оно как раз
хорошее, — а из-за шести дефектов, каждый из которых виден клиенту или оператору с первой
минуты после открытия:

| # | Что сломается сразу после открытия |
|---|---|
| L1 | Каждый заказ с сайта уже сейчас порождает мёртвое outbox-сообщение и ложную тревогу `🚨 OUTBOX DEAD-LETTER` админам. Подтверждено на проде: 4 заказа из 4. |
| L2 | В подвале **каждой** страницы намертво зашито «Приём платежей временно отключён». После запуска текст не изменится сам. |
| L3 | Гость (не залогиненный) всегда получает `enabled:false` — даже в режиме `mode=on`. Витрина будет говорить «оплата отключена» открытому миру. |
| L4 | На планшетах 768–1023 px (все iPad в портрете) **нет ни одной точки входа в ЛК** — ни ссылки, ни бургера. |
| L5 | В тёмной теме кнопка «Кабинет» в мобильном меню — белый текст на белом фоне (то, о чём говорил владелец). Контраст ≈ 1.05:1. |
| L6 | Guide-контейнер в проде отстал от Web (`9dafe35f8551386f` ≠ `9cd2d74bde5cf9c5`). Главная точка входа с WB крутит старую сборку. |

Плюс системный дефект первого экрана: **вся тёмная тема включается только после гидратации**
(L7) — на телефоне первый кадр всегда «светлая страница + тёмная шапка», потом рывок.

Платёжное ядро, наоборот, подтверждено как надёжное — см. §2.

## 2. Что проверено и признано надёжным

Перепроверено кодом и живыми запросами, замечаний нет:

- **Подпись и жизненный цикл платежа.** `buildTinkoffToken` соответствует схеме банка;
  webhook проверяет подпись, `TerminalKey`, `PaymentId`, сумму и допустимость перехода;
  идемпотентность — по `OrderEvent.idempotencyKey` + `rawEventHash` для возвратов; всё в
  `Serializable`-транзакции; `OK` отдаётся только после durable-коммита.
- **Возвраты.** Резервирование суммы через `PENDING/SUBMITTED/SUBMIT_UNKNOWN` закрывает гонку
  двух менеджеров; `refundNeedsReceipt` (U7) корректно отделяет «первый и сразу полный» от
  остальных; при неизвестном исходе — `SUBMIT_UNKNOWN` без автоповтора.
- **Создание заказа.** Котировка потребляется атомарно, бонус и скидка списываются с
  проверкой «не изменились», запись в `BonusLedger` — единственная точка; внешних вызовов
  внутри транзакции нет.
- **Вход в TWA (U1).** `initData` HMAC или подписанный ботом `linkToken`; `av`-отпечаток
  состава `ADMIN_IDS`; TTL 2 ч; `timingSafeEqual`. Path 2 по Telegram ID удалён.
- **Rate-limit (U2).** `TRUSTED_PROXY_MODE=direct` в проде подтверждён; `clientIp` берёт
  только hop от Traefik, `cf-connecting-ip` игнорируется.
- **Гейты админки.** Все 34 роута `/api/twa/*` (кроме самого `auth`) требуют `extractTwaUser`;
  `/api/admin/*` — сессия `role=ADMIN` либо bearer `ADMIN_SECRET` с `timingSafeEqual`.
- **Открытые редиректы.** `safeReturnPath` отбивает `//`, `\`, control-символы, чужой origin
  и `/admin`.
- **Anti-enumeration.** Регистрация, resend, reset пароля дают одинаковый ответ для
  существующего и несуществующего адреса; троттлинг до обращения к БД и bcrypt.
- **Секреты.** В репозитории нет; `.gitignore` закрывает `.env*`, `HANDOFF.md`, `PLAN-*.md`,
  `/data/`, `/scratch/`. Прод-значения живут только в Coolify.
- **Прод-конфигурация платежей** (сверено через Coolify API, production scope):

  `PAYMENT_METHOD=full_prepayment`, `PAYMENT_OBJECT=service`.
  Дубли ключей в списке — это пары production/preview, конфликта в рантайме нет.

## 3. Безопасность

### S1 — Два хоста, один сайт: `robloxbank.ru` и `www.robloxbank.ru` — P1

**Суть.** Оба хоста отдают приложение напрямую (200 на обоих, без 301). При этом:

| Где | Значение |
|---|---|
| `NEXTAUTH_URL`, `NEXT_PUBLIC_APP_URL` (prod) | `https://www.robloxbank.ru` |
| `metadataBase`, `robots.txt`, `sitemap.xml`, все внутренние ссылки | `https://robloxbank.ru` |

`NEXT_PUBLIC_APP_URL` подставляется в `SuccessURL` / `FailURL` / `NotificationURL` при
`Init`. То есть клиент оформляет заказ на apex, а банк возвращает его на **www**.

**Риск.** Cookie сессии NextAuth — host-only (домен не задан). После оплаты клиент
приземляется на www **без сессии**: в шапке «Войти», ЛК недоступен, «мои заказы» пусты.
Заказ на `/payment/status` он увидит только потому, что там работает `token` из URL.
Дополнительно: дубль контента для поисковиков, второй cookie-jar для `site_unlock`,
рассинхрон canonical (тегов `<link rel="canonical">` вообще нет).

**Что делать.** Выбрать один канонический хост (рекомендую apex — он уже в sitemap, robots и
`metadataBase`), поставить 301 на Traefik для второго, привести `NEXTAUTH_URL` и
`NEXT_PUBLIC_APP_URL` к нему же, добавить `alternates.canonical` в `metadata`.

**Приёмка.** `curl -I https://www.robloxbank.ru/` → 301 на apex; вход на apex → оплата →
возврат из банка: в шапке «Кабинет», а не «Войти».

### S2 — CSP на платёжном сайте всё ещё с `unsafe-inline` и `unsafe-eval` — P1

**Суть.** Боевая политика: `script-src 'self' 'unsafe-inline' 'unsafe-eval' https://telegram.org`.
Report-Only со строгой политикой уже едет параллельно (U10, этап 1), приёмник
`/api/observability/csp-report` отвечает 204.

**Риск.** На сайте, который принимает деньги, это главный отсутствующий барьер против XSS.
Известный риск №26 в [security.md](security.md).

**Что делать.** Снять отчёт `[csp-report]` из логов Web за период с реальным трафиком
(iPhone Safari, Android Chrome, Telegram WebView, VK WebView), устранить оставшиеся
inline-скрипты (см. также L7 — там как раз понадобится один inline-скрипт, его нужно
закрыть хешем, а не `unsafe-inline`), затем перенести строгую политику в `Content-Security-Policy`.

### S3 — Мёртвый `initTinkoffPayment` — P2

`src/lib/tinkoff.ts:49` — легаси-функция инициализации платежа: **без** `NotificationURL`,
**без** `Receipt`, с рублями вместо копеек. Не вызывается ниоткуда. Пока она экспортируется,
любой будущий вызов создаст нефискализированный платёж, о котором мы не узнаем.
**Удалить** вместе с тестами на неё.

### S4 — Диагностический JSON-лог Init остаётся в коде — P2

**Что делать.** После закрытия кейса Т‑Банка удалить код целиком. Если оставляем «на всякий» —
маскировать `token=` в URL перед записью и выключить флаг в preview.

**Что делать:** добавить `rateLimit` по IP, перевыпустить `ADMIN_SECRET` длиной ≥ 32 байта.

### S7 — HSTS без `includeSubDomains` — P2

`Strict-Transport-Security: max-age=31536000`. Добавить `includeSubDomains` (и `preload`,
если поддомены точно все под HTTPS) — иначе `www` и будущие поддомены не покрыты.

---

### S8 — Лимитер в памяти процесса — P2 (документировать)

`src/lib/rate-limit.ts` — `Map` в одном Node-процессе. Это осознанное решение для одного
контейнера, но при любом горизонтальном масштабировании лимиты молча умножатся на число
реплик. Зафиксировать в `deploy.md` как явное ограничение: «Web масштабировать нельзя без
переезда лимитера в Redis».

---

### S9 — Email чека нигде не подтверждается — P1 (комплаенс + UX)

Провайдер `admin-login` не проверяет `emailVerifiedAt` — войти можно с неподтверждённым
адресом. `receiptEmail` в чекауте — свободное поле, не подставляется из профиля и не
сверяется с ним. То есть фискальный чек уходит на адрес, который покупатель никак не
подтверждал (и который может быть чужим).

**Что делать (минимум для запуска).** Подставлять email аккаунта в поле чека по умолчанию,
показывать «чек придёт на …», и если адрес отличается от подтверждённого — предупреждать.
Полноценное требование верификации — отдельным шагом после стабилизации доставки Brevo.

## 4. Работоспособность

### F1 — `web.order.created` не имеет обработчика: каждый заказ = мёртвое сообщение + ложная тревога — **P0**

**Суть.** `createCanonicalWebOrder` кладёт в outbox сообщение с топиком `web.order.created`
(`src/lib/canonical-web-order.ts:255`). Воркер `bots/shared/payment-outbox.ts:63` знает
только `payment.confirmed` и `payment.refund.recorded`, на всё остальное — `throw`.

**Доказательство (production БД, на момент ревью):**

```

--------------------------+-----------+---+-------------
payment.confirmed         | DELIVERED | 1 | 1
payment.refund.recorded   | DELIVERED | 1 | 1
web.order.created         | DEAD      | 4 | 8
lastError: "unsupported outbox topic: web.order.created"
```

**Риск.** Каждый заказ с сайта: 8 попыток с бэкоффом ~2 часа, затем `DEAD` и сообщение
`🚨 OUTBOX DEAD-LETTER` всем админам. При 50 заказах в день — 50 ложных тревог в день,
которые похоронят настоящие. Ровно та проблема, ради которой заводилась карточка `Og1cOXZ4`.

**Что делать.** Либо реализовать обработчик (уведомление админам «новый заказ, ждём оплату» —
это полезно), либо не создавать сообщение при `WEB_ORDER_CREATED` и оставить только
`OrderEvent`. Рекомендую первое: у оператора появится сигнал о брошенных корзинах.
Плюс — «неизвестный топик» должен становиться `DEAD` сразу, без 8 попыток.

**Приёмка.** Новый тестовый заказ → в `OutboxMessage` нет строк со статусом `DEAD`;
существующие 4 строки закрыть вручную.

## 5. Дизайн и мобильный UX

Основные устройства — телефон и планшет ([feedback_twa_target_devices]), поэтому findings
отсортированы по тому, что видит человек с телефона.

### D1 — Кнопка «Кабинет» в мобильном меню: белое на белом — **P0**

`src/components/navbar.tsx:62`:

```tsx
className="... border border-[#dcd5ef] bg-white text-sm font-bold"
```

Цвет текста не задан → наследуется от `<nav className="... text-[var(--rb-text)]">`. В тёмной
теме `--rb-text = #f4f0ff`. Итог: белый текст + белый фон + почти белая рамка `#dcd5ef`.
Контраст **≈ 1.05:1** при требуемых 4.5:1. Это и есть баг, о котором говорил владелец.

Рядом, строка 63: `bg-[#7556e8]` тоже захардкожен мимо токенов.

**Что делать.** Перевести обе кнопки на токены: `bg-[var(--rb-surface)]`,
`text-[var(--rb-text)]`, `border-[var(--rb-border)]` / `bg-[var(--rb-strong)]`.
И завести правило: в `navbar`/`footer` (единственных Tailwind-компонентах публичного шелла)
запрещены литеральные цвета.

### D2 — На планшетах нет входа в личный кабинет вообще — **P0**

Разбор классов в `navbar.tsx`:

| Элемент | Класс | Видим при |
|---|---|---|
| Ссылка «Войти/Кабинет» | `hidden … lg:flex` | ≥ 1024 px |
| Кнопка-бургер | `md:hidden` | < 768 px |

В диапазоне **768–1023 px** не видно ни того, ни другого. Это iPad Mini (768), iPad Air (820),
iPad Pro 11″ (834) в портрете и любой Android-планшет. Клиент физически не может попасть

**Что делать.** Ссылку в шапке показывать с `md:flex`, а не `lg:flex` (места хватает: при

### D3 — Первый кадр всегда в чужой теме — **P0 (системный)**

`data-theme` ставится только в `useEffect` `ThemeProvider` (`theme-provider.tsx:42`), в
серверном HTML его нет. При этом **вся** тёмная тема модульных стилей завязана на
`html[data-theme="dark"]`: 45 правил в `storefront`, 34 в `checkout`, 24 в `site-guide`,
5 в `dashboard` — и **ноль** fallback-ов на `prefers-color-scheme`. А вот общие токены
`--rb-*` в `globals.css` переключаются сразу, через
`@media (prefers-color-scheme: dark) html:not([data-theme])`.

Результат на телефоне с тёмной системной темой: первый кадр — **светлая страница с тёмной
шапкой и тёмным подвалом**, затем, после гидратации, всё скачком перекрашивается. На
мобильном 3G/4G это заметная вспышка на каждой навигации.

**Что делать.** Блокирующий inline-скрипт в `<head>`, который до первой отрисовки читает
`localStorage`/`matchMedia` и ставит `documentElement.dataset.theme`. Скрипт закрыть
CSP-хешем (не `unsafe-inline`) — это стыкуется с S2. Как страховка на случай отключённого
JS — продублировать ключевые дарк-правила через
`@media (prefers-color-scheme: dark) { html:not([data-theme]) … }`.

## 6. Ощущается ли это экосистемой

Отдельный вопрос владельца. Коротко: **связки есть, но обратная связь односторонняя.**

Работает хорошо:
- один `User` на все каналы, `UserIdentity` склеивает TG/VK/email, бонусный баланс общий;
- заказы всех источников (SITE / WB / DIRECT / AVITO / MANUAL) в одной ленте ЛК;
- оплаченный заказ с сайта попадает в ту же очередь «К выкупу», что и WB (`buyout-queue.ts`);
- `/payment/status` предлагает связать Telegram и подписаться — post-purchase loop замкнут;
- гейт → бот → выкуп → отзыв → бонус → повторный прямой заказ — цепочка целая.

Не работает:
- **F8**: клиент с одним email не получает ни одного сообщения — для него «экосистема»
  сводится к тому, что он сам открывает ЛК и обновляет страницу;
- **F1**: оператор получает ложную тревогу вместо сигнала «пришёл новый заказ»;
- **S1**: после возврата из банка клиент оказывается на другом хосте, и ЛК выглядит так,
  будто он не входил, — это ровно тот момент, где ощущение «единой системы» ломается сильнее
  всего;
- у сайта нет «продолжить в боте» из ЛК с контекстом заказа — только generic-ссылка в
  поддержку.

## 8. План реализации

Этот раздел написан как **исполняемая спецификация**: его можно отдать сессии целиком, и
каждая задача содержит контекст, точные файлы, требуемое поведение, тесты и критерий приёмки.
Задачи внутри волны независимы, если явно не указано иное. Волны упорядочены так, чтобы после
каждой можно было остановиться и не остаться в сломанном состоянии.

### Общие правила для исполнителя

1. **Одна задача = один коммит.** Формат: `fix(<область>): <суть> (<ID>)`, например
   `fix(outbox): обработать web.order.created (F1)`.
2. **Перед каждым коммитом** — `npm run gates` (lint · tsc · bots:tsc · jest · test:bots ·
   build). Красный гейт = коммита нет.
3. **Каждая задача с логикой обязана принести тест.** Если поведение нельзя покрыть unit-тестом,
   в описании задачи указан ручной прогон — выполнить и записать результат в `HANDOFF.md`.
4. **Документация — в том же коммите** (правило `AGENTS.md`): затронул поведение — правь
   соответствующий файл `docs/`; новый риск — `docs/security.md`; итог сессии — `HANDOFF.md`.
5. **Ничего не деплоить в прод без явного «го» владельца.** Push в `main` запускает автодеплой
   Web/TG/VK — это уже прод. Guide автодеплоем **не** покрывается.
6. **Секреты не выводить** — ни в чат, ни в логи, ни в документацию. Только в Coolify.
7. **Тексты для клиента — по-русски, на «ты»** (единый тон витрины), без номеров заказов
   ([feedback_no_order_numbers]) — идентификатор для клиента это код ВБ или `publicOrderId`.

#### F7 · Heartbeat фоновых воркеров (закрывает карточку `jYOEHLjT`)

**✅ Реализовано и принято production drill 28.07.2026.** `ServiceHeartbeat` обновляется TG

**Сделать:**

1. Таблица/строка heartbeat: воркер после каждого тика пишет `{ worker, lastTickAt }`

**Приёмка:** остановить TG-бот на 6 минут в контролируемом окне → тревога пришла; поднять →
