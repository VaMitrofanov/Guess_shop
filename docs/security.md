# Безопасность

Репозиторий **публичный** (`Guess_shop`). Правило: секреты, платёжные ассеты и приватные
картинки — только в env / БД, никогда в коммит.

## Что проверено

- **Секреты в коде** — не найдено. Токены (`TG_TOKEN`, `VK_TOKEN`, `.ROBLOSECURITY`,
  `DATABASE_URL`) читаются только из env.
- **TWA API** — все `/api/twa/*` роуты закрыты `extractTwaUser` (JWT `twa-admin`).
  Исключения: `auth` (точка входа) и `debug` (за `ADMIN_SECRET` + `timingSafeEqual`).
- **VK-логин** — личность резолвится на сервере через VK `user_info`/`public_info`
  (`src/lib/vk-id.ts`), клиентские `vk_id`/`name` не принимаются (риск #5 закрыт).
- **initData** — HMAC-проверка подписи Telegram + отклонение старше 24 ч.
- **wb-code** — атомарный резерв в транзакции, валидация формата кода.

## <a name="twa-auth"></a>Известные риски

### 1. TWA auth fallback (Path 2) — приоритет высокий, ⏳ инструментирован (2026-07-03)
`src/app/api/twa/auth/route.ts`: если запрос без `initData`, роут доверяет `userId` из тела
и проверяет только `isAdmin(userId)`. Telegram user ID **не секретны** (видны в форвардах/чатах).
Любой, кто знает TG ID менеджера, может получить валидный 12-часовой admin-токен → полный
доступ к заказам, cookie, балансу, выкупу.

**Статус:** добавлен серверный лог `[twa-auth] hasInitData=… platform=… path2=…` (клиент
шлёт `platform` из `Telegram.WebApp`). Нужно открыть TWA на целевых устройствах (iPhone
14/15 Pro Max + MacBook 16") и проверить в логах Web-контейнера, приходит ли `initData`.
Если во всех логах `hasInitData=true` → **удалить Path 2** (строки 24–29 роута) без потери
доступа. Если какое-то устройство реально не отдаёт → заменить публичный `userId` на
подписанный `TWA_FALLBACK_SECRET`.

### 2. Rate-limiting на публичных API — ⚠️ ЧАСТИЧНО (2026-07-03)
`/api/wb-code` за in-memory token-bucket (`src/lib/rate-limit.ts`): POST burst 10 / 1-в-5с,
GET burst 20 / 1-в-2с, 429 + `Retry-After`. Код верный — **прямой тест контейнера**
(в обход прокси, ключ «unknown») даёт ровно 20 проходов + 10×429.

**Ограничение прода:** цепочка **Cloudflare-tunnel → Traefik НЕ пробрасывает реальный IP
клиента** в контейнер — приложение видит `X-Forwarded-For`/`X-Real-Ip` = IP хоста
(`89.110.94.117`) для всех запросов, `cf-connecting-ip` не доходит. Значит per-IP лимит
вырождается в грубый глобальный троттл (все клиенты в одной корзине) и не различает атакующего
от легитимных. Диагностический лог `[wb-code] POST reserve … ip=… cf=… xff=…` добавлен для
подтверждения в проде.

**Что делать (на выбор):** (а) настроить проброс client-IP в Traefik (trusted forwarded
headers) + cloudflared, тогда per-IP лимит заработает как задумано; (б) перенести
rate-limiting на **Cloudflare WAF** (rate-limiting rules) — естественное место, раз трафик и
так через CF; (в) оставить как есть (грубый троттл + abuse-лог). Лимитер безвреден и остаётся.
Также: при масштабировании на >1 реплику Web нужен общий стор (Redis) вместо in-memory Map.

**Обновление 2026-07-04:** DNS переключён на **прямой A** `robloxbank.ru → 89.110.94.117`
(grey-cloud, минуя Cloudflare-tunnel — см. риск #7). Теперь client-IP в принципе доходит до
Traefik напрямую; вариант (а) стал реалистичным — проверить лог `[wb-code] ip=` после
переключения и, если IP реальный, включить per-IP лимит. Одновременно ушла CF-защита перед
источником → см. риск #7 (публичный IP).

### 7. Прямой публичный IP источника после ухода с Cloudflare-tunnel — 🆕 (2026-07-04)
Раньше `robloxbank.ru` резолвился на Cloudflare (proxied) и трафик шёл через
`cloudflared`-туннель — источник был скрыт за CF (DDoS-защита, WAF). На 04.07 DNS —
**прямой A на `89.110.94.117`** (RF-сервер), сертификат Let's Encrypt. Причина смены —
деградация Cloudflare у российских розничных провайдеров (ТСПУ): сайт «работал только с VPN»
(жалобы клиентов, «вечное восстановление сессии»). Побочный эффект — **IP источника публичен**:
прямой вектор для DDoS/сканов, CF-WAF больше не прикрывает. ⚠️ **Кто переключил DNS —
подтвердить у владельца** (в HANDOFF записей нет; если не он — инцидент доступа к CF-аккаунту).
Митигации (на решение владельца): Traefik rate-limit middleware / CrowdSec (уже есть контейнер
`crowdsec` на хосте) / вернуть CF proxy только для не-РФ гео. `panel.robloxbank.ru` остаётся
proxied (CF) — это ок.

### 8. Google Sheets credentials для B2B sync — 🆕 (2026-07-09)
B2B-режим `Антон` готовится к Google Sheets sync/write-back. Для подключения понадобится
service-account JSON с доступом к таблице. Это секрет: хранить только в env/Coolify или
локальном `HANDOFF.md`, не в `docs/` и не в коммитах. Публичная документация может описывать
только имена env, схему колонок и правила sync. Саму таблицу лучше шарить на конкретный
service-account с минимальным доступом Editor только к нужному документу, а не на весь диск.
Для Антона публично фиксируется только `spreadsheetId`, маппинг колонок и статусы; локальный
путь к JSON и содержимое credentials остаются вне git. Прод-подключение использует env
`ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` и `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`; значение JSON
нельзя логировать и нельзя добавлять в `.env.example`/docs. Перед прод-подключением нужно
проверить, что Google Sheet расшарен на service-account email из JSON с правом Editor.

Пока Google sync не подключён, TWA принимает ручной `.xlsx` upload для Антона. Ограничения:
до `5 MB`, до `300` строк, бинарный файл не сохраняется, в БД остаются только metadata строки.
В такие файлы нельзя добавлять cookie, seed-фразы, токены, service-account JSON и другие
секреты. Зависимость `xlsx` нужно держать обновлённой и проверять через `npm audit`, потому
что парсинг офисных файлов расширяет поверхность атаки.

### 3. `debug`-роут — ✅ ЗАКРЫТО (2026-07-03)
`/api/twa/debug` (за `ADMIN_SECRET` + `timingSafeEqual`) больше не отдаёт первые 12 символов
`WB_API_TOKEN`: в проде поле `tokenFirst12` = `"(hidden in prod)"`, длина токена остаётся для
диагностики. Полный превью доступен только при `NODE_ENV !== "production"`.

### 4. Захардкоженные IP серверов — ✅ ЗАКРЫТО (2026-07-03)
IP убраны из кода и комментариев (`Dockerfile`, `bots/tg/admin/hub-system.ts`,
`src/app/api/twa/system/route.ts`, `scripts/setup-swap.sh`). Health-URL ботов теперь
берутся **только** из env (`VK_BOT_HEALTH_URL`, `TG_BOT_HEALTH_URL`); без env сервис

переменные заведены в Coolify (значения — в `HANDOFF.md`), иначе виджет здоровья
покажет ботов красными.

### 5. `vk-id` CredentialsProvider доверял клиенту — ✅ ЗАКРЫТО (2026-07-03)
**Было:** провайдер `vk-id` принимал `vk_id`/`name`/`image` из тела запроса **без серверной
проверки**; любой с CSRF-токеном логинился под произвольным VK ID.

**Фикс:** клиент (`VKAuthButton.tsx`) больше не шлёт личность — только сырые токены из
`VKID.Auth.exchangeCode()` (`access_token` + `id_token`). Сервер (`src/lib/vk-id.ts`,
`verifyVkIdUser`) резолвит личность через VK: `POST https://id.vk.com/oauth2/user_info`
(по `access_token`), фолбэк `.../oauth2/public_info` (по `id_token`), оба с `client_id`.
`vk_id`/имя/аватар берутся **только** из ответа VK. Проверено симуляцией атаки: подделанные
токены и старый формат (`vk_id` без токенов) → `CredentialsSignin`, сессия не создаётся.

**Побочный эффект:** ушёл клиентский fallback «VK User» — имя всегда из проверенного ответа
VK; вдобавок `authorize()` теперь обновляет `User.name`/`image` только непустыми значениями,
так что пустой ответ VK больше не затирает реальное имя в БД
(см. `docs/corridor-and-site.md`, «TG-уведомления при VK-логине»).

## select-gamepass — валидация
`api/wb-code/select-gamepass` ре-валидирует цену и `isActive`, но не проверяет принадлежность
геймпасса нику (`creatorId`). Hand-crafted POST может привязать чужой геймпасс с совпадающей
ценой. Митигируется ручным выкупом менеджером (он видит карточку). Низкий приоритет.
