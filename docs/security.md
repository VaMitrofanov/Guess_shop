# Безопасность

Репозиторий **публичный** (`Guess_shop`). Правило: секреты, платёжные ассеты и приватные
картинки — только в env / БД, никогда в коммит.

## Что проверено

- **Секреты в коде** — не найдено. Токены (`TG_TOKEN`, `VK_TOKEN`, `.ROBLOSECURITY`,
  `DATABASE_URL`) читаются только из env.
- **TWA API** — все `/api/twa/*` роуты закрыты `extractTwaUser` (JWT `twa-admin`).
  Исключения: `auth` (точка входа) и `debug` (за `ADMIN_SECRET` + `timingSafeEqual`).
  ⚠️ Сама проверка слабее, чем кажется: `extractTwaUser` сверяет только claim `role` и не
  перепроверяет членство в `ADMIN_IDS`, а выдача токена имеет обходной Path 2 — риск №1.
- **VK-логин** — личность резолвится на сервере через VK `user_info`/`public_info`
  (`src/lib/vk-id.ts`), клиентские `vk_id`/`name` не принимаются (риск #5 закрыт).
- **initData** — HMAC-проверка подписи Telegram + отклонение старше 24 ч.
- **wb-code** — атомарный резерв в транзакции, валидация формата кода.
- **Ручной replay outbox** — только с desktop-сессией роли `ADMIN`; endpoint принимает UUID
  idempotency key и допускает исключительно `DEAD → PENDING` в serializable transaction.
  Он не умеет отправлять банк-операции, не раскрывает payload/текст ошибки и оставляет
  неизменяемый `OUTBOX_REPLAY_REQUESTED` с hash прежней ошибки. Подробнее: `payments-and-kkt.md`.

## <a name="twa-auth"></a>Известные риски

### <a name="wb-dbs-delivery-code"></a>36. WB DBS: код получения, buyer-chat и широкий RW-токен — P0, 🟡 CONTROLLED ROLLOUT (2026-08-11)

Новый courier/DBS flow просит покупателя прислать в WB-чат код подтверждения получения, а
затем использует его в Marketplace API. Этот код — одноразовый credential с денежным и
операционным эффектом: успешный `receive` переводит заказ в полученный/проданный независимо
от того, завершил ли RobloxBank внутренний Game Pass fulfillment.

**Риск:** утечка кода в лог, URL, transcript или telemetry; подстановка кода от другого
заказа; повторный/преждевременный `receive`; WB `sold`, но generated activation code не
создан или не доставлен; duplicate chat message после timeout; раскрытие `replySign`, ФИО,
телефона или адреса; компрометация текущего широкого production RW-токена затрагивает сразу
несколько категорий WB API.

**Обязательные меры до canary:** отдельные scoped Marketplace/Chat tokens; сохранение нового
DBS из `/orders/new` до любых status mutations; корреляция только по `rid`; atomic один
marketplace order → один `WbCode`; номинал только из server-side product snapshot; код
получения в short-lived AES-GCM/KMS secret с HMAC, маской, TTL ≤24 ч и очисткой после
использования; запрет секретов/PII в logs, URL, Trello, analytics и client DTO; `receive`
только после `gateState=SENT`, повторной проверки WB status, явного admin confirm и
append-only audit; проверка каждого `results[]` bulk-ответа; mutation kill-switch на
`401/403`; постоянная очередь `WB_RECEIVED && internal != COMPLETED`.

**Реализовано:** отдельные marketplace/chat/cursor/secret/audit модели; AES-256-GCM с
purpose-bound AAD и HMAC; redaction до persistence; TTL 24 ч и purge; `rid`-only correlation;
DB lease/cursor/heartbeat; tolerant contracts; atomic один DBS → один `WbCode`;
origin/auth/rate-limit; live status recheck перед receive; partial bulk result check;
unknown-outcome stop state; secret purge после успеха; синтетический E2E без WB writes.
Read-only TG sync включается отдельно, live chat/status flags остаются OFF до canary.
Первый shadow-run выявил и закрыл безопасный contract edge: успешный WB `status/info`
возвращает `errors: null`; provider-массивы нормализуются до `[]`, regression покрыт.

POST-действия desktop-админки дополнительно требуют JSON, `Sec-Fetch-Site: same-origin`
(когда заголовок доступен) и точное совпадение `Origin` со строгим allowlist публичных
доменов/настроенного app origin. Проверка учитывает reverse proxy: внутренний container
origin не является единственным допустимым адресом. TWA использует отдельную
Bearer-аутентификацию и тот же rate limit/role guard.

**Закрыто 19.08.2026 — plaintext кода доставки в списочном API.** `toDto` расшифровывал
секрет для каждой строки, а обзорный endpoint прогонял через него все 150 заказов: клиент
получал открытые коды доставки всех живых заказов каждые 20 секунд, на экран, который их не
отображает. Это нарушало собственный инвариант раздела («запрет секретов в client DTO») с
момента реализации. Расшифровка стала opt-in и осталась только в `loadWbDeliveryOrder` —
одном явно открытом заказе; в карточке код прячется за тапом «Показать». Инвариант закреплён
`src/__tests__/wb-delivery-secret-exposure.test.ts`.

**Сужено 19.08.2026 — ПД покупателя.** Для сопоставления чата WB с диалогом в боте добавлен
`buyerName`. Живой ответ `POST /api/v3/dbs/orders/client` содержит `phone`,
`replacementPhone`, `phoneCode`, `additionalPhones`, `additionalPhoneCodes`. Схема
`WbDbsClientResponseSchema` — единственная в файле **без `.passthrough()`**: телефоны
отсекаются на границе парсинга и не доходят до памяти, логов и error payload. В БД пишется
только первое имя; адрес и полное ФИО не сохраняются.

**Открытый риск — отменённый заказ с непотраченным кодом.** Покупатель может отменить заказ
на WB (деньги возвращаются), сохранив выпущенный гейт-код, и активировать его: робуксы уйдут
бесплатно. Автоматического аннулирования нет — семантика `WbCode.isUsed + userId` несёт
денежный смысл в шести точках активации, и её изменение требует отдельной задачи. Смягчение:
`wbCancelledCodeAtRisk` держит такой заказ в стадии `attention` с инструкцией отклонить
внутренний заказ вручную; остальные отмены из консоли скрыты. На 19.08 таких заказов в
проде — 0.

Открытый риск: production пока использует legacy широкий `WB_API_TOKEN` как fallback;
отдельные scoped Marketplace/Chat tokens остаются обязательным hardening до массового
rollout. Создать чат продавцом стабильный официальный API пока не позволяет: UI обязан показывать
manual fallback, а не вызывать отозванный endpoint. Полная реализация и stop conditions:
[wb-dbs-delivery-plan.md](wb-dbs-delivery-plan.md).

### 34. В проде стоял чужой `NEXT_PUBLIC_VK_APP_ID` — вход через VK был сломан для всех — ✅ ЗАКРЫТО 2026-07-28

Владелец прислал скриншот: `id.vk.ru` встречает «Ошибка загрузки». Причина — в Coolify на
**Web и Guide** стоял `NEXT_PUBLIC_VK_APP_ID = 51912345`, тогда как настоящее приложение —
`54539012` (значение локального `.env` и фолбэка в коде). Воспроизведено headless-браузером:
`51912345` → «Error loading», `54539012` → «Sign in to «RobloxBank»».

Почему держалось долго и незаметно:

- переменная **build-time**: неверное значение запекается в клиентский бандл и живёт до
  пересборки — рестарта контейнера недостаточно;
- смоук проверял только **присутствие** бандла VK ID в чанках гейта, а не то, какой в нём
  app id. Бандл был на месте, CSP в порядке, `smoke-corridor` — зелёный;
- VK-вход отмечен в документации как «ждёт живой приёмки под настоящим аккаунтом»
  (`site-acquiring-master-plan.md`), то есть автоматически его никто и не проверял.

**Закрыто:** значение исправлено на обоих сервисах, Web и Guide пересобраны (фингерпринт
совпадает), живой прогон кнопки на `/login` открывает VK ID с формой входа в «RobloxBank».
В `smoke-corridor` добавлена проверка `VK app id в сборке гейта` (32-я): сверяет id, реально
уехавший в прод, с ожидаемым (`EXPECTED_VK_APP_ID`, по умолчанию `54539012`).

Сверка идёт по **границам числа**: простой `includes` давал ложный зелёный — произвольная
последовательность цифр находится внутри чужих чисел (например `99999999` совпадает с
float-литералами `1.0000000000001` из framer-motion). Гард проверен в обе стороны: с верным
id — зелёный, с любым другим — красный с указанием, что реально в сборке.

> Общее правило: любая `NEXT_PUBLIC_*` переменная обязана быть одинаковой на **Web и
> Guide** и требует **пересборки** обоих. Расхождение не увидит ни health, ни рестарт.

### 33. Роль админа не сверялась после входа, а источников правды было два — ✅ ЗАКРЫТО 2026-07-28

Два дефекта одного корня, найдены при подготовке переезда админки в веб:

1. `token.role` записывалась в JWT **один раз при входе** и больше не сверялась с базой
   (`src/auth.ts`, callback `jwt`). Снятие роли не действовало до перелогина: у бывшего
   админа сессия оставалась рабочей.
2. «Кто админ» решалось в двух местах — `User.role === "ADMIN"` для desktop `/admin` и
   `ADMIN_IDS` для TWA с ботами. Составы никак не связаны, при трёх админах расхождение
   гарантировано. Фактически в базе был **один** `role=ADMIN` (аккаунт с паролем без
   привязок), а в `ADMIN_IDS` — четыре Telegram ID.

**Закрыто этапом A1.** Источник правды один — `ADMIN_IDS`; роль **выводится** на каждом
запросе (`deriveSessionRole`), правило живёт в единственном `adminGrantFor`
(`src/lib/admin-grant.ts`), доступ спрашивается через единственный `requireAdmin`
(`src/lib/admin-access.ts`), принимающий и веб-сессию, и Bearer TWA. Отдельной проверки прав
внутри роутов нет — иначе появилась бы «вторая, более слабая дверь к деньгам».

Следствие, которое надо помнить: **`role = "ADMIN"` в базе сам по себе больше не даёт
админку.** Нужна проверенная TG-личность из `ADMIN_IDS` либо запасной вход владельца — адрес
в `ADMIN_BREAKGLASS_EMAILS` **и** роль в БД одновременно. При ошибке запроса к БД роль
fail-closed понижается до `USER`. Тесты: `src/__tests__/admin-grant.test.ts`, 12/12.

Осталось за владельцем: подтвердить почту break-glass-аккаунта (`emailVerifiedAt` пуст) и
сменить его пароль; задать `ADMIN_BREAKGLASS_EMAILS` в Coolify **до** деплоя.

### 32. Оплата прямых заказов в ботах / manual transfer — HIGH, 🟡 ТЕХНИЧЕСКИ МИТИГИРОВАНО (2026-08-09)

Прямые заказы в TG/VK оплачиваются переводом по статическому СБП-QR
(`bots/shared/sbp.ts`): покупатель шлёт **скриншот**, админ сверяет его глазами и вручную
подтверждает. Ни `PaymentAttempt`, ни `Receipt`, ни фискальный чек при этом не создаются —
деньги приходят вне контура эквайринга и вне 54-ФЗ.

Пока это направление было полукустарным, риск был терпимым. После подключения официального
эквайринга он становится заметным: сайт продаёт ту же услугу по тем же ценам
(`retail-direct-v2`), но с чеком, а боты — без. Замер 28.07: 34 прямых заказа всего, 3
завершены, 9 висят на шаге оплаты.

Побочно: подтверждение оплаты держится на визуальной проверке скриншота — подделать его
существенно проще, чем подписанный callback банка.

**Реализовано 09.08:** hybrid checkout — готовая страница сайта и кнопка в боте используют
один `TBANK` attempt/`PaymentURL`; signed webhook подтверждает оплату. Bot→Web запрос
подписан отдельным HMAC-secret с timestamp window, actor/intent ownership сверяется по БД,
intent потребляется CAS, сумма и льготы не принимаются из callback. Status link содержит
opaque bearer token, в БД только hash. Manual path получает `MANUAL_TRANSFER` attempt;
proof никогда не подтверждает его автоматически, а `pay_ok` отказывает для TBANK.

Provider Init защищён отдельным DB single-flight claim: повторный тап или replay не вызывает
второй запрос в банк. После полученного provider success локальная ошибка сохранения не
переводит attempt в `FAILED` и не компенсирует льготы; состояние остаётся live и требует
reconciliation. Просроченный intent отдельно фиксируется `EXPIRED` после rollback основной
serializable-транзакции.

Raw реквизиты находятся только в Web runtime env и возвращаются официальному боту по HMAC;
в order сохраняется лишь config version. SITE/BOT и manual нельзя создать параллельно для
одного intent. Скриншот recovery выбирает только manual/legacy attempt. Согласие с текущей
версией оферты/политики фиксируется на заказе и в append-only `ConsentEvidence`.

**Открытая граница:** автоматическая отправка реквизитов не создаёт фискальный чек. До
production-эксплуатации fallback бухгалтер/владелец должны подтвердить допустимость получателя,
кассовый контур, доставку чека и возвратный чек. Raw реквизиты разрешены только в secret
env/HANDOFF, запрещены в Git/Trello/log/public API. Полный threat model и rollout —
[bot-acquiring-plan.md](bot-acquiring-plan.md).

### 1. TWA auth fallback (Path 2) — ✅ ЗАКРЫТО 2026-07-26

### 2. Rate-limiting на публичных API — ✅ ОБХОД ЗАКРЫТ 2026-07-26
`/api/wb-code` за in-memory token-bucket (`src/lib/rate-limit.ts`): POST burst 10 / 1-в-5с,
GET burst 20 / 1-в-2с, 429 + `Retry-After`. Код верный — **прямой тест контейнера**
(в обход прокси, ключ «unknown») даёт ровно 20 проходов + 10×429.

**Ограничение прода:** цепочка **Cloudflare-tunnel → Traefik НЕ пробрасывает реальный IP
клиента** в контейнер — приложение видит `X-Forwarded-For`/`X-Real-Ip` = IP хоста
(значение хранится только в `HANDOFF.md`) для всех запросов, `cf-connecting-ip` не доходит. Значит per-IP лимит
вырождается в грубый глобальный троттл (все клиенты в одной корзине) и не различает атакующего
от легитимных. Диагностический лог `[wb-code] POST reserve … ip=… cf=… xff=…` добавлен для
подтверждения в проде.

**Что делать (на выбор):** (а) настроить проброс client-IP в Traefik (trusted forwarded
headers) + cloudflared, тогда per-IP лимит заработает как задумано; (б) перенести
rate-limiting на **Cloudflare WAF** (rate-limiting rules) — естественное место, раз трафик и
так через CF; (в) оставить как есть (грубый троттл + abuse-лог). Лимитер безвреден и остаётся.
Также: при масштабировании на >1 реплику Web нужен общий стор (Redis) вместо in-memory Map.

**Обновление 2026-07-16:** отдельные buckets теперь есть на регистрации, quote, checkout,
Roblox games/gamepasses, TG login challenge, identity-link, WB reserve/read,
`select-gamepass`, polling статуса SITE-заказа и client observability. Для текущей одной
Web-реплики это закрывает основной site abuse-scope; перед горизонтальным масштабированием
по-прежнему нужен общий Redis/WAF limiter и production-подтверждение реального client IP.

**Обновление 2026-07-04:** DNS переключён на **прямой A к RF-хосту**
(grey-cloud, минуя Cloudflare-tunnel — см. риск #7). Теперь client-IP в принципе доходит до
Traefik напрямую; вариант (а) стал реалистичным — проверить лог `[wb-code] ip=` после
переключения и, если IP реальный, включить per-IP лимит. Одновременно ушла CF-защита перед
источником → см. риск #7 (публичный IP).

**Обновление 2026-07-25 (ultra-review) — статус ухудшается до 🔴 P0:** переключение на
grey-cloud имело незамеченное последствие. `clientIp()` (`src/lib/rate-limit.ts:79-90`)
безусловно доверяет `cf-connecting-ip`, затем `true-client-ip`, затем `x-forwarded-for` —
это логика времён Cloudflare-туннеля. Проверка 25.07 подтверждает, что туннеля больше нет:
`dig robloxbank.ru A` даёт RF-адрес вне диапазонов Cloudflare, а ответ прода не содержит ни
`cf-ray`, ни `server: cloudflare`. Значит `cf-connecting-ip` сейчас — **обычный клиентский
заголовок**, и достаточно менять его в каждом запросе, чтобы полностью обойти все
IP-лимиты: `wb-code` (перебор и разведка кодов), `pricing/quote`, `orders/create`, IP-ведро
подбора пароля (`auth-throttle.ts`), `observability/client`, опрос статуса заказа. Устоит
только email-ведро, оно не привязано к IP. Прямое следствие — неаутентифицированный
`POST /api/pricing/quote` неограниченно создаёт строки `PriceQuote` в продовой БД, ретенции
для них нет. План (флаг `TRUSTED_PROXY_MODE`, разбор XFF по ближайшему hop, unit-тест на
подделку заголовка, опционально возврат orange-cloud + WAF) — `ultra-review-2026-07-25.md`,
находка U2.

**✅ Закрыто 2026-07-26.** `clientIp()` переписан: режим доверия задаётся env
`TRUSTED_PROXY_MODE` (`direct` по умолчанию, в проде выставлен явно).

- `direct` — берётся **последний** hop `x-forwarded-for`, то есть адрес, который дописал

### 8. Google Sheets credentials для B2B sync — 🆕 (2026-07-09, sync включён 2026-07-10)
B2B-режим `Антон` использует Google Sheets sync/write-back (`src/lib/google-sheets.ts`).
Для подключения нужен service-account JSON с доступом к таблице. Это секрет: хранить только в env/Coolify или
локальном `HANDOFF.md`, не в `docs/` и не в коммитах. Публичная документация может описывать
только имена env, схему колонок и правила sync. Саму таблицу лучше шарить на конкретный
service-account с минимальным доступом Editor только к нужному документу, а не на весь диск.
Для Антона публично фиксируется только `spreadsheetId`, маппинг колонок и статусы; локальный
путь к JSON и содержимое credentials остаются вне git. Прод-подключение использует env
`ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` и `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`; значение JSON
нельзя логировать и нельзя добавлять в `.env.example`/docs. `google-sheets.ts` не логирует
JSON credentials, private key, access token и raw-ответы Google, а `GoogleSheetsError` несёт
только короткий текст. Google Sheet расшарен на service-account email из JSON с правом Editor
(write-back пишет в `D/E`); scope ограничен `spreadsheets`. Sync ходит в Google только с
сервера — клиентский TWA работает с задачами из БД, а не с таблицей напрямую.
С Этапа 5.8 (2026-07-11) бот дополнительно лочит выполненные строки `addProtectedRange`
(анти-tampering: сотрудники не могут править/удалять уже оплаченные строки `A:D`).
Редакторы защиты берутся из `client_email` credentials + env
`GOOGLE_SHEETS_PROTECTED_EDITORS` (email владельца таблицы) — email'ы не хардкодятся
в публичном репозитории.

TWA также принимает ручной `.xlsx` upload для Антона как запасной путь импорта. Ограничения:
до `5 MB`, до `300` строк, бинарный файл не сохраняется, в БД остаются только metadata строки.
В такие файлы нельзя добавлять cookie, seed-фразы, токены, service-account JSON и другие
секреты. Зависимость `xlsx` нужно держать обновлённой и проверять через `npm audit`, потому
что парсинг офисных файлов расширяет поверхность атаки.

### 11. Связывание TG/VK/email-аккаунтов — HIGH, 🟡 TG FLOW ЗАКРЫТ, VK LINK/UNLINK ОСТАЛИСЬ (2026-07-15)

БД у каналов общая, legacy TG/VK/email-поля остаются в `User`, а серверно подтверждённые
субъекты также хранятся в `UserIdentity`. Автослияние по Roblox username небезопасно: в
production уже есть одинаковый ник у разных профилей. Обычный VK-login поэтому не
показывается как безопасная привязка/merge.

**Риск:** захват/переключение аккаунта, потеря видимости заказов, ошибочное объединение и
двойное либо потерянное списание бонусов.

**Сделано:** внешний iframe Telegram Login Widget удалён. Web создаёт криптографически
случайный challenge с TTL 5 минут, хранит только SHA-256 state и передаёт raw state боту в
deep link. Бот строит callback из Telegram-профиля и HMAC-подписывает его своим токеном;
Web повторно проверяет подпись/возраст и атомарно потребляет challenge ровно один раз.
Login резолвит legacy TG-профиль через `UserIdentity`. Link challenge выдаётся только при
web-session моложе 10 минут, заранее привязан к target User, запрещён для ADMIN и после
подтверждения переносит identities/orders/intents и бонус через ledger с
`AccountMergeAudit`. Имя, email и Roblox nick доказательством не являются.

**До запуска:** live Telegram login/link после deploy под реальным пользователем, негативная
merge matrix на prod-like clone, аналогичные явные link/unlink для VK и
recovery/admin-console. Source-профиль пока остаётся инертным audit anchor;
автоматического rollback UI нет.

**Обновление 28.07.2026.** Живой TG login/link под реальным пользователем **пройден**:
владелец завёл аккаунт по почте, привязал Telegram, профили слились
(`AccountMergeAudit` = `COMPLETED`), заказы и бонусы переехали.

Отсутствие VK-привязки тоже подтверждено вживую и уже даёт наблюдаемый эффект: вход через
VK создал **отдельный профиль** рядом с существующим TG+email, а не привязался к нему.
Практические следствия, которые надо помнить до реализации VK-link:

- клиент, у которого заказы под TG, после VK-входа увидит **пустой кабинет** и решит, что
  история потерялась;
- **вход через VK не даёт админку** — админом делает TG-личность из `ADMIN_IDS`, а она
  остаётся на другом профиле. Это работает в нашу пользу: случайный VK-вход владельца не
  создаёт второй привилегированный аккаунт.

**Обновление 29.07.2026 — migration debt измерен, не скрыт UI.** Production-срез показал
597 профилей: 372 имеют Telegram-канал и 220 — VK-канал с учётом legacy-полей, но у
170 социальных профилей хотя бы один такой канал не представлен канонической
`UserIdentity` (TG — 128, VK — 42). Это не немедленный bypass: админские права по-прежнему
выводятся только из проверенной TG identity, а не из `User.tgId`. Риск операционный:
сегментация, merge/recovery и будущие рассылки могут по-разному трактовать один и тот же
профиль, если читают только новый или только старый слой.

Админка временно считает объединение обоих слоёв и явно показывает legacy-only записи,
не выдавая их за подтверждённые identity. До удаления legacy необходимо: найти все пути,
которые ещё создают/обновляют только `tgId`/`vkId`; сделать идемпотентный backfill с
проверкой уникальности `(provider, subject)`; отдельно разобрать конфликты; после миграции
сверить количества и только затем запрещать чтение старых полей. Автоматически превращать
legacy ID в доказанную identity без происхождения/конфликт-проверки нельзя.

**Кодовый фикс 29.07.2026:** новые TG/VK bot events теперь являются provenance для ленивой
синхронизации: actor ID приходит от платформы, `syncVerifiedBotUser` атомарно сопоставляет
identity с тем же legacy `User`, а любой cross-owner конфликт отклоняет без merge. Это
закрывает дальнейшее накопление долга и постепенно лечит активную аудиторию. Старые записи,
с которыми пользователь ещё не связался после выката, намеренно не backfill-ятся «по вере
в колонку» и остаются видимым долгом до отдельной conflict-аудированной миграции.

Профильные данные тоже разделены по доверию: Telegram берётся из `ctx.from`; VK — из
официального `users.get`. VK timeout/error не перезаписывает известное имя fallback-строкой.
Общий `User.username` не перетирается вторым социальным каналом; provider-specific handle
хранится в `UserIdentity.metadata`. Это данные для контакта/интерфейса, не новое основание
для account merge или выдачи админских прав.

### 14. Выкуп геймпасса по live-цене без сверки с номиналом (TOCTOU) — ✅ ЗАКРЫТО (2026-07-12), пробел в TG закрыт 2026-07-17

**Инцидент 12.07:** клиент подложил один геймпасс в два заказа и поднял его цену между
приёмом ботом и ручным выкупом (715 → 1143 R$). TWA-выкуп покупал по live-цене без сверки

**Фикс (PLAN-gp-price-guard Ш1–Ш4):** единый гард `src/lib/purchase-guard.ts`
(`expected = ceil(amount / 0.7)`, допуск ±2 R$ — эталон автовыкупа) на всех точках выкупа:

- `api/twa/orders` `purchase` — блок до покупки с пометкой `[ЦЕНА-СТОП]` в adminNote

  создатель пасса ≠ подтверждённому нику заказа). Гонку «цену подняли между проверкой и

- ⚠️ **Пробел, найденный 17.07:** гард `Ш2` доехал только до TWA. TG-кнопка «📋 Скрипт»

- UI: карточки выкупных статусов в TWA показывают «⚠️ цена ≠ номиналу» до нажатия
  «Выкупить» (данные `gp-live-check`).

Легальный путь при расхождении — привести заказ/пасс в порядок (замена пасса клиентом,
`edit-order` из карточки, `attach-gamepass`), «мягкого» override нет. Обратный порядок
атаки закрыт 17.07: pre-existing ownership/`AlreadyOwned` больше не является автоуспехом.

ручная сверка возможного переиспользования ГП.

**Ремедиация инцидента (12.07):** данные пострадавшего заказа скорректированы под новый
пасс клиента с корректной ценой (номинал приведён к фактическому остатку долга, аудит в

появился `edit-order` («✏️ Редактировать», см. docs/twa-admin.md) — раньше требовался
прямой SQL.

**Регрессия Managed/Regional Pricing (14.07) — закрыта.** Roblox включает региональные
цены пассов по умолчанию: публичный product-info показывал глобальную цену продавца, а
cookie-аккаунт имел другую buyer-specific цену. Передача публичной цены в `expectedPrice`
давала чистый отказ `PriceChanged`; 12 валидных заказов оказались в ERROR. Денежные пути

отличается, покупка запрещена: основной TWA-путь ищет у того же ника свободную full-price
замену, проверяет её цену, продавца и отсутствие во владении; без замены ставит
`ERROR/REGIONAL_PRICE`. Клиентский `price/productId/sellerId` не является источником истины;
cookie не передаётся proxy-fallback. Регресс покрыт unit-тестами регионального стопа.

legacy v1 возвращает `PriceChanged`, но не стал постоянным обходом. Рабочий контракт не
принимает скидку из клиента: сервер читает свежий authenticated product-info и распознаёт

typed-причину `RobloxPlusSubscription:10`, а не Regional Pricing. Roblox Plus официально
субсидирует 10–20% и сохраняет доход продавца. Реализованный контракт allowlist-ит только
typed Plus-detail, проверяет процент, сумму скидки и base-price, а любой unknown/mixed
discount оставляет fail-closed. Реальный canary показал, что legacy v1 отклоняет и base,
и buyer-price как `PriceChanged`, а `/v2/user-products/{productId}/purchase` для pass
возвращает 404. Баланс, ownership и заказ не изменились. 17.07 официальный client flow
поднят в настоящем Chrome: cookie-инъекция в чистый профиль доказана покупкой, а typed Plus
передаёт проверенную buyer-price только после сверки base/арифметики скидки. Unknown/mixed
discount остаётся fail-closed; guessed endpoints не используются. Покупка считается успехом
только при ownership `false→true` и точной дельте баланса. Полный план —
`docs/roblox-plus-buyout-plan.md`.

### 15. Компрометация кода до покупателя (ПВЗ-фрод) — HIGH, 🔴 ОТКРЫТО, план утверждён (2026-07-13)

Код на вкладыше — единственный секрет, а активация работает по принципу «кто первый ввёл».
Вкладыш можно вскрыть/сфотографировать до того, как карта попадёт к честному покупателю:

**Утверждённый план (`PLAN-wb-antifraud`, локальный):**

- **A — физическая защита тиража:** скретч-слой/запечатанный конверт + предупреждение

  подтверждения продажи.
- **E — процесс инцидентов:** IP/UA-форензика активации, диспут-флоу «код уже использован»
  в ботах с автосбором доказательств и карточкой менеджеру, таблица блэклиста с мягким
  холдом выкупа.

До внедрения B основная митигация — ручной разбор жалоб менеджером.

### 18. Новый purchase API не сверяет продавца — [ПРОДАВЕЦ-СТОП] остался без второй линии — 🟡 ПРИНЯТО (2026-07-17)

Старый `economy/v1/purchases/products` принимал в теле `expectedCurrency` + `expectedPrice`
+ `expectedSellerId`, и Roblox **сам** отклонял покупку при несовпадении продавца. Это была
вторая линия защиты после нашего seller-check.

Новый `game-passes/v1/game-passes/{productId}/purchase` принимает в теле **только**
`expectedPrice` (подтверждено разбором клиентского кода Roblox: ветка `"Game Pass" ===
assetType` шлёт `{expectedPrice}`). Продавец не сверяется сервером Roblox вообще.

Последствие: `[ПРОДАВЕЦ-СТОП]` теперь **единственная** защита от подмены продавца — сценарий
общего/чужого ГП (инцидент 12.07, `YTGQ5BQ`/`QARJR71`) ловится только нами. Цена по-прежнему
имеет вторую линию: `expectedPrice` уходит в Roblox, расхождение = `PriceChanged`.

Митигация: seller-check продублирован на всех точках — сервер (`sellerMatchesOrder`,
`purchase-guard.ts`) и сам браузерный скрипт (`roblox-purchase-script.ts` сверяет
`info.Creator.Id` с зашитым числом до открытия окна покупки). Дублирование в скрипте
намеренное: тот же текст исполняется и purchase-service, и браузером менеджера.

Purchase-service слушает только SG docker bridge, защищён отдельным Bearer-токеном и
single-flight очередью; Web/TWA подключён через ограниченный SSH-туннель. Cookie не
логируется и не пишется в отдельное хранилище сервиса; она остаётся в изолированном Chrome
profile. `AlreadyOwned`/pre-existing ownership — стоп, а не
успешное завершение заказа.

### 19. Donor-cookie используется из двух egress/context и инвалидируется до покупки — P0, 🟡 DEPLOY/READINESS ГОТОВЫ; CANARY ОТКРЫТ (2026-07-17)

Новый browser transport перенёс только финальный purchase в persistent Chrome на SG, но
authenticated preflight остался в Web/TWA на RF: cookie-save/refresh, balance,
buyer-specific product-info, authenticated user и часть ownership/drain checks выполняются
прямым Node fetch. Затем та же cookie инъецируется в Chrome с другого egress/context.

Production-доказательства: service/Chrome/tunnel healthy, очередь 0; обе реальные попытки
`NotLoggedIn`; cookie присутствует в Chrome с правильными атрибутами, но authenticated user
и currency дают 401. Свежая cookie была сохранена за две минуты до второй попытки. Заказ не
закрыт, списания и нового ownership нет, автомат OFF. Canary, выполненный целиком на SG, эту
границу не проверял.

Риск: Roblox может инвалидировать donor session из-за смены IP/региона/device/HBA context.
Повторная загрузка cookie через текущий TWA даёт ложноположительное «валидна», а generic
`BrowserUnavailable` скрывает необходимость заменить cookie. Автоматические ретраи способны
сжечь новые funded sessions и остановить всю очередь.

Митигация задеплоена: один no-backlog single-flight browser-auth boundary на SG
для session, currency, buyer product-info, ownership и purchase; authenticated direct-fetch
и fallback с RF/Node удалены из donor-путей. Добавлены стабильные error codes,
PII/secret-safe structured logs и contract-test, запрещающий `.ROBLOSECURITY` в Roblox
headers вне browser service. Отдельный cookie аккаунта-приёмника drain остаётся в своём
контуре и не передаётся donor helpers. SG service, Web→SG и TG→SG прошли readiness smoke с
тестовой невалидной строкой; до новой cookie и canary 3/3 все денежные автоматические пути
выключены. План и acceptance — `docs/roblox-plus-buyout-plan.md`,
deploy-инвариант — `docs/deploy.md`.

Дополнительный donor guard: buyer-specific preflight возвращает account ID вместе с
gamepass-данными. Ручной скрипт не может быть выдан с пустым `buyerUserId`, а фоновые
воркеры при недоступной/невалидной session переходят в 15-минутный backoff вместо частых
повторов с той же cookie. 11.08.2026 source-contract обнаружил, что fallback-ветка TWA
`purchase-script` потеряла явную проверку `buyerAccountId`; guard восстановлен до deploy и
закреплён полным `donor-single-egress` suite 14/14.

### 20. Email account lifecycle и доказательство consent — 🟡 КОД ГОТОВ / SMTP ACCEPTANCE (2026-07-18)

Регистрация требует `agreedToPrivacy: true` и bcrypt-хеширует пароль, однако email не
проверяется одноразовой ссылкой, reset-пути нет, а согласие не сохраняется как versioned
evidence. Поэтому `EMAIL` identity нельзя трактовать как доказанную пользователем до
завершения lifecycle.

**Закрыто 17.07 — throttling password sign-in.** `CredentialsProvider` больше не проверяет
пароль без лимита: `src/lib/auth-throttle.ts` ограничивает попытки по IP (строго) и по
нормализованному email (сеть безопасности) **до** обращения к БД и bcrypt. Это закрывает и
второй, менее очевидный вектор: bcrypt cost 12 = ~250 мс CPU на попытку при 2 vCPU, то есть
безлимитный вход был ещё и дешёвым CPU-DoS. Ёмкость email-ведра намеренно больше IP-ведра,
иначе один хост выжигает бюджет жертвы и **блокирует ей вход** (поймано тестом на первой
версии). Инвариант закреплён тестом.

**Закрыто в коде 18.07:** verification/resend и password reset используют random 256-bit
bearer, в БД хранится только SHA-256; TTL 24 часа/30 минут, consume-once выполняется
атомарно. Регистрация даёт generic anti-enumeration ответ, `EMAIL` identity создаётся лишь
после verification. `ConsentEvidence` хранит version/timestamp/source/keyed-IP-hash без
сырого IP/UA. Reset пишет bcrypt-12 и увеличивает `sessionVersion`; JWT другой версии
инвалидируется. Legacy JWT без версии намеренно потребует повторный вход один раз после
rollout, иначе такой токен нельзя было бы отозвать.

**Закрыто 27.07 — внутренний origin в verification redirect.** За reverse proxy
`req.nextUrl.origin` у Route Handler равнялся внутреннему `https://0.0.0.0:3000`. Токен
успешно потреблялся, но финальный `303 Location` уводил пользователя на локальный адрес;
кроме UX-дефекта это делало результат зависимым от proxy/Host metadata. Verification route
теперь строит абсолютный redirect только из allowlist-origin (`robloxbank.ru`, `www` или
`localhost` в dev), а внутренний/чужой host откатывается на `https://robloxbank.ru`.
Регрессия закрыта unit-тестом и проверкой production-заголовка `Location`.

**Статус 29.07:** Brevo SMTP, DKIM/DMARC, branded SPF/return-path, Gmail-доставка,
verification redirect и Mail.ru delivery приняты в production. Mail.ru подтвердил, что
прежний `550 spam message rejected` был provider-side ошибкой, снял блокировку, после чего
владелец получил повторное письмо. Интерфейс всё равно не обещает доставку после одного
SMTP acceptance и предлагает Telegram/другой email. Входящий MX/служебный ящик и отдельный
Yandex recipient-check остаются задачами. Детали: `docs/email-setup.md`.

**Риск (остаточный):** до SMTP acceptance самостоятельный recovery недоступен; in-memory
лимит не заменяет shared limiter при нескольких web-репликах; абсолютный/idle TTL и кнопка
«выйти на всех устройствах» остаются отдельным P1.

### 24. IDOR в callback-кнопках ботов — ✅ ЗАКРЫТО 2026-07-26

`bots/shared/gp-watch-confirm.ts:26,71` принимает `orderId` строкой и **не проверяет, что
заказ принадлежит вызывающему**. Функции вызываются из `bots/tg/handlers.ts:3397,3420`
(`gpw_ok:` / `gpw_no:`) и `bots/vk/handlers.ts:818,834`. Та же дыра в
`handlers.ts:4426-4444` (`uci:` — отмена `DirectIntent` по ID).

**Почему это достижимо:** `callback_data` не является доверенным вводом. В Telegram любой
пользователь, у которого есть хоть одно сообщение бота с inline-клавиатурой, может через
неофициальный MTProto-клиент вызвать `messages.getBotCallbackAnswer` с **произвольной**
строкой `data`. В VK аналогично отправляется произвольный `payload`.

**Последствие:** чужой заказ переводится в `PENDING`, и при этом *предположительный* ник
(`probableNick`, найденный автоматикой) записывается в `robloxUsername` как подтверждённый
клиентом — комментарий в коде прямо называет его «authoritative». Дальше заказ уходит в
очередь на реальный выкуп робуксов на ник, который настоящий покупатель никогда не
подтверждал. Обратный вариант (`gpw_no:`) стирает `probableNick` у чужого заказа.

**Что ограничивает:** нужен точный `orderId` — CUID 25 символов, перебору не поддаётся.
Поэтому HIGH, а не критично. Но любая утечка ID (скриншот, пересланная карточка, ошибка в
логах) превращает это в потерю денег.

**Показательно:** соседние ветки того же файла сделаны правильно — `user_resubmit:`
(`handlers.ts:4988-4994`) и `ucd:` (`:4474`) владельца проверяют. Это пропуск, а не принятое
решение.

**План:** передавать в функции `actor` (платформа + внешний ID), резолвить `User` и
сверять `order.userId`; при несовпадении — отказ и лог `[gp-watch] ownership violation` как
сигнал атаки; вынести общий хелпер `assertOwnsOrder` и провести им аудит всех 55 веток
`callback_query`. Детали — `ultra-review-2026-07-25.md`, находка U6.

**✅ Закрыто 2026-07-26.** Появился общий хелпер `bots/shared/ownership.ts`
(`assertOwnsOrder` / `assertOwnsIntent`): сущность читается только вместе с резолвом
`User` по `tgId`/`vkId` и жёсткой сверкой владельца, нарушение пишется в лог как
`[ownership] violation …` — это сигнал атаки. `confirmGpWatch`/`declineGpWatch` теперь

«чужой заказ → forbidden» и «вызывающий вообще не наш пользователь»).

### 25. Бонусы и скидка списываются без компенсирующей записи — ✅ ЗАКРЫТО 2026-07-26

Не уязвимость извне, а системный дефект денежного учёта, поэтому фиксируется здесь наравне
с рисками: пользователь теряет накопленное, а расследовать это нечем.

`src/lib/canonical-web-order.ts:143-180` в транзакции создания заказа списывает `balance` и
обнуляет `rubleDiscount`. Компенсации нет ни на одном исходе: провал `Init`
(`api/orders/create/route.ts:153-171`), `REJECTED`/`CANCELED` от банка
(`api/webhooks/tinkoff/route.ts:105-107`), брошенная оплата. `BonusLedger` пишется только с
отрицательной дельтой; `balance: { increment }` во всём проекте встречается один раз —
бонус за отзыв.

В ботах симметрично: `bots/tg/handlers.ts:4476-4506` пытается вернуть бонус при отмене
прямого заказа, но берёт номинал из строки `WbCode`, которой у `DIR-` заказов **никогда не
существует** (`handlers.ts:2450`), поэтому ветка возврата недостижима. Скидка не

при гонке, и запись в леджер не делается.

накапливается молча, спор с клиентом нечем закрыть.

`SUM(deltaRobux) == balance` и ручная компенсация пострадавшим с 12.07. Детали —
`ultra-review-2026-07-25.md`, находки U3/U4.

**✅ Закрыто 2026-07-26.**

### 26. CSP всё ещё допускает `unsafe-inline`/`unsafe-eval` — 🟡 ЭТАП 1 (2026-07-26)

`next-security.ts`: боевая политика по-прежнему разрешает инлайн-скрипты и `eval` — на
платёжном сайте это главный отсутствующий барьер против XSS. Ужесточать вслепую нельзя:
гейт открывают из Telegram WebView и VK WebView, поломка входа там видна только по жалобам.

**Сделано (этап 1):** рядом с боевой политикой едет строгая `Content-Security-Policy-Report-Only`
(без `unsafe-inline`/`unsafe-eval`) с `report-uri /api/observability/csp-report`. Браузер
ничего не блокирует, но присылает всё, что строгая политика запретила бы; нарушения
логируются строкой `[csp-report] directive=… blocked=… doc=…`, роут за rate-limit.

**Дальше:** перевести инлайн-скрипт `src/app/twa/page.tsx` на nonce → убрать `unsafe-eval`
→ убрать `unsafe-inline` в `script-src` → enforce, и только после чистого отчёта на
iPhone / Android / Telegram WebView / VK WebView. План — `ultra-review-2026-07-25.md`, U10.

**⚠️ Инцидент 28.07: hash в боевой политике отменил `'unsafe-inline'`.** Вместе с D3
sha256-хеш boot-скрипта темы добавили не только в Report-Only, но и в боевую политику,
рядом с `'unsafe-inline'`. По спецификации CSP наличие hash- или nonce-источника
**отменяет** `'unsafe-inline'` в той же директиве — то есть политика фактически стала
строгой, и браузер заблокировал все inline-скрипты Next.js. Гидратация не запускалась:
`/login` и `/checkout` отдавали пустой экран, на главной ничего не реагировало на нажатия.
Замер на проде: `window.__next_f` пуст, в консоли `Executing inline script violates …`.
Server-rendered HTML при этом отдавался нормально, поэтому `smoke:site` и `smoke-corridor`
остались зелёными — они проверяют HTML, а не исполнение скриптов.

**Исправлено:** хеш убран из боевой политики и оставлен только в Report-Only. Инвариант
закреплён контракт-тестом `src/__tests__/theme-boot.test.ts`: пока в боевой политике есть
`'unsafe-inline'`, hash/nonce в ней запрещены. Вывод для будущего enforce: **добавление
хеша — это уже enforce**, промежуточного состояния «и хеш, и `unsafe-inline`» не бывает.

**Вторая причина, почему заметили поздно (исправлена 28.07).** У `<html>` в
`src/app/layout.tsx` не было `suppressHydrationWarning`, хотя boot-скрипт темы намеренно
правит этот узел до гидратации (`data-theme`, `data-theme-mode`, `color-scheme`). React
писал предупреждение о рассинхроне на **каждой** странице — проверено на `/`, `/faq`,
`/guarantees`, `/legal/details`, `/login`, `/checkout`. В этом постоянном шуме настоящая
поломка гидратации ничем не выделялась. Теперь подавление стоит ровно на `<html>`, остальное
дерево проверяется как обычно, и появление предупреждения снова означает реальную проблему.

### 21. Коды активации Roblox — предъявительские секреты в БД — P0, 🔵 ПЛАН (2026-07-17)

Планируемый товар «коды активации» вводит в систему **предъявительский инструмент**: строка
кода сама по себе является деньгами, для её траты не нужен ни аккаунт, ни пароль. Это
принципиально опаснее всего, что есть сейчас: утёкший код невозможно «отозвать», а факт
кражи виден только по жалобе клиента.

**Риск:** утечка дампа БД или логов = прямая потеря денег; инсайдерская кража кода
менеджером; двойная выдача одного кода при гонке; оплата без выдачи и без возврата;
чарджбэк «код не работал» без доказательства раскрытия; мёртвые коды при нелегальном или
регионально несовместимом поставщике.

**Требования (обязательные, до первой продажи):** envelope-шифрование кода в покое (ключ в
env/KMS, не в публичном репозитории); запрет кода в любых логах/ошибках/уведомлениях с
contract-тестом; атомный резерв (`UPDATE … WHERE status='IN_STOCK'` / `SKIP LOCKED`) вместо
read-modify-write; идемпотентная выдача на `PaymentAttempt.idempotencyKey` + `OutboxMessage`;
аудит доступа менеджера; фиксация `revealedAt` как доказательство для спора; автоматический
возврат, если деньги взяты, а код не выдан. Логика родственна риску №15 (скретч-слой WB).

**План и открытые вопросы:** `docs/roblox-codes-plan.md`.

### 12. Детерминированный пароль в seed — ✅ ЗАКРЫТО В КОДЕ (2026-07-12)

### 13. Публичная витрина: headers, abuse и глобальные SDK — HIGH, 🟡 ЧАСТИЧНО ЗАКРЫТО (2026-07-12)
