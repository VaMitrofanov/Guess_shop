# WB chat opener («кликер»): последний ручной шаг DBS

Статус на 21.08.2026: **план, реализация не начата.** Нужен ответ владельца по О1–О4
(раздел 11) — в первую очередь принципиальное «идём в неофициальную автоматизацию кабинета
или нет».

⚠️ **23.08.2026: у этой задачи появилась альтернатива без автоматизации кабинета.**
Триггер T1 из [wb-voice-call-plan.md](wb-voice-call-plan.md) добивается того же —
открытого чата без человека — но чат открывает сам покупатель после звонка, поэтому нет ни
сессии кабинета, ни риска нарушения правил WB. Рекомендация: держать кликер на паузе до
результатов этапа Z6 голосового плана (решение владельца Г7).

## 1. Зачем

Проверка 21.08.2026 (детали и пробы — [wb-dbs-delivery-plan.md](wb-dbs-delivery-plan.md),
раздел «Чат ещё не доступен API») показала: **весь DBS-контур уже автоматический, кроме
одного клика.** Публичный API WB не умеет создавать чат, но и ждать покупателя не нужно —
чат открывает продавец кнопкой «Перейти в чат с покупателем» в кабинете. После клика WB сам
публикует системное событие (`isNewChat: true`, `sender: seller`, «Чат с покупателем по
товару {nmId}»), в `GET /api/v1/seller/chats` появляется `replySign`, и дальше наш воркер
работает сам.

Живая проверка на заказе `5544369355` (21.08, 06:57 UTC): владелец нажал кнопку → чат и
`replySign` появились в API за секунды, воркер подтянул имя покупателя и перевёл заказ в
`CODE_REQUESTED`. **Но сообщение покупателю при этом не ушло** — это отдельный баг, K0 ниже;
до него доходило только потому, что владелец вставлял тот же текст руками из шаблона
кабинета.

Цена этого клика по 48 заказам с чатом:

| Кто открыл чат | Заказов | Медиана от создания заказа | Максимум |
|----------------|---------|----------------------------|----------|
| Продавец (клик в кабинете) | 34 | 3.2 мин | 133.9 мин |
| Покупатель (написал сам) | 14 | 1.4 мин | 20.6 мин |

То есть 70% заказов ждут человека, и хвост — больше двух часов. Всё это время покупатель
стоит без инструкции, а мы не можем ни получить код доставки, ни закрыть заказ.

**Цель:** новый DBS-заказ получает открытый чат и запрос кода без участия человека,
медиана ≤ 60 секунд, потолок ≤ 5 минут, ручной режим остаётся рабочим fallback навсегда.

## 2. Граница задачи

Автоматизируем **ровно один шаг** — открытие чата по заказу. Ничего больше в кабинете не
трогаем: ни статусы (они идут через официальный marketplace API), ни цены, ни карточки, ни
чтение переписки. Всё, что после открытия чата, уже работает:

```
новый DBS-заказ → [ клик, единственный ручной шаг ] → chat + replySign в API
   → бот просит код доставки → покупатель присылает код → receive → гейт-код → TG/VK
```

## 2а. K0 — системное сообщение WB обманывает автоответ (чинится отдельно от кликера)

Найдено 21.08 при разборе живого заказа. **После клика покупателю ничего не отправляется —
хотя всё для отправки уже есть.**

Механика: `markCodeRequested` (`bots/shared/wb-delivery-sync.ts:1196`) считает любое
не-покупательское событие сообщением оператора: «оператор ответил из кабинета, значит
инструкцию уже отправили». Но системная карточка, которой WB открывает чат, тоже приходит
как `sender: seller` (`isNewChat: true`, `goodCard`, текст «Чат с покупателем по товару
{nmId}»). Поэтому заказ прыгает `WAITING_BUYER_CHAT → CODE_REQUESTED` с
`source: wb-seller-cabinet`, а `tryAutoRequestCode` вызывается только для сообщений
покупателя (строка 1205) и уже не срабатывает.

Итог: чат открыт, консоль показывает «код запрошен», покупатель не получил ничего. В проде
это норма для всех заказов, открытых продавцом: 13 из последних 20 событий
`DELIVERY_CODE_REQUESTED` — `wb-seller-cabinet`, и запрос доезжал до покупателя только
руками. Живой пример: `5544369355` — чат открыт в 06:57 UTC, последнее сообщение в чате всё
ещё системная карточка WB.

**Фикс:** отличать открытие чата от сообщения оператора — событие с `isNewChat: true`,
вложением `goodCard` и текстом `^Чат с покупателем по товару \d+$` означает «чат открыт»
(`chatState → READY`), после чего штатный `tryAutoRequestCode` отправляет запрос кода.
Настоящий ответ оператора из кабинета по-прежнему должен вести в `CODE_REQUESTED` — на это
нужен тест, как и на то, что запрос уходит ровно один раз.

**Почему это первым:** K0 закрывает половину проблемы без всякой автоматизации кабинета —
после ручного клика дальше всё идёт само. Он не зависит от решения О1 и делается за час.

## 3. Что неизвестно и выясняется в K1

Ответы на это определяют выбор варианта, поэтому K1 — обязательный первый этап.

1. Какой запрос уходит по кнопке «Перейти в чат с покупателем»: метод, URL, тело, какие
   поля заказа в нём (`orderId`? `rid`? `nmID`? `chatID` заранее?).
2. Чем он авторизуется: cookie `WBToken`, заголовок `Authorization`, что-то ещё; есть ли
   подпись/anti-bot заголовки (`x-wb-*`), которые нельзя воспроизвести вне браузера.
3. Живёт ли сессия кабинета вне браузера: срок жизни токена, есть ли refresh, требует ли
   продление SMS-кода.
4. Идемпотентность: второй клик по тому же заказу создаёт второй чат или возвращает
   существующий (у заказа `5540950769/5540950770` в списке видны два чата на один `rid` с
   суффиксами `.0.0` и `.0.1` — это разные позиции заказа, но проверить надо явно).
5. Есть ли ограничение по статусу заказа: можно ли открыть чат на `new`, или только после
   `confirm`/`deliver`.

**Как выясняем:** владелец открывает кабинет, мы смотрим сетевую панель на одном живом
заказе (Claude in Chrome или DevTools → Copy as cURL) и повторяем этот запрос из curl с той
же сессией. K1 закрыт, когда `curl` открыл чат на реальном заказе и чат виден в
`GET /api/v1/seller/chats`.

## 4. Варианты и рекомендация

| Вариант | Суть | Плюсы | Минусы |
|---------|------|-------|--------|
| **A. HTTP-replay** | воркер сам зовёт внутренний endpoint кабинета с сохранённой сессией | дёшево, быстро, без браузера в проде, живёт внутри текущего воркера | падает, если WB добавит подпись/anti-bot; сессию надо продлевать |
| **B. Headless-браузер** | отдельный сервис с Chromium и залогиненным профилем жмёт кнопку | воспроизводит любые скрытые заголовки, ближе всего к «живому» продавцу | тяжёлый контейнер, медленнее (секунды), ломается при редизайне вёрстки |
| **C. Полуавтомат** | пуш владельцу «открой чат по заказу X» с дедлайном и эскалацией | ноль риска, делается за час | человек остаётся в цикле — цель не достигнута |

**Рекомендация: A, если K1 покажет воспроизводимый запрос; иначе B.** C реализуем в любом
случае как страховку (K2) — она же покрывает случай «сессия кабинета умерла».

Оба пути A и B — **неофициальная автоматизация кабинета**: вне гарантий WB, ломается при
редизайне, формально может считаться нарушением правил площадки. Это осознанное решение
владельца (О1), а не техническая мелочь. Снижаем риск объёмом и поведением: один клик на
свой же заказ, человеческий темп, потолок в час, kill switch.

## 5. Архитектура (вариант A, вариант B отличается только транспортом)

Новый модуль `bots/shared/wb-cabinet-chat.ts` — единственная точка, которая знает про
кабинет. Наружу отдаёт одну функцию:

```ts
openBuyerChat(order: { wbOrderId: string; rid: string; nmId: number }): Promise<
  | { ok: true }
  | { ok: false; reason: "SESSION_EXPIRED" | "RATE_LIMITED" | "REJECTED" | "UNKNOWN" }
>
```

Вызов встраивается в существующий цикл `runWbDeliverySync` (тик 5 с, лизинг воркера уже
есть — `acquireLease`, так что двух кликеров одновременно не будет) отдельным проходом
`openMissingChats(db, out)` **после** `syncChatDirectory`, чтобы решение принималось по
свежему списку чатов.

Кого берём в работу:

- `chatState = WAITING_BUYER_CHAT` **и** чата у заказа нет;
- `cancelledAt is null`, `completedAt is null`;
- `supplierStatus` в разрешённом наборе (уточняется в K1, по умолчанию `new|confirm|deliver`);
- возраст заказа ≥ `WB_CHAT_OPENER_DELAY_SEC` (по умолчанию 45 с — даём покупателю шанс
  написать первым и не гоняем кабинет на заказах, которые тут же отменяются);
- `chatOpenAttempts < 3` и `chatOpenNextAt <= now()`.

Порядок и идемпотентность (тот же приём, что у отправки сообщений — CAS **до** внешнего
вызова):

1. CAS `chatState: WAITING_BUYER_CHAT → CHAT_OPENING` c `chatOpenAttempts += 1`; кто не
   выиграл гонку — выходит;
2. `audit(..., "CHAT_OPEN_REQUESTED", "chat-open:{orderId}:{attempt}")`;
3. вызов кабинета;
4. успех → ждём, пока чат приедет в `syncChatDirectory` (он сам переведёт в `READY`);
   `CHAT_OPENING` держится не дольше `WB_CHAT_OPENER_TIMEOUT_SEC` (120 с), после чего
   возвращается в `WAITING_BUYER_CHAT` с backoff — то есть «неизвестный исход» никогда не
   застревает;
5. отказ → `WAITING_BUYER_CHAT`, `lastErrorCode`, `chatOpenNextAt = now + backoff`
   (1 → 5 → 15 мин), после третьей попытки — эскалация в TG админам и в консоль;
6. `SESSION_EXPIRED` — особый случай: глобальный стоп кликера, алерт владельцу «зайдите в
   кабинет и обновите сессию», все заказы уходят в ручной режим C.

Флаги (в стиле существующих `WB_CHAT_SEND_ENABLED` / `WB_DBS_MUTATIONS_ENABLED`, значения
по умолчанию — выключено):

| Переменная | Смысл |
|------------|-------|
| `WB_CHAT_OPENER_ENABLED` | главный выключатель кликера |
| `WB_CHAT_OPENER_DRY_RUN` | всё считаем и логируем, но кабинет не зовём (этап K3) |
| `WB_CHAT_OPENER_DELAY_SEC` | пауза после создания заказа, по умолчанию 45 |
| `WB_CHAT_OPENER_MAX_PER_HOUR` | потолок кликов в час, по умолчанию 20 |
| `WB_CABINET_SESSION_KEY` | ключ шифрования сессии кабинета (или переиспользуем `WB_DELIVERY_ENCRYPTION_KEY`) |

Темп: не чаще одного клика в 20–40 секунд (jitter), не больше `MAX_PER_HOUR`, никаких
параллельных вызовов. При превышении потолка — не очередь до бесконечности, а эскалация в C.

## 6. Данные

- `WbMarketplaceOrder`: новое состояние `chatState = CHAT_OPENING`, поля
  `chatOpenAttempts Int @default(0)`, `chatOpenNextAt DateTime?`, `chatOpenedBy String?`
  (`auto` | `manual`) — последнее нужно, чтобы честно мерить долю автоматики.
- Новая модель `WbCabinetSession` (одна строка): `encryptedValue`, `keyVersion`,
  `expiresAt`, `lastOkAt`, `lastErrorCode`, `updatedAt`. Шифрование — тем же конвертом, что
  и `replySign`/код доставки (`encryptWbSecret`/`decryptWbSecret`).
- Аудит: `CHAT_OPEN_REQUESTED`, `CHAT_OPENED`, `CHAT_OPEN_FAILED`, `CABINET_SESSION_EXPIRED`
  в существующий `WbMarketplaceEvent` (append-only, idempotencyKey по заказу и попытке).

Все очереди DBS по-прежнему считаются от `stage`; `CHAT_OPENING` должен попасть в ту же
классификацию, иначе заказ пропадёт из «Срочных» на две минуты.

## 7. Безопасность

- **Сессия кабинета — самый чувствительный секрет проекта:** это доступ ко всему кабинету
  WB, шире, чем API-ключ. Хранить только зашифрованной, в БД или secret store, никогда в
  репозитории (он публичный), в логах, в TWA-ответах и в error payload. Значение не
  показывать в консоли даже админу — только статус «живая до …».
- Кликер не читает и не пишет в кабинете ничего, кроме открытия чата по своему заказу.
- Все действия — под тем же admin/audit-контуром, что и остальные защищённые операции:
  ручная кнопка «Открыть чат» требует admin-сессии, CSRF/origin guard и пишет в аудит.
- Новый риск завести в [security.md](security.md): «автоматизация кабинета WB — компрометация
  сессии даёт полный доступ к кабинету; митигация: шифрование, kill switch, потолок действий,
  аудит, ручной fallback».
- Логи кликера — только коды и идентификаторы заказа, без имён, телефонов и текста чата.

## 8. Риски

| Риск | Как проявится | Митигация |
|------|---------------|-----------|
| WB считает автоматизацию кабинета нарушением | предупреждение, блок аккаунта | человеческий темп, потолок в час, только свои заказы, только один тип действия, мгновенный kill switch |
| Сессия протухает | 401 на клике | детект `SESSION_EXPIRED`, стоп кликера, алерт владельцу, автоматический откат в ручной режим |
| WB меняет endpoint/вёрстку | клики падают | contract-тест на форму запроса, алерт при 3 подряд отказах, fallback C |
| Дубли чатов | два чата на заказ | CAS перед вызовом, проверка списка чатов после, K1-проверка идемпотентности |
| Кликер бьёт по отменённым заказам | лишние чаты, недовольные покупатели | фильтр `cancelledAt is null` + свежий статус перед кликом |

## 9. Наблюдаемость

- Метрика **time-to-chat**: медиана и p95 от `createdAt` заказа до первого события чата,
  отдельно `auto` и `manual`; сейчас 3.2 мин / ~134 мин — целевое ≤ 60 с / ≤ 5 мин.
- Доля заказов, где чат открыт автоматически (цель ≥ 90% при живой сессии).
- Алерты в TG: `SESSION_EXPIRED`, три подряд `CHAT_OPEN_FAILED`, заказ в
  `WAITING_BUYER_CHAT` дольше 10 минут, кликер выключен флагом при живых заказах.
- Виджет DBS в консоли: строка «Чат открыт автоматически / вручную / ждёт».

## 10. Этапы

| Этап | Что | Готово, когда |
|------|-----|---------------|
| **K0** | Системная карточка WB ≠ сообщение оператора: чат открыт → `READY` → автозапрос кода (раздел 2а) | после клика покупатель получает запрос кода в течение одного тика воркера, ровно один раз; ответ оператора из кабинета по-прежнему гасит автоответ; тесты зелёные |
| **K1** | Discovery: снять запрос кнопки, повторить его из curl, проверить идемпотентность, срок жизни сессии, зависимость от статуса | чат на реальном заказе открыт из curl, ответы на все 5 вопросов раздела 3 записаны сюда |
| **K2** | Fallback C: пуш владельцу и кнопка «Открыть чат» в консоли/TWA + эскалация по таймауту | заказ без чата даёт уведомление в течение 60 с, кнопка ведёт прямо в нужный чат кабинета |
| **K3** | Каркас без побочных эффектов: модуль, состояния, миграция, флаги, аудит, `DRY_RUN=true` | в логах видно «кого бы кликнули», реальных вызовов ноль, тесты на выбор кандидатов зелёные |
| **K4** | Хранение сессии: модель, шифрование, экран «сессия кабинета» в админке (статус + вставка нового токена), детект `SESSION_EXPIRED` | владелец обновляет сессию из админки за минуту, значение нигде не светится |
| **K5** | Ручной триггер: кнопка «Открыть чат» в консоли зовёт кабинет через тот же модуль | один клик в нашей админке заменяет клик в кабинете WB, всё в аудите |
| **K6** | Canary: авто-кликер включён с потолком 5 в час и задержкой 90 с, на одном товаре | сутки без дублей чатов, без отказов WB, time-to-chat < 5 мин |
| **K7** | Полный автомат: потолки штатные, backoff, эскалация, алерты | 95% новых DBS-заказов получают чат без человека |
| **K8** | Документация и приёмка: обновить этот файл фактами, `wb-dbs-delivery-plan.md`, `security.md`, HANDOFF | цифры «до/после» зафиксированы, риск заведён, kill switch проверен на проде |

Оценка: K0 — час, независимо от остальных решений; K1 — полчаса вместе с владельцем; K2 — час; K3–K5 — рабочий день; K6 — сутки
наблюдения; K7–K8 — полдня. Вариант B добавляет к K3 отдельный контейнер с Chromium и
примерно день работы.

## 11. Решения владельца

- **О0.** K0 (раздел 2а) — делаем сразу? Он полезен при любом ответе на О1 и не трогает
  кабинет вообще.
- **О1.** Идём ли в неофициальную автоматизацию кабинета (раздел 4, риски раздела 8)? Без
  «да» делаем только K2 — быстрый полуавтомат, человек остаётся в цикле.
- **О2.** Если K1 покажет, что запрос воспроизводится — берём A; если нет, поднимаем
  headless-контейнер (B) или останавливаемся на C?
- **О3.** Как обновляем сессию кабинета: ручная вставка токена в админку (просто, надёжно,
  раз в N дней) или пытаемся автологин с SMS-кодом (сложно, хрупко, лишний риск)?
- **О4.** Пороги: задержка перед кликом (45 с?), потолок кликов в час (20?), число попыток
  (3?) и время до эскалации владельцу (10 мин?).

## 12. Definition of Done

1. Новый DBS-заказ получает открытый чат без человека; медиана time-to-chat ≤ 60 с.
2. Ни одного дубля чата и ни одного клика по отменённому/закрытому заказу.
3. `WB_CHAT_OPENER_ENABLED=false` мгновенно возвращает контур к сегодняшнему ручному режиму,
   и это проверено на проде.
4. Смерть сессии кабинета не роняет заказы: автоматический откат в режим C + алерт.
5. Сессия кабинета нигде не появляется в открытом виде; риск описан в `security.md`.
6. Каждый клик виден в аудите с заказом, попыткой и исходом.
7. Метрики «до/после» записаны в этот файл и в HANDOFF.
