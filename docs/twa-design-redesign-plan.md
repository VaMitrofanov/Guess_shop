## Целевой дизайн-контракт

### Визуальный язык и иерархия

Целевой язык — **Apple iOS Liquid Glass / Ultraviolet**, а не Material/Android. Компактность
не означает плоскую плотную Android-ленту:

- системный SF/Apple font stack, large navigation titles и touch targets не меньше 44 pt;
- inset grouped lists, мягкие разделители и один стеклянный tab bar;
- объём создают один доминирующий glass hero и ограниченные elevation/shadow, а не множество
  одинаковых карточек;
- без floating action button, Material search button, card-wall и декоративных badge на
  каждом поле;
- первая отрисовка Главной имеет только три уровня: поиск, hero «Сегодня», grouped list
  «Сейчас» с двумя операционными переходами;
- результаты единого поиска не занимают Главную заранее и появляются только после запроса.

### 2. Единый поиск на главной

Сейчас поиск разделён:

- `OrdersScreen` ищет внутренние заказы по коду, имени, username, Roblox-нику, заметке,
  ID/URL геймпасса;
- `BossrobuxScreen` через публичные Roblox API ищет пользователя и его live-геймпассы по
  нику, ID или URL.

Новый поиск объединяет результаты, но не смешивает их визуально:

1. группа **«Заказы»** — данные нашей БД;
2. группа **«Геймпассы Roblox»** — live-результаты внешнего API;
3. тап по результату открывает нужный экран и конкретный заказ/геймпасс.

Контракт запроса:

- WB/DIR/AV/MN-код, `@username`, TG/VK ID и текстовый запрос всегда идут во внутренний
  поиск;
- Roblox profile/gamepass URL и числовой gamepass ID запускают оба источника;
- Roblox-ник от трёх символов запускает внутренний поиск сразу и live-поиск после debounce;
- старый запрос отменяется через `AbortController`, ответы связываются с исходной строкой;
- частичный сбой Roblox не скрывает найденные заказы и наоборот;
- внешние результаты имеют явную метку `live`, чтобы их не принять за существующий заказ.
- до ввода запроса результаты не монтируются: Главная сохраняет спокойную иерархию.

Рекомендуемая реализация: один новый оркестрирующий `GET /api/twa/search` с лимитами и общей
авторизацией. Он переиспользует существующие функции поиска, но возвращает компактный union
`orders[] / gamepasses[] / partialErrors[]`; бизнес-логику в React не дублируем.

Trello: [единый поиск](https://trello.com/c/mYXlYOT9).

#### Order Intelligence: полное досье выбранного заказа

Поиск работает в два уровня, чтобы не перегружать Главную и не создавать N+1:

1. `GET /api/twa/search` возвращает лёгкие кандидаты из БД и Roblox;
2. после выбора заказа `GET /api/twa/orders/[id]/intelligence` собирает одно нормализованное
   досье `OrderIntelligence`.

Досье объединяет уже известные системе данные, но сохраняет происхождение и свежесть:

| Группа | Что показывает |
|---|---|
| Заказ | код, источник, статус, чистый номинал, фактическая цена gamepass, таймеры, favorite/note |
| Клиент | подтверждённые TG/VK/EMAIL identity, username, Roblox-ник, reachability, бонус, число заказов |
| Gamepass | ID/URL, название, live price, seller match, `isForSale`, duplicate/reused/ownership checks |
| Деньги | payment status, продажа, refund balance, purchase snapshots, себестоимость и точная/оценочная прибыль |
| Выкуп | donor/purchaser account, cookie freshness без самого cookie, completedAt, ownership recovery |
| Коммуникации | последний доставленный канал, review/GP-watch, недостижимый VK и требуемое ручное действие |
| Связи | прошлые заказы identity-кластера, тот же Roblox-ник/gamepass, последний WB-код, active duplicate |
| Контроль | собранные warnings, partial errors и `observedAt` для live-полей |

Правила доверия:

- TG/VK/EMAIL identity считаются подтверждёнными только по `UserIdentity`/legacy verified
  каналам; совпадение Roblox-ника не объединяет пользователей;
- DB-данные возвращаются даже при таймауте Roblox/VK; внешний сбой записывается в
  `partialErrors[]`, а не превращает всё досье в ошибку;
- live-поля имеют `observedAt`, TTL и явную метку `live`; денежные snapshots не
  пересчитываются текущими настройками;
- GET досье не делает write, не отправляет уведомления и не запускает выкуп;
- cookie/token/секреты никогда не входят в response, показывается только validity/age;
- PII доступна только после `extractTwaUser` и не логируется целиком.

Рекомендуемая серверная архитектура:

- чистый агрегатор `src/lib/order-intelligence.ts` с типом `OrderIntelligence`;
- один базовый Prisma query заказа с нужными relations, затем ограниченные параллельные
  aggregates по user/gamepass/payment/events;
- live Roblox/VK checks запускаются параллельно с timeout и существующими cache helpers;
- related orders ограничиваются компактной сводкой и последними N строками, полная история
  остаётся cursor-paginated;
- endpoint возвращает `completeness: FULL|PARTIAL`, `warnings[]`, `partialErrors[]` и
  server timing по группам для контроля latency;
- budget: быстрый DB-summary до 400 мс, полное досье с live-проверками до 1.5 с p95; при
  превышении отдаётся PARTIAL, клиент может обновить только live-блок.

UX результата:

- сверху один summary: источник/статус/код, Roblox-ник, username, номинал;
- рядом денежная тройка `продажа / себестоимость / прибыль`, если применимо;
- ниже iOS grouped rows `Клиент / Геймпасс / Оплата / Выкуп / Связи / Контроль`;
- критические warnings стоят между summary и rows и не прячутся;
- действия контекстные: `Открыть заказ`, `Написать`, `Исправить`, `Обновить live`; опасные
  действия остаются в родной карточке заказа с прежними подтверждениями.

Trello: [полное досье заказа](https://trello.com/c/BTO5Hhwn).

### 3. Компактная карточка заказа

Обычная карточка по умолчанию состоит из трёх строк:

1. источник + статус + возраст;
2. Roblox-ник + рабочая сумма R$;
3. username клиента + код + номинал.

Постоянно видны только данные, по которым менеджер принимает решение. Исключения — красные
или жёлтые предупреждения: протухший cookie, price mismatch, gamepass off-sale, VK 901,
отказ GP-watch и ошибка оплаты. Они не прячутся.

По тапу раскрываются gamepass, donor account, заметка, review-бонус, вторичные таймеры и
действия. Основное контекстное действие (`Выкупить`, `Исправить`, `Подтвердить оплату`)
остаётся доступно в один дополнительный тап; редкие действия уходят в action sheet.

Критерий плотности: на iPhone 14/15 Pro Max до первого скролла должно помещаться минимум
вдвое больше обычных заказов, чем в текущем варианте, без уменьшения основного текста ниже
14 px.

### 4. История покупок

История становится плоской хронологической лентой с фильтрами `Все / WB / Direct / Avito`.
Группировка по cookie-аккаунту из основной ленты убирается: этот контекст не входит в
запрошенный минимальный набор и уже виден в аккаунтном дашборде/аудите.

Строка истории показывает:

- Roblox-ник;
- номинал (чистые R$);
- WB-код либо внутренний DIR/AV-код;
- username клиента;
- источник; для DIRECT/AVITO — точную прибыль в ₽, только когда есть денежные snapshot.

Нельзя снова загружать все страницы `DONE` при раскрытии. Нужна серверная pagination и
серверные агрегаты по источникам/прибыли; первая страница должна быть быстрой и полезной.

Trello: [карточки и история](https://trello.com/c/D7jNGFYR).

### 5. Прибыль DIRECT и AVITO

Текущая модель недостаточна для точной истории:

- `DirectIntent.rublePrice` хранит фактическую сумму продажи со скидкой, но при создании
  `WbOrder` не переносится;
- для AVITO сумма продажи в рублях не запрашивается и не хранится;
- `WbOrder.purchaseRate` — snapshot курса закупки **в $ за 1000 R$**, но отдельного snapshot
  `USD/RUB` и итоговой себестоимости в копейках нет;
- пересчёт старой прибыли по текущим настройкам менял бы историю и потому запрещён.

Целевой денежный контракт для новых DIRECT/AVITO:

| Snapshot | Когда фиксируется | Источник |
|---|---|---|
| `saleAmountKopecks` | создание заказа | DIRECT: `DirectIntent.rublePrice × 100`; AVITO: обязательное поле формы |
| `purchaseRobuxAmount` | фактический выкуп | живая/подтверждённая цена gamepass, а не только расчётный номинал |
| `purchaseRateUsdPer1k` | фактический выкуп | текущий `GlobalSettings.purchaseRate` |
| `purchaseUsdToRub` | фактический выкуп | текущий `GlobalSettings.usdToRub` |
| `purchaseCostKopecks` | фактический выкуп | округлённая себестоимость по трём snapshot выше |
| `profitKopecks` | фактический выкуп | `saleAmountKopecks - purchaseCostKopecks` |

Формула себестоимости:
`round(purchaseRobuxAmount / 1000 × purchaseRateUsdPer1k × purchaseUsdToRub × 100)`.

Snapshot-поля меняются только в контролируемых переходах заказа и не вычисляются заново при
чтении истории. Все пути `COMPLETED` обязаны использовать одну общую функцию фиксации
себестоимости: TWA purchase/complete, батч, автовыкуп и TG/VK admin flow.

Legacy-правило:

- старые строки без фактической суммы продажи показывают `нет точных данных`;
- оценка по текущей retail policy допустима только с явной меткой `≈ оценка`, не входит в
  итог точной прибыли;
- корреляция старого `DirectIntent` и `WbOrder` по времени/нику не считается надёжным
  backfill без отдельного ручного аудита.

Trello: [точная прибыль](https://trello.com/c/7JkJoozU).

### 6. Компактный слив остатка

Большая постоянная секция `DrainSection` убирается из основного потока. В дашборде Аккаунта
остаётся одна строка:

`Слив остатка · <аккаунт-приёмник> · <баланс> · последний <сумма/дата>`.

По тапу раскрываются:

- текущая сумма к сливу и кнопка `Слить`;
- обновление балансов;
- `Cookie приёмника`;
- вложенная редкая настройка выбора gamepass.

Существующие price/ownership checks, подтверждение, immediate balance update и `DrainEvent`
сохраняются без изменений. Закрытый блок занимает одну строку; смена cookie доступна максимум
за два тапа.

Trello: [компактный слив](https://trello.com/c/vyYCdIks).

## Этап 2 — Premium Calm для «Аккаунта» и «Заказов»

Дата концепт-ревью и реализации: 14.07.2026. Статус: **реализовано и принято запросом
владельца по финальному визуальному референсу; готово к production после общего release gate**.

Production-проверка на iPhone viewport `430×932` показала, что текущий Liquid Glass baseline
работает, но два самых операционных экрана всё ещё выглядят плотнее Главной:

- в `Аккаунте` hero, четыре равноправные плитки, поиск и большой блок очереди конкурируют за
  первый экран; ключевое состояние «донор пуст, 11 заказов ждут 16 292 R$» распадается на
  несколько областей;
- в `Заказах` одновременно видны девять status-chips, четыре summary-card и отдельные
  карточки каждой строки. Данные полезны, но иерархия больше похожа на мониторинг, чем на
  спокойный iOS work queue;
- главный premium-эффект должен появиться не от дополнительного blur, а от удаления
  визуального шума, более строгой типографики и единственного акцентного слоя на экран.

### Дизайн-принципы Premium Calm

- почти чёрный graphite canvas, один холодный ultraviolet accent и системные semantic colors;
- один glass hero на экран; повторяющиеся сущности — inset grouped rows с hairline-разделителями,
  без отдельной тени и blur на каждой строке;
- числа и рабочий статус имеют приоритет над декоративными подписями; emoji в основном UI
  заменяются на единый набор outline-иконок;
- навигационный title `30–34 pt`, primary `17 pt`, secondary `13–15 pt`, touch target `44 pt`;

### Хотфикс 14.07.2026 — «мёртвый» /twa после деплоя

Симптом на устройстве владельца после выпуска Premium Calm: TWA открывался как скелет без

- `/twa` переведён на `force-dynamic`: HTML рендерится на каждый запрос и всегда указывает

- Инлайн-скрипт страницы самолечит уже розданный протухший HTML: `ChunkLoadError`/failed
  dynamic import → одна автоперезагрузка не чаще раза в 60 с.
- `ready()+expand()` гарантированы после реальной загрузки Telegram SDK (поллинг до 6 с):
  путь с сохранённым JWT раньше их пропускал, и на iOS viewport оставался неразвёрнутым —

### Подтверждённые UX-баги и локальный хотфикс

#### Детали визуально появляются «за карточкой»

Технически detail уже рендерится порталом в `document.body`, но его компактная шапка была
`position: sticky` внутри того же scroll-container. При прокрутке шапка постоянно лежала над
деталями и создавала эффект, будто содержимое уходит за исходную карточку.

Хотфикс:

- шапка больше не sticky и участвует в обычном потоке sheet;
- добавлен системный grabber, визуально объясняющий слой и направление закрытия;
- фон ленты остаётся под отдельным backdrop, а вся информация живёт внутри одного
  foreground-container;
- ограничения высоты, portal, safe-area, backdrop-close и сохранение scroll position ленты
  не меняются.

В этом же выпуске реализован единый `BottomSheet` shell с тремя зонами
`handle / scrollable content / pinned primary action`, focus trap, Escape/BackButton и
опциональным переходом `72% → full` только для длинного досье.

#### «История» в Аккаунте выглядит неактивной

Причина: строка меняла `showTxHistory`, но история находится ниже поиска, очереди и слива;
экран оставался на прежней позиции, поэтому видимого результата не было.

Хотфикс: `История` теперь идемпотентно раскрывает блок, сразу переводит к skeleton секции,
а после асинхронной загрузки центрирует первую операцию через `scrollIntoView`. Повторный тап
по строке hero не закрывает уже открытую историю и не оставляет пользователя наверху;
свернуть её можно в самой секции.

### Главная: что показывать вместо «Выручка сегодня»

`Выручка сегодня` не помогает принять ближайшее операционное решение и удаляется из первого
экрана. Денежная аналитика остаётся в соответствующем drill-down, но не занимает hero.

#### Вариант A — «Фокус действий» (рекомендуется)

Иерархия первого экрана:

1. глобальный search-field;
2. hero `Требует действия`: общее число, возраст самого старого, три сегмента
   `К выкупу / Ждут ссылку / Ошибки`;
3. оснащённый inset-group `Сейчас`:
   - `Выкупить N заказов` + требуемые R$ и покрытие донором;
   - `Запросить N ссылок` + доступность каналов клиента;
   - `Исправить N ошибок` + первая конкретная причина;
   - `Ответить N клиентам` + вопросы/отзывы;
4. две вторичные команды: `Новый заказ` и `Обновить данные`.

Плюсы: отвечает на вопрос «что делать сейчас», переиспользует существующие рабочие очереди,
не требует читать график и хорошо деградирует до empty-state `Срочных действий нет`.
Минус: для честного donor coverage и client inbox нужна компактная агрегация в dashboard API.

#### Вариант B — «Поток смены»

Hero показывает `обработано / входящий объём`, health-ring и четыре ступени
`Новые → Ссылки → Выкуп → Ошибка`. Ниже — ближайшие исключения и ресурс донора.

Плюсы: лучше объясняет темп смены и узкое место процесса. Минусы: менее очевидно главное
действие; ring и pipeline сложнее интерпретировать ночью с телефона; повышается риск снова
получить «дашборд ради дашборда». Рекомендуется только если владелец ежедневно управляет
сменой по throughput, а не лично обрабатывает очередь.

#### Вариант C — «Search first» (резерв)

Поиск занимает hero, ниже остаются только три smart-shortcut. Подходит, если основной сценарий
TWA — найти конкретный заказ по сообщению клиента. Не рекомендуется как baseline: теряется
проактивное предупреждение о старых/ошибочных заказах.

### Оснащённый виджет «Сейчас»

Каждая строка имеет одинаковый контракт:

| Поле | Смысл |
|---|---|
| Иконка и semantic color | тип действия, не декоративная категория |
| Заголовок-глагол | `Выкупить`, `Запросить`, `Исправить`, `Ответить` |
| Число | объём работы прямо сейчас |
| Подстрока | причина, ресурс или ограничение |
| Тап | сразу открывает соответствующий рабочий фильтр |

Запрещено: смешивать в `Сейчас` пассивную недельную аналитику, показывать `donor balance` как
английскую заглушку, делать четыре независимые glass-card и красить строку целиком.

### Умный поиск v2

Текущий API уже объединяет заказы и live gamepasses, но выдаче не хватает языка единой
экосистемы. Новый UI-контракт:

- поиск открывается в спокойном focus-state без перестройки всей Главной;
- сверху filter chips `Все / Заказы / Геймпассы` с реальными counts;
- каждая группа объясняет **почему найдено**: `по коду`, `по нику`, `по клиенту`,
  `по gamepass ID`;
- order-row: source/status, ник + R$, клиент + код, warning только при действительной проблеме;
- live-row: название/цена, seller, sale-state, freshness и явная метка `live`;
- выбор заказа сначала показывает компактный preview и primary action `Открыть заказ`, а
  полное досье открывается в том же sheet-shell без встраивания большой карточки в выдачу;
- partial failure показывается на уровне группы и не превращает найденные DB-заказы в error;
- старые ответы отбрасываются, запрос отменяется, клавиатура не закрывает preview, после
  возврата сохраняются query, chips и позиция выдачи.

Поиск по Roblox-нику остаётся вероятностным: он не объединяет identities и не помечает
заказ подтверждённым. Чувствительные поля и секреты не добавляются.

| Уровень | Целевой размер |
|---|---:|
| Ключевое число/hero | `46 px` |
| Заголовок экрана | `29 px` |
| Заголовок секции | `31 px` |
| Основная строка/название | `23 px` |
| Значение справа | `21–25 px` |
| Вторичная строка | `16–18 px` |
| Badge/status | `14–16 px`, ниже `14 px` запрещено |

Секции разделяются не только размером шрифта: у заголовка есть вертикальный ultraviolet
marker, увеличенный отступ сверху; inset-group получает более выраженный hairline и отдельный
elevation. Карточки получают высоту `92–98 px`, действия — не меньше `56 px`. Кнопки снова
компонуются по две в ряд там, где подписи помещаются без обрезания; три hero-метрики также
возвращены в одну строку. Длинные
значения переносятся, а не обрезаются ellipsis. Ради читаемости первый экран больше не обязан
показывать четыре строки целиком: контент и длинное досье прокручиваются, но search, hero и
начало `Сейчас` должны без двусмысленности задавать структуру.

### Критерии готовности

- детали никогда не оказываются под исходной строкой, sticky-header или tab bar;
- после тапа `История` первый history-row виден без ручного скролла;
- Главная за один взгляд показывает количество, приоритет и ближайшее действие;
- ни одна цифра в hero/`Сейчас` не является декоративной или несвязанной с deeplink;
- поиск визуально различает DB и live, объясняет совпадение и переживает partial failure;
- business actions, confirmations и серверные guards остаются прежними;
- на `390×844` search, hero и начало секции `Сейчас` читаются без наложений; остальные
  строки доступны естественным вертикальным скроллом и не ужимаются ради первого кадра.
