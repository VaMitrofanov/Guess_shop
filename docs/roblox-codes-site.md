### Как включить продажу (чек-лист)

1. **Ключ склада.** Сгенерировать 32 байта (`openssl rand -hex 32`), положить в Coolify Web как
   `ACTIVATION_CODE_ENCRYPTION_KEY` и в `HANDOFF.md`. Тот же ключ нужен там, где запускают загрузку
   кодов. Потеря ключа = потеря всех кодов склада.
2. **Оферта и чек.** Решить с бухгалтером/юристом предмет расчёта для кода (сейчас в чеке
   «Цифровая услуга по заказу», как у геймпасса) и текст о возврате после выдачи кода.
3. **Коды на склад.** `node --import tsx scripts/codes-import.ts <файл> <номинал> [метка]`,
   файл после загрузки удалить.
4. **Флаг.** `CODES_SALES_ENABLED=true` в Coolify Web (нужен рестарт контейнера, пересборка — нет:
   флаг серверный). `SITE_ACQUIRING_ENABLED` уже включён.
5. **Живая проверка.** Одна покупка тестовой картой на тестовом терминале или минимальная
   настоящая (100 R$) с возвратом; проверить письмо и кабинет.
6. **Объявить.** В теме «Апдейты» нажать «📣 Опубликовать в канал и ВК» под постом про коды.

## Три отдельных процесса

| Процесс | Где | Что не трогали |
|---|---|---|
| Новый код на сайте | блок `#codes` на главной → `/pay/<токен>` → письмо/кабинет | — |
| Оплаченная карточка WB | `/guide?source=wb` (кнопка «Ввести код» в первом экране и ссылка внизу блока кодов) | весь коридор WB |
| Геймпасс | калькулятор → `/checkout` | заказы, оплата, выкуп |

Активация кода — на `https://www.roblox.com/redeem` самим покупателем. Выдача кода магазином ≠
активация: интерфейс и письма это проговаривают.

**Округление (владелец, 14.11.2026):** копеек в цене нет. Сумма после скидки округляется ВВЕРХ до
рубля, кроме случая, когда рубли уже кончаются на 9 — тогда копейки просто отбрасываются, чтобы не
ломать «…9»: 3 999,03 → 3 999, 3 542,04 → 3 543 (`roundCodePriceKopecks`).

Сумму считает только сервер (`quoteCode`), в копейках, всегда целый рубль.
Номинал, база, процент, скидка и итог фиксируются в `CodeOrder` при создании и больше молча не
меняются; после истечения предложения (24 ч) нужна явная кнопка «Подтвердить за N ₽».

## Скидка за приглашения

1 % сразу после регистрации; 3 / 10 / 20 / 30 засчитанных покупателей → 2 / 3 / 4 / 5 %. Уровни
заменяют друг друга. Засчитан = аккаунт, привязанный по ссылке `/r/<код>` (подписанная кука
`rb_ref`, 30 дней; привязка один раз и только НОВОМУ аккаунту), у которого есть выданный и не
возвращённый заказ кода, оплаченный после привязки. Счётчик не хранится — считается запросом
(`countQualifiedInvites`), поэтому повторный webhook не добавляет, а возврат сам убирает.
На витрине крупно — номинал Robux, цена вторым планом; пакет с самой низкой ценой за 1 R$
среди доступных помечен «Выгоднее всего» с ценой за 1 R$ (цифра из той же цены).
Создатель заказа = тот, кто оформил; родитель, оплативший по ссылке, на счёт не влияет и
аккаунт по его email не создаётся. Программа только для кодов.

## Данные (миграция `20261114_activation_codes_store`, аддитивная)

- `CodeOrder` — заказ: `publicId` (`CODE-XXXXXXXX`), суммы, создатель или `recipientEmail`
  гостя, `payTokenHash`, статус `AWAITING_PAYMENT → PAYMENT_PENDING → ISSUED` (или `PAID` при
  пустом складе, `REFUNDED`), срок предложения, отметки письма и показа кода.
- `CodePayment` — попытка оплаты, OrderId у банка `CODE-…-N`, свой email для чека.
- `ActivationCode` — склад: значение только в AES-256-GCM (`ACTIVATION_CODE_ENCRYPTION_KEY`),
  дубли по HMAC; `IN_STOCK → RESERVED (2 ч) → ISSUED`.
- `CodeOrderEvent` — журнал с ключами идемпотентности.
- `User.referralCode / referredById / referredAt`.

Почему не `WbOrder`: там `PENDING` — очередь выкупа геймпасса, оплаченный код попал бы в очереди
админов и ботов.

## Поток денег

1. «Оплатить» → резерв кода (`FOR UPDATE SKIP LOCKED`) → `Init` Т-Банка (тот же терминал, чек
   и классификаторы не менялись) → банк.
2. `/api/webhooks/tinkoff`: подпись и терминал как раньше; `OrderId` с `CODE-` уходит в
   `handleCodePaymentNotification` — сверка PaymentId, суммы, валюты, перехода статуса; код
   выдаётся в той же транзакции, что фиксирует оплату. Возврат браузера ничего не подтверждает.
3. После коммита — письмо (`sendCodeEmail`). Упало — заказ остаётся `ISSUED`, ошибка в
   `emailLastError`, кнопка «Отправить письмо ещё раз» шлёт тот же код.
4. Нет кода после оплаты / второй платёж по оплаченному заказу → пуш в «Уведы» (тема «Нужно
   действие»), деньги — ручной возврат.

Время в сырых SQL склада — только параметром из приложения (не `NOW()`): колонки без пояса,
Prisma пишет UTC. Сквозной тест поймал, что при поясе сессии ≠ UTC последний код уходил двоим.

## API

`GET /api/codes/catalog` · `POST /api/codes/orders` (`self` | `share`) · `POST /api/codes/pay` ·
`POST /api/codes/status` · `POST /api/codes/refresh` · `POST /api/codes/resend` ·
`POST /api/codes/reveal` (только создатель, по сессии) · `GET /r/<код>`. Токен ссылки — всегда в
теле запроса, кроме самого адреса страницы `/pay/<токен>`.

## Склад

```
node --import tsx scripts/codes-import.ts <файл> <номинал> [метка] [--dry-run]
```

Файл — по коду в строке; скрипт печатает только счётчики, дубли отсекает. Файл после загрузки
удалить. Интерфейса склада в TWA пока нет (этап K5 плана).

## Проверки перед выкатом (14.11.2026)

Локальная Postgres + подставной Т-Банк и SMTP, продовая сборка: 51 сквозной сценарий (оплата,
повторный webhook, подмена суммы/подписи, гонка за последний код, просрочка, ошибка банка,
сбой письма и повторная отправка, рефералы и возвраты, чужой код), матрица 47 «номинал × скидка»
до суммы в банке, 23 визуальные проверки (360/390/768/1440, обе темы, клавиатура). Найдено и
исправлено: время резерва в SQL зависело от пояса сессии БД (последний код уходил двоим).
