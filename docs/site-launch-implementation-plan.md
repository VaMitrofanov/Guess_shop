# План подготовки сайта к боевому запуску

**Дата решения:** 18.07.2026
**Статус:** выполняется; боевой эквайринг выключен до завершения этапов A–F и отдельного
решения владельца на контрольную оплату.
**Продуктовая граница:** юридический повторный аудит и перенос БД в РФ в эту итерацию
не входят по решению владельца. Это решение не означает, что технические риски этих
пунктов исчезли; оно только исключает их из текущего графика.

## 1. Что уже зафиксировано

- Создан и проверен восстановимый baseline dump production-БД; файл хранится локально в
  игнорируемом `data/backups/`, контрольная SHA-256 записана только в `HANDOFF.md`.
- Контрольный снимок без ПД: `526 User`, `551 WbOrder`, `5 PriceQuote`, платёжных попыток,
  возвратов, событий и outbox-записей пока `0`; `BonusLedger` — `50` строк / `4900 R$`,
  суммарный cached balance — `5800 R$`.
- В production установлен `SITE_ACQUIRING_ENABLED=false`, пересборка завершилась успешно;
  health отвечает `200`, публичный acquiring status — `enabled:false`.
- Рабочие credentials Т‑Банка получены владельцем, но в Web пока не вставляются: сначала
  закрывается текущий план и проводится приёмка ЛК/checkout без движения денег.

## 2. Согласованные правила продукта

1. Гость может рассчитать сумму, найти Roblox-ник, увидеть и выбрать геймпасс и цену.
2. Перед созданием заказа и переходом в Т‑Банк пользователь обязан войти или
   зарегистрироваться. После входа возвращается тот же draft, а сервер выпускает новую
   персональную котировку.
3. Любой заказ — SITE, WB, TG, VK или ручной — виден в одном ЛК, если identity подтверждена
   и связана с тем же `User`.
4. Сайт — контрольная поверхность заказа; бот/сообщество — подтверждённый канал identity,
   уведомлений, повторных продаж и поддержки.
5. Уже принятый платёж продолжает webhook/outbox/refund-обработку даже при экстренном
   выключении новых оплат.

## 3. Детальный план реализации

| B | Поэтапный допуск `off → allowlist → percentage → on`, server-side enforcement | 0,5 дня | **код готов, deploy после согласования** |

### B. Поэтапный допуск оплаты

- `SITE_ACQUIRING_ENABLED` остаётся master kill switch.
- `SITE_ACQUIRING_MODE=off|allowlist|percentage|on` обязателен и по умолчанию `off`.
- allowlist содержит только внутренние `User.id`, не email/телефон/социальные ID.
- percentage использует стабильный SHA-256 bucket по `User.id`; перезапуск не меняет группу.
- `/api/acquiring/status` возвращает только публичные `off|limited|on`, не раскрывает список.
- `POST /api/orders/create` повторяет auth+eligibility независимо от UI.
- webhook, refund и outbox не читают rollout gate.

Stop conditions: расхождение суммы/заказа, неизвестный webhook, dead-letter, неотправленный
чек, двойная операция, рост 5xx/Init failure или заказ без понятного статуса. При срабатывании
— `SITE_ACQUIRING_ENABLED=false`, новые Init прекращаются, принятые операции завершаются.

### C. Регистрация строго перед оплатой

- Draft переносит только несекретные поля `amount`, `username`, `gamepassId`.
- `next` принимается только как безопасный same-origin path; `//`, external URL, backslash,
  control chars и `/admin` отбрасываются.
- Email, TG и VK login возвращают пользователя в draft; Telegram хранит return path только
  в `sessionStorage`, одноразовый auth challenge остаётся серверным.
- Гостевая quote не оплачивается. После входа создаётся новая quote, учитывающая актуальные
  бонус/скидку и принадлежащая текущему `User`.
- Сервер без сессии всегда отвечает `401`, даже если клиентский код был обойдён.

### D. ЛК «как на взрослом сайте»

Уже есть: общий action-center, SITE/WB/DIRECT/AVITO/MANUAL history, bonus balance,
verified identities, payment/receipt/refund snapshot, logout и safe order links. В текущем
batch добавлена верхняя карточка активного заказа с этапами `Оплата → Очередь → Выкуп →
Готово` и явным следующим действием.

До публичного `100% on` остаётся:

1. Email verification, повторная отправка и password reset с одноразовыми hash-токенами.
2. Evidence согласия: версия политики, timestamp, минимизированный IP/audit record.
3. Проверка живых TG/VK login/link на реальных аккаунтах и безопасный merge-конфликт.
4. Пагинация истории после 50 заказов и отдельный detail URL для WB-заказа без public id.
5. Refund timeline и причина отклонения в customer-safe формулировке.
6. Набор E2E: пустой/1/50+ заказов, длинные значения, expired session, offline и повторный вход.

Email lifecycle зависит от рабочего SMTP/DNS из `email-setup.md`. До него email-регистрация
может использоваться только как ограниченный способ входа; забытый пароль восстановить
невозможно. TG/VK остаются альтернативными подтверждёнными каналами.

### F. Матрица дизайн-приёмки

- Маршруты: `/`, calculator, `/checkout` guest/auth/disabled/limited, `/login`, `/register`,
  `/dashboard` 0/1/50 заказов, `/payment/status` waiting/paid/work/completed/error/offline,
  `/guide` SITE/WB/TG/VK, FAQ/reviews/guarantees/legal.

## 4. WB-выдача на сайте без потери аудитории

### Рекомендуемая модель

**Channel binding обязателен, подписка на публичную группу — не блок выдачи уже купленного
на WB товара.** Блокировать оплаченную выдачу требованием подписки рискованно и создаёт
поддержку/возвраты. Нужная аккумуляция достигается тем, что клиент обязательно начинает
диалог с TG- или VK-ботом и связывает identity; подписку на канал/сообщество проверяем и
поощряем бонусом, но не удерживаем сам номинал.

Целевой поток:

1. Клиент вводит WB-код на сайте; код только резервируется на 15 минут, не считается
   использованным и не материализует заказ.
2. Сайт предлагает выбрать Telegram или VK и выдаёт одноразовый opaque handoff state.
3. Клиент нажимает Start/Начать в боте. Бот подтверждает платформенный user id, связывает
   `UserIdentity` и возвращает signed callback на сайт.
4. В боте показываются: ссылка на группу/канал, проверка подписки и бонус за подписку;
   вся важная операционная информация и поддержка остаются в диалоге.
5. После подтверждения канала сайт открывает поиск ника/геймпасса, сохраняет выбор и создаёт
   обычный `WbOrder` с тем же `User` и `orderSource=WB`.
6. Статус синхронно виден в ЛК и боте; изменения идут через текущий outbox/notification
   механизм. Повторная покупка ведёт в прямой заказ бота или site checkout того же профиля.
7. Если callback потерян, резерв можно безопасно продолжить из ЛК или бот-команды; TTL
   освобождает незавершённый код без двойного использования.

### Реализация G1–G5

| Подэтап | Изменение | DoD |
|---|---|---|
| G1 | Продуктовые события `code_reserved`, `channel_chosen`, `bot_started`, `identity_bound`, `subscription_checked`, `order_created` | виден funnel и drop-off |
| G2 | Одноразовый handoff challenge: hash в БД, TTL, consume-once, привязка к reservation/user | raw WB code не является auth state |
| G3 | TG `getChatMember` / VK membership check при достаточных правах бота | результат проверяется сервером, отказ не блокирует номинал |
| G4 | Материализация `WbOrder` только после identity binding; idempotency на code+user | повтор callback не создаёт второй заказ |
| G5 | ЛК + bot notifications + recovery + desktop/mobile/WebView E2E | один статус во всех каналах |

Ключевые метрики: доля `code_reserved → identity_bound`, доля начавших диалог, подписка,
успешное создание заказа, среднее время до gamepass, повторная прямая покупка за 30 дней,
support rate. Для rollout сначала тестовые коды, затем 5% новых WB-кодов, 25%, 100%.

## 5. Боевой E2E и включение

Production credentials вставляются напрямую в secret env, не в git/чат. Затем:

1. `MODE=allowlist`, allowlist — отдельный USER владельца/команды, master flag ещё `false`.
2. Deploy и smoke подтверждают `enabled:false`; затем master `true` и один redeploy.
3. Создать минимальный реальный заказ из guest draft через login; сверить quote/order/amount.
4. Пройти Т‑Банк, дождаться подписанного webhook `CONFIRMED`, статуса `PENDING`, event и
   outbox delivery; проверить ЛК, status page и чек.
5. Выполнить контролируемый полный возврат; сверить `REFUNDED`, сумму, чек возврата, ЛК и
   отсутствие повторной доставки.
6. Отдельно проверить decline/cancel и retry с новым idempotency key.
7. Только после reconciliation — 10%, 50%, 100%. Между ступенями минимум один рабочий день
   без stop condition.

## 6. Definition of Done запуска

- Пользователь не может создать оплату без аккаунта или вне rollout group.
- Сумма checkout, Init, webhook, БД, чек и возврат совпадают в копейках.
- В ЛК и status page понятны текущий этап, следующий шаг, чек и возврат.
- WB-клиент связан с TG/VK identity до создания заказа и получает уведомления; funnel виден.
- Все client routes приняты на desktop/mobile/WebView, smoke и automated gate зелёные.
- Есть проверенный rollback: master off останавливает новые Init, не ломая уже принятые деньги.
