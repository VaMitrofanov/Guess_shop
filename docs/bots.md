# Боты (Telegram + VK)

Оба бота — отдельные процессы. Воркфлоу идентичен. VK шлёт уведомления менеджерам через
Telegram (`bots/shared/notify.ts` → `tgSend` → `ADMIN_IDS`).

Payment-worker watchdog работает в независимом VK-процессе: durable heartbeat/outbox и
`lastAlertAt` атомарно дедуплицируют stop/recovery alerts. Если Telegram/SG bridge не
подтвердил отправку, VK вызывает защищённый Web endpoint, который пишет подтверждённому
владельцу по email. `lastAlertAt` сохраняется только после успеха хотя бы одного канала.

## WB DBS-контур (реализован 11.08.2026, controlled rollout)

Только что завершённый заказ с доставкой продавцом виден WB API как `deliveryType=dbs`, а
событие buyer chat однозначно связывается с ним по `goodCard.rid = order.rid`. Текущий
`bots/tg/admin/wb-client.ts` и 15-минутный hub-monitor читают только FBS и не могут быть
источником правды для DBS: новый заказ надо сохранить из `/api/v3/dbs/orders/new` до его
перехода в следующий статус.

`bots/shared/wb-delivery-sync.ts` каждые 5 секунд синхронизирует новые DBS и buyer-chat,
держит DB lease/cursor/heartbeat, раз в минуту сверяет чат и статусы, раз в пять минут —
завершённые заказы. Сопоставление только по `rid`; сообщения и delivery code дедуплицируются.
`WB_DBS_SYNC_ENABLED=true` включает только чтение: worker никогда сам не отправляет сообщение
и не меняет статус WB. Эти операции принадлежат общей TWA/web-admin службе и требуют
отдельных `WB_CHAT_SEND_ENABLED`/`WB_DBS_MUTATIONS_ENABLED`.

TG/VK не получают отдельную развилку fulfillment: после
серверной выдачи generated `WbCode` покупатель проходит существующий flow активации, выбора
канала, инструкции и отправки ника/геймпасса. Автоматическая отправка сообщения и
автоматический `receive` запрещены. Синтетический `isTest`-заказ проходит весь операторский
flow локально и не вызывает WB mutations.

Полный API-контракт, state machine, privacy-границы и этапы:
[wb-dbs-delivery-plan.md](wb-dbs-delivery-plan.md).

Provider-поля-массивы нормализуют `null`/отсутствие в `[]`: первый production shadow-run
подтвердил, что успешный `status/info` WB фактически возвращает `errors: null`.
Любая запись официального completed-feed помечается terminal даже при отсутствии
`supplierStatus`/`wbStatus`, поэтому завершённый заказ не остаётся в активной очереди.

## Аварийное объявление о недоступности выкупа

Одноразовая рассылка запускается скриптом `scripts/broadcast-roblox-maintenance.mjs`.
Он публикует согласованный текст в Telegram-канале и на стене VK-сообщества, затем
отправляет его пользователям с незавершёнными реальными `WbOrder` (тестовые,
завершённые и отклонённые заказы исключаются). Перед запуском доступен режим
`--dry-run`, который только показывает размер аудитории.

Последняя рассылка 17.07.2026: публикация в оба сообщества успешна. Для пользователей
без ожидания геймпасса отправлено 10 Telegram-уведомлений (10 доставлено). Для группы
`AWAITING_GAMEPASS` отправлено 24 Telegram-уведомления (23 доставлено) и 22 VK-
уведомления (14 доставлено). Недоставленные сообщения не помечаются как доставленные

## Анонс запуска сайта

Финальный текст презентации `robloxbank.ru` хранится в
`scripts/broadcast-site-launch.mjs`. Без параметров скрипт только печатает Telegram- и
VK-версии и ничего не отправляет. Живая публикация требует явного `--publish`, всех четырёх
channel credentials и успешного публичного preflight: `/api/acquiring/status` обязан вернуть
`mode=on`, `available=true`. Поэтому анонс невозможно случайно отправить, пока checkout
остаётся в `off`, `allowlist` или `percentage`. Скрипт публикует только в Telegram-канал и
VK-сообщество; массовых личных сообщений клиентам не делает.

Перед `--publish` обязательны ротация раскрытого Password рабочего terminal, redeploy,
production smoke и проверка одной новой оплаты на уже ротированном секрете. Сам текст честно
описывает сервис покупки Robux через геймпассы и отдельно указывает, что RobloxBank не
является банком и не связан с Roblox Corporation.

## Общее

- **Профиль и identity (29.07.2026):** после успешно обработанного входящего события оба
  бота асинхронно синхронизируют пользователя через `bots/shared/user-profile-sync.ts`.
  ID берётся из actor поля самого Telegram/VK update, а не из текста клиента, поэтому можно
  безопасно создать/обновить `UserIdentity` без эвристического merge. Legacy `tgId`/`vkId`
  сохраняются для текущих order/notify-путей. Конфликт, где identity и legacy ID принадлежат
  разным `User`, fail-closed и не склеивается автоматически.
- Telegram сохраняет имя, фамилию, username и ограниченные provider metadata из `ctx.from`.
  VK вызывает официальный `users.get` v5.199 и сохраняет имя, `screen_name`, `photo_100`,
  closed/deactivated state. Синхронизация троттлится на 6 часов в памяти процесса и идёт
  после основной обработки сообщения, поэтому профильный API не задерживает ответ бота.
  Ошибка VK API даёт `null` и сохраняет прежние данные — фиктивный `VK #id` больше не
  записывается как профиль. Provider-specific handle хранится в metadata identity, поэтому
  у связанного TG+VK профиля один канал не перетирает другой.
- SG bridge `/tg-proxy` возвращает payload `result` только для read-only
  `getChat`/`getChatMemberCount`. Это позволяет RF Web показывать живой размер Telegram-
  канала, не имея прямого маршрута к `api.telegram.org` и не передавая токен бота через
  межсерверный запрос; доступ по-прежнему требует `VALIDATOR_KEY`. Для send-методов контракт
  остаётся минимальным `{ok:true}`.

- **Единая нить заказа (02.09.2026).** Все сообщения об одном DBS-заказе несут одну и ту же
  шапку `orderRef()` (`WB #… · КОД · сумма · покупатель`) и уходят `reply_to_message_id` на
  живую карточку DBS — Telegram рисует цитату, и три сообщения перестают читаться как три
  разных дела. Вход покупателя на сайт для DBS-заказа больше не отдельная карточка, а строка
  таймлайна `вошёл на сайт (VK)` (`noteDbsBuyerSignedIn`). Детали —
  [wb-dbs-delivery-plan.md](wb-dbs-delivery-plan.md#один-заказ--одна-нить-02092026).
- `bots/shared/admin.ts` — карточки заказов/отзывов, объект `CB` со всеми `callback_data`.
  **Идентификатор в карточках и сообщениях — код заказа** (ВБ / `DIR-…` / `AV-…`), внутренние
  номера `#SHORTID` убраны везде (решение владельца, вариант C2, 2026-07-03). Клиент видит
  код ВБ или «заказ на N R$»; заявки (intents) кода не имеют — идентифицируются `ник · сумма`.
  TWA-диплинк из карточек — `?q=<код>`.
- `ADMIN_IDS` нормализуется через `Set`: пустые и повторяющиеся chat ID отбрасываются до
  fan-out. То же правило действует в web-уведомителях, auth-уведомлениях и payment outbox;
  повтор одного ID в env больше не создаёт две одинаковые карточки. Идемпотентность одной
  заявки по-прежнему обеспечивается status-guard транзакции (см. приём геймпасса ниже).
- Новая и перерисованная админ-карточка готового к выкупу заказа показывает
  `⏳ Возраст заказа` от исходного `WbOrder.createdAt`: 🟢 <1 суток, 🟡 1–2 дня,
  🟠 3–6 дней, 🔴 ≥7 дней (`· недельный`; ≥14 — `· старше 2 недель`). Это относится к
  TG/VK submit, one-tap с сайта, refresh/search-карточке и legacy admin hub.
- `bots/shared/nick.ts` — `noteProbableNick`: ранний захват ника Roblox в `adminNote`
  заказа (`[НИК? дата] ник (источник)`), веб-зеркало — `src/lib/capture-nick.ts`. Вероятный
  ник **не** пишется в `robloxUsername` (юзер мог опечататься) — основное поле заполняют
  только подтверждённые пути (успешная валидация геймпасса, one-tap, менеджер).
- `bots/shared/roblox.ts` — валидация геймпасса. Богаче, чем `src/lib/roblox.ts`: возвращает
  `validationSkipped`, `isNotInCatalog`, `isGamePrivate`, `isAgeRestricted`, managed-pricing.
- `bots/shared/gamepass-search.ts` — `searchGamepassesByNick` → union `user_not_found /
  no_gamepasses / ok`. Поиск: до 150 публичных игр (cursor-pagination, limit=50 × 3 стр),
  до 100 геймпассов на игру. Фильтр `isForSale !== false` (не strict `=== true`).
  **Ходит не напрямую, а через `searchGamepassesByNickRouted`** (мост первым, прямой путь
  фолбэком): с российского хоста API-хосты Roblox недостижимы по TCP, и прямой вызов там
  означал ~90 с ожидания и ответ `user_not_found` про существующий аккаунт. Это касалось
  **ВК-бота** (он на RF); ТГ-бот на SG не ломался, и расхождение двух ботов — сигнал искать
  сеть, а не код. После перевода на мост оба отвечают за ~1 с —
  см. [corridor-and-site.md](corridor-and-site.md#roblox-недоступен-с-российского-хоста--весь-поиск-идёт-через-мост-28082026).
- Сессии — **in-memory** (`session.ts`): `pendingLink`, `pendingRobloxNick`,
  `pendingDirectFlow`, `pendingNickEdit`, `pendingReview`, `pendingPaymentScreenshot` и т.д.
  После рестарта восстанавливаются из БД (см. ниже).

## TG-бот — `bots/tg/handlers.ts`

Регистрация: `registerStart`, `registerStatus`, `registerText`, `registerPhoto`,
`registerAdmin`, `registerCallbacks`, `registerChatMember` + admin-хабы (`admin/index.ts`).

### `answerCallbackQuery` — ранний ответ (2026-07-13)

`registerCallbacks` первым делом вызывает `ctx.answerCbQuery().catch(() => {})` — до
любых БД-запросов и Roblox API. Это снимает спиннер Telegram с кнопки немедленно;
без раннего ответа тяжёлые операции (выкуп, sync, поиск) заставляли кнопку крутиться
десятки секунд и давали клиенту «query is too old». Все последующие `answerCbQuery`
вызовы тоже обёрнуты в `.catch(() => {})` — повторный ответ Telegram молча отбрасывает.

### Активация (`bot.start`)
- Парсит `wbg_`/`wb_` payload (код + sessionId + guide-флаг).
- Rate-limit: 5 стартов / мин на sessionId|tgId; дедуп дубля iOS-deep-link (`recentCodeStarts`).
- Без кода → приветствие по статусу клиента: активный `AWAITING_GAMEPASS` → персональная
  инструкция; активный заказ → статус; вернувшийся → апселл прямых заказов; новый → подписка.
- С кодом → provisional TX (claim + `AWAITING_GAMEPASS`, предзаполнение `robloxUsername`
  если returning user) → админ-уведомление → гейт подписки (опц.) → инструкция или one-tap.
  Карточку «НОВЫЙ КЛИЕНТ» отправляет только транзакция, которая действительно создала
  `WbOrder`: повторный `/start`, повторная доставка update или повторное открытие deep-link
  лишь возвращают клиента к существующему заказу, без нового fan-out админам.
  Returning user с сохранённым ником видит `🎮 Ник: X` и кнопку `✅ Найти у X` (auto-search).

### Текстовый роутер (`registerText` / `bot.on("text")`)
Приоритеты: reply-keyboard кнопки → админ-режимы (reject-reason, payment-details) →
ввод ника → прямой заказ (сумма/ник) → редактирование ника → восстановление сессии из БД
(`AWAITING_GAMEPASS`) → прямой ввод WB-кода → REJECTED-заказ (resubmit) → идл.
Ник-подобный текст в активной сессии уходит в поиск по нику, а не в ошибку формата.

### Sweep стейл-стейтов (П2, 2026-07-06)

Map-стейты, привязанные к заказу (TG `pendingLink`/`pendingRobloxNick`, VK
`AWAITING_LINK`/`AWAITING_ROBLOX_NICK`), могут отстать от БД: gpw_ok, attach из
TWA или выкуп переводят заказ дальше, а стейт в памяти бота остаётся и съедает
любой текст формат-ошибкой «Напиши свой ник…» (кейс DCTAKAJ). Правила:

- **Перед обработкой** такого стейта хендлер перепроверяет статус заказа в БД
  (`sweepStaleOrderState` в TG, `sweepStaleVkOrderState` в VK): заказ уже не
  `AWAITING_GAMEPASS`/`REJECTED` → стейт чистится и юзер получает честный ответ
  по фактическому статусу («в очереди на выкуп» / «выполнен» / «ждёт оплату»).
  Валидный WB-код в тексте не глотается — уходит в штатную активацию.
- **`gpw_ok`** (оба бота) чистит все стейты юзера (заказ ушёл в очередь);
  **`gpw_no`** чистит и сразу взводит ввод ника (`AWAITING_ROBLOX_NICK` /
  `pendingRobloxNick`) — «пришли свой ник сюда» реально ведёт в ник-поиск.
- **Инвариант для новых терминальных переходов** (заказ → PENDING/COMPLETED/
  REJECTED, оплата подтверждена): чистить стейт в точке перехода, если она в
  процессе бота; переходы со стороны Web ловит sweep при следующем сообщении.

### Приём геймпасса (`processGamepassSubmission`)
`getGamepassDetails` → ветки ошибок с конкретными подсказками:
- не найден / черновик → поддержка;
- не в каталоге (закрытая игра) → как открыть Public;
- private-игра → инструкция открытия;
- не на продаже → включить On Sale;
- неверная цена → детект **Managed pricing** (частая причина) + как отключить;
- Roblox недоступен → принять `validationSkipped`, алерт админам о ручной проверке.

Финальная транзакция атомарна: claim кода (`updateMany` с OR-guard на RESERVED/null/provisional)
+ промоушен/создание `WbOrder → PENDING`. `COMPLETED` — единственный терминальный блок.

**Идемпотентность повторной отправки (фикс «двойных карточек», 2026-07-03, оба бота):**
- тот же геймпасс на заказ в `PENDING`/`IN_PROGRESS` → no-op в транзакции: без пере-PENDING,
  без второй админ-карточки; клиенту — «✅ Этот геймпасс уже принят» (кейс J2XVS0: one-tap
  с сайта + отправка того же пасса в бот минутой позже);
- **другая** ссылка на заказ в обработке (клиент передумал) → апдейт как раньше, но карточка
  идёт с маркером `🔁 ЗАМЕНА ГЕЙМПАССА (было: <passId>)` (`replacedGamepassUrl` в
  `sendAdminOrderCard`) — менеджер видит, что это не новый заказ;
- `previousOrderCount` («ПОВТОРНЫЙ КЛИЕНТ») исключает сам текущий заказ (`wbCode != текущий`)
  — раньше свежепромоутнутый сайтом заказ считал сам себя и давал ложный бейдж; тот же фикс
  в `renderExtendedCard` admin-хаба (`id != order.id`).

**Ранний захват ника** (`noteProbableNick`): при вводе ника в поиск (все ветки кроме
`user_not_found`) и в fail-ветках валидации геймпасса (`creatorName` от Roblox) ник
дописывается в `adminNote` заказа — менеджер может привязать геймпасс из TWA, не дожидаясь
клиента.

**След покупателя для спора (28.08.2026).** Заметка дедуплицируется — молчит, когда ник
совпал с подтверждённым или уже записан, — поэтому доказательства «что человек вводил» она не
даёт. Рядом с ней, но **до** дедупликации, оба бота пишут неизменяемые записи в `OrderEvent`:
`AUDIT_NICK_ENTERED` (ник, канал, знает ли Roblox такой аккаунт) и `AUDIT_GAMEPASS_SUBMITTED`
(ID пасса, владелец по данным Roblox, цена) — `bots/shared/order-audit.ts`. Вызовы
best-effort (`void`), пользовательский поток они не роняют. Чтение — блок «След покупателя» в
карточке TWA и `node scripts/order-audit-trail.mjs <КОД>`; подробности — [twa-admin.md](twa-admin.md).

**Ссылка на геймпасс — запасной вход, когда поиск по нику молчит (24.08.2026, оба бота).**
Поиск живёт на публичных списках Roblox (`resolveRobloxUserId` + `listForSaleGamepasses`
с `accessFilter=Public`), и они регулярно отдают пусто при живом геймпассе: скрытый плейс
(треть застрявших активаций по разбору 22.08), только что созданный пасс, лаг API. Ссылку
на свой геймпасс покупатель при этом видит в браузере. Бот принимал такую ссылку всегда —
но НИ НА ОДНОЙ тупиковой ветке об этом не говорил, а в режиме ввода ника отвечал на неё
«⚠️ Ник не похож на ник Roblox». Человек упирался в «пройди инструкцию ещё раз» и уходил;
на DBS это стоит дороже всего — там счёт идёт на часы.

Что изменилось:
- ветки `user_not_found`, `no_gamepasses`, «не та цена» и инфра-сбой поиска получили кнопку
  **«🔗 Прислать ссылку на геймпасс»** (TG `CB.sendGpLink`, VK payload `send_gp_link`).
  Она ставит `pendingLink` / `AWAITING_LINK` и объясняет, где взять ссылку;
- ссылка, присланная **вместо ника**, больше не формат-ошибка: `handleRobloxNickInput` в
  обоих ботах сначала пробует `extractPassId` и уводит текст в
  `processGamepassSubmission` / `handleGamepassLink`;
- текст ветки `no_gamepasses` теперь разделяет два разных случая — «геймпасс уже создан,
  но поиск его не видит» (→ ссылка) и «ещё не создан» (→ инструкция);
- заказ, оформленный этим путём, доезжает до менеджера как обычно, но карточка несёт маркер
  **`🔗 ССЫЛКА ВРУЧНУЮ`** (`OrderCardPayload.viaManualLink`): у такого заказа плейс почти
  наверняка скрыт, и выкуп стоит глянуть глазами. Маркер ставится только когда покупателя
  привёл сюда провалившийся поиск (кнопка или ссылка вместо ника) — обычная отправка ссылки
  с первого шага остаётся немаркированной;
- разбор ссылки у сайта и обоих ботов теперь один — `bots/shared/gamepass-id.ts`
  (`parseGamepassRef`), зеркало `src/lib/gamepass-id.ts`. Понимает `game-pass/`,
  `game-passes/`, `game_pass/`, `passes/` (Creator Hub), query/hash в хвосте и голый ID.
  Голый ID принимает только `parseGamepassRef` — в поле поиска по нику число обязано
  остаться ником (`NICK_RE` их допускает), поэтому там работает `parseGamepassUrl`.

**«Уже сделал/исправил — проверить» перепроверяет ПРЕЖНИЙ ник (2026-07-05, оба бота).**
Кнопки ретрая в ветках `no_gamepasses` / «не та цена» (TG `CB.findGpRetry`, VK payload

### Прямые заказы (без WB-кода)
`startDirectFlow` → выбор пакета (`buildPackKb`, бонусы/скидки) → *(экран «🎁 Бонус» —
только при bonus>0)* → ник → поиск геймпасса → выбор из списка (или автопропуск при
ровно одном совпадении по цене) → «Подтверждение» → submit (создаётся `DirectIntent`) →
выбор оплаты: готовая страница сайта / эквайринг Т‑Банка в боте / перевод по реквизитам.
После выбора Web атомарно создаёт `WbOrder(DIRECT)` и `PaymentAttempt`; менеджер не нужен
для выдачи способа оплаты. Код заказа — синтетический `DIR-…` (нет `WbCode`).

**Ссылка вместо ника работает и здесь (24.08.2026).** Шаг «ник» принимает ссылку/ID
геймпасса (`handleDirectGamepassLink` в TG, `handleVkDirectGamepassLink` в VK): пасс
проверяется по цене и `isActive`, ник получателя берётся у **владельца геймпасса**
(`GamepassDetails.creatorName`) — он надёжнее набранного вручную, — и флоу сразу уходит
на экран «Подтверждение». Ветки `user_not_found` / `no_gamepasses` называют ссылку вслух. Старые
`sqi/spi` и TWA-действия сохранены для pending intents предыдущей версии, но используют
тот же CAS `PENDING → CONSUMED` и не могут создать второй заказ при гонке.

После «✅ Оплата пришла» (`pay_ok`, проставляется `paidAt`) заказ уходит в **общую очередь
«К выкупу»** вместе с WB/сайтом/ручными — с 2026-07-25 отдельной папки для выкупа прямых
нет, потому что выкупаем руками и без разбиения по аккаунтам (правило очереди —
`src/lib/buyout-queue.ts`). До подтверждения оплаты заказ по-прежнему вне всех путей
выкупа, включая авто-воркер `bots/tg/auto-workers.ts`.

**Честные шаги (Ф4, О1, 2026-07-12).** Раньше «Шаг 2 · Подтверждение» показывался ДО
выбора ника/геймпасса — при bonus=0 это был пустой лишний клик (скрин владельца).
Теперь: **bonus=0** → 4 шага (Пак → Ник → Геймпасс → Подтверждение), промежуточного
экрана нет; **bonus>0** → 5 шагов, экран честно называется «🎁 Бонус» («использовать
в этом заказе? С бонусом цена геймпасса — X R$, без — Y R$») с кнопками
`[✅ С бонусом][Без бонуса]`. Решение о бонусе обязано быть до шага «Геймпасс»:
`passPrice = ceil((amount+bonus)/0.7)`. Финальный экран переименован «Итого» →
«Подтверждение». `stepBar(current, total, label)` — динамический total (4/5);
`hasBonusStep` фиксируется в flow-state при выборе пака и не меняется после
«Без бонуса» (нумерация не скачет). Back-навигация: с ника при bonus=0 — сразу к
пакам (иначе повторный выбор пака снова прыгнул бы на ник — цикл). TG + VK зеркально
(TG `DirectFlowState.hasBonusStep`, VK `DirectFlowData.hasBonusStep`).

### Фоновые воркеры (`bots/tg/auto-workers.ts`, старт из `crons.ts` → `startAutoWorkers`)

Browser purchase transport подключён к ручным и автоматическим денежным путям. Бот
передаёт текущую cookie только в локальный SG purchase-service. Проверка аккаунта/баланса,
buyer-specific цена и Plus-классификация, ownership и guarded purchase выполняются в одном
persistent Chrome и сериализуются общим no-backlog lock. Бот и Web не посылают donor cookie
Roblox напрямую и не имеют direct-fetch fallback. `/setcookie` принимает raw/copy-header,
нормализует и сохраняет cookie только после успешного SG `/session`. При недоступности
browser service claim откатывается в `PENDING`, пишется `[AUTOBUY-BLOCKED]`, включается
пауза и остаётся ручной script fallback. Точные коды различают invalid cookie, другой
аккаунт, 2FA, busy, временный отказ Roblox, price/seller/ownership guard и неподтверждённый баланс. Контур
задеплоен 17.07 и прошёл Web/TG readiness; production canary с новой funded cookie ещё обязателен. Runbook — в
[`roblox-plus-buyout-plan.md`](roblox-plus-buyout-plan.md).

**❄️ Заморозка в автовыкупе (30.08.2026) — два рубежа.** Первый: `heldAt: null` в `where`
самой выборки PENDING. Второй: пакетная перепроверка `OrderHold` по кодам выбранной пачки
(`activeHoldCodes`) — `heldAt` не видит заказ, который бот только что создал по заранее
замороженному коду, а крон-свип ещё не пометил; окно небольшое, но именно в нём тратятся
чужие робуксы. Найденный замороженный уходит в `autobuySkip` и получает пометку через
`assertOrderNotHeld` (тот же вызов проставляет заморозку на заказ, чтобы дальше он выглядел
замороженным в ленте, а не «почему-то не выкупается»). Тот же гард стоит в ручном выкупе из
карточки бота (`pb:`) — до `getGamepassProductInfo`, чтобы замороженный заказ не ходил в
Roblox вовсе.

**Крон `sweepPendingHolds`** (в `crons.ts`, раз в минуту, `[OrderHold]`): сажает активные
заморозки на заказы, созданные после них. Покрывает все 11 мест, где рождается `WbOrder`, не
трогая ни одно из них. За безопасность траты не отвечает — она на `assertOrderNotHeld`.

Оба kill-switch по умолчанию **OFF** (в `GlobalSettings`), включает владелец командой.
Сохранение новой donor-cookie в TWA или через `/setcookie` только проверяет аккаунт и обновляет
`GlobalSettings`; оно намеренно не меняет `autoBuyoutEnabled`. После обязательных 3/3 canary
автомат включается отдельно через `/autobuy on`.

Donor-readiness теперь означает успешный SG `/session`, а не `/health` и не прямой запрос
Roblox из процесса бота. Buyer-specific preflight возвращает одновременно product/ownership
и подтверждённые `buyerUserId`/имя/баланс; ручной скрипт не выдаётся без account guard.
Если session invalid/busy/unavailable, авто-воркер ставит 15-минутную паузу, оставляет
kill-switch без изменений и сообщает менеджеру точную причину.

## Уведомления — кто и когда

**Клиент:** provisional-заказ (приветствие+цена), геймпасс принят (`PENDING`), `COMPLETED`
(два сообщения, см. ниже), `REJECTED` (причина + «исправить ссылку»), `review_ok`
(+100 R$ + «заказать ещё»).

### COMPLETED = два сообщения (Ф5, 2026-07-12)

`notifyUserCompleted` (боты/автовыкуп) и `notifyOrderCompleted` (действия из TWA) шлют
**два** сообщения; тексты и ветвление — `bots/shared/completed-messages.ts`
(зеркало в `src/lib/twa-notify.ts`, менять синхронно):

- **msg1 — операционное** (всем): факт выкупа + дата разблокировки робуксов
  (`completedAt` + 5 дн, МСК) + как проверить (transactions → Pending). Без маркетинга.
- **msg2 — бонусное**, по приоритету:
  1. WB-заказ, бонус не на балансе, `WbCode.reviewBonusClaimed=false` → питч отзыва,
     кнопки `[📸 Прислать отзыв][💎 Купить напрямую]` (О2);
  2. бонус на балансе → «бонус N R$ до {дата}» + `[💎 Использовать бонус]`;
  3. повторный WB-клиент → TIER-2 питч закрытого формата (текст прежний);
  4. прямой заказ → благодарность/N-й заказ (+скидка 60 ₽, если её начислила
     политика `bots/shared/direct-discount.ts`).
- **Скидка 60 ₽ — одна на клиента за всё время** (правило владельца 20.08.2026).
  Выдаётся при завершении **первого** прямого заказа и только если он был меньше
  500 R$ и бонус в 100 R$ на нём не активировали; тратится на второй покупке.
  Бонус активирован → скидки нет. Первый заказ от 500 R$ → скидки нет.
  Решение и начисление — один модуль на бота и веб, идемпотентность через
  `User.directDiscountGrantedAt`. До 20.08 правило звучало как «после каждого
  завершённого прямого заказа < 500 R$» и начисляло скидку по кругу.
- Кнопки TG и VK одинаковые: TG `callback_data` = VK `payload.command`
  (`review_hint` / `start_direct`). `pendingReview` из TWA-пути не ставится —
  bot-side callback `review_hint` и DB-фолбэк photo-handler'а восстанавливают стейт.

**Админы (TG):** provisional-заказ (карточка `sendAdminOrderCard` с [✅ ВЫКУПЛЕНО][❌ ОШИБКА]),
VK-логин с кодом / без, fail валидации геймпасса, нажатие поддержки, фото отзыва.

### Один заказ — одна ветка (05.09.2026)

Правило от 02.09 («о заказе DBS говорит одна живая карточка») доведено до конца. Три вещи,
которые его ломали:

**1. Утечка карточки входа.** В `src/auth.ts` стоял `else if (shouldSendLoginNotif(vkId))`.
Вход, УСПЕШНО свёрнутый в карточку DBS, проваливался в эту ветку — и под аккуратной
карточкой висели три сиротские строки «🆕 Новый пользователь / 👤 Имя / 🆔 VK ID»: без
кода, без номера WB, мимо ветки. Условие теперь `!foldedIntoDbsCard && …`, а голая карточка
входа осталась ровно тем, чем задумывалась, — сообщением о входе **без заказа**.

**2. Личность покупателя — строка в карточке.** `noteDbsBuyerSignedIn` принимает имя,
ссылку на профиль и «новый ли клиент», кладёт их в payload события `BUYER_SIGNED_IN`, и
карточка рисует `👤 Имя · VK · новый клиент` под шапкой. Payload перезаписывается, если
второй заход знает больше первого: карточка собирается ТОЛЬКО из событий, второго источника
правды у неё нет. Зовут это все три входа — сайт, TG-бот, VK-бот.

**3. Единый корень ветки для всех отправителей.** `orderThreadRoots(db, code)` отвечает на
вопрос «к чему пришивать» один раз: живая карточка DBS (`adminCardMessages`), иначе карточка
активации кода (`ADMIN_CARD_ROOT`), иначе без ответа. Раньше про два корня знали только две
карточки выкупа, а обращение в поддержку, подтверждённый выкуп, скрин оплаты и скрин отзыва
уходили россыпью — хотя код заказа знали все до одного. `replyToRoot` даёт поля ответа и
всегда с `allow_sending_without_reply`: корень могли удалить, а сообщение бывает о деньгах.
Туда же переведено «покупатель нашёлся сам» — оно единственное оставалось сырым текстом
мимо `formatAdminNotice`.

**Карточка ведёт заказ целиком, а не до гейта.** Раньше она застывала на «доставка закрыта,
гейт отправлен · покупатель активирует код в боте» навсегда. Теперь после закрытия доставки
заголовок ведёт сам заказ на выкуп: «код активирован — ждём геймпасс» → «в очереди на
выкуп» → «выкуплен» (плюс «ошибка выкупа», «заказ отменён» и заморозка, которая бьёт
статус). В таймлайн добавились «ссылка получена — в очереди на выкуп» и «выкуплен».

Состояние **выводится** из `WbOrder` при обновлении карточки, а не собирается из событий:
статус меняют пять разных путей (TWA, бот, воркер, сайт, скрипты), инструментировать
пришлось бы каждый, и разошлись бы они в первый же день. Обновление зовут три громких
момента: обе карточки выкупа (`sendAdminOrderCard`, `sendWebOrderCard` — ссылка получена) и
оба завершения (`notifyOrderCompleted` и кнопка `admin_ok` в TG). Вход — `refreshDbsCardByCode`
в `bots/shared/wb-dbs-thread.ts` для тех, кто знает код, но не знает id заказа доставки.

Инварианты — `bots/shared/__tests__/dbs-order-lifecycle.test.ts`,
`bots/shared/__tests__/order-thread.test.ts`, `src/__tests__/admin-order-thread.test.ts`.

## Изменения 26.07.2026 (ultra-review)

### Кнопки больше не доверяют `callback_data` (U6, риск №24)

`callback_data` — не доверенный ввод: через неофициальный MTProto-клиент можно вызвать
`messages.getBotCallbackAnswer` с произвольной строкой, в VK — прислать произвольный
`payload`. Появился общий хелпер `bots/shared/ownership.ts`:

```ts
const owned = await assertOwnsOrder(tgActor(ctx.from.id), orderId, { status: true });
if (!owned.ok) { /* forbidden | not_found */ }
```

Он резолвит `User` по `tgId`/`vkId` и сверяет владельца сущности; нарушение пишется в лог
как `[ownership] violation platform=… actor=… order=… owner=…` — это сигнал атаки, а не
бытовая ошибка. Переведены `gpw_ok:` / `gpw_no:` (обе платформы) и `uci:`.
`confirmGpWatch`/`declineGpWatch` теперь принимают `actor` и умеют возвращать `forbidden`.

**Правило:** любая новая ветка `callback_query`, которая читает сущность по ID из кнопки,
обязана либо стоять за `ADMIN_IDS.includes(...)`, либо пройти через `assertOwns*`.

### Деньги клиента (U3/U4, риск №25)

- `bots/shared/order-benefits.ts` — единственная точка изменения баланса на стороне ботов:
  всегда `increment`, всегда запись в `BonusLedger`, всегда ключ идемпотентности.
  Прежний `updateData.balance = user.balance + x` (read-modify-write, lost update при
  гонке) больше не используется.
- `ucd:` (отмена прямого заказа покупателем) чинён: раньше бонус считался как
  `amount − WbCode.denomination`, а строки `WbCode` у `DIR-` заказов не существует, поэтому
  ветка возврата была **недостижима**, а скидка не возвращалась вовсе. Теперь источник —
  поля `bonusAppliedRobux` / `discountAppliedKopecks` самого заказа, и клиенту в сообщении
  об отмене видно, что именно вернулось.
- При создании заказа из `DirectIntent` (`sqi:` и `spi:`) применённые бонус и скидка
  записываются в заказ, а списание бонуса проходит через леджер.
- Бонус за отзыв (`review_ok:`) тоже переведён на леджер — раньше это был единственный
  `increment` в проекте и он не оставлял записи в журнале.
