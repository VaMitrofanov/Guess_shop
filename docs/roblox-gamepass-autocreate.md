# Автосоздание геймпасса по ключу клиента — мастер-план

**Проблема.** Робуксы переводятся выкупом геймпасса клиента: клиент создаёт пасс
нужного номинала у себя, мы его выкупаем — робуксы уходят клиенту (минус налог
Roblox). Узкое место — **создание пасса руками**: эмпирически даже по подробной
инструкции значительная часть покупателей не доводит его до конца (нет пасса —
28 из 54 застрявших в живой диагностике, см. `wb-activation` разбор).

**Идея.** Клиент выдаёт нам **Open Cloud API-ключ** с правами на геймпассы,
а бот **сам создаёт покупаемый пасс нужного номинала**.

**Что подтверждено живьём (05.09.2026, повторено 06.09.2026 на двух аккаунтах).**
Open Cloud создаёт покупаемый геймпасс нужной цены **одним запросом** (раньше API
этого не умел — устаревшее знание). Точный рецепт — в памяти
`project_roblox_opencloud_gamepass_api`; кратко:

- `POST https://apis.roblox.com/game-passes/v1/universes/{universeId}/game-passes`
- тело — **multipart/form-data** с ASP.NET-полями `request.Name`, `request.Price`,
  `request.IsForSale` (JSON → 415); иконка (`request.Icon`) **необязательна**;
  `IsForSale=true` проходит **при создании** — отдельный PATCH не нужен;
- **скоуп ключа (важно, стоило часа отладки):** в Creator Hub нужен API System
  **`game-passes`** с операциями **`game-pass:read` + `game-pass:write`**.
  Соседний `legacy-game-passes → legacy-game-pass:manage` **не работает вовсе** —
  `403 Scope not authorized` даже на чтение. Выбора experience у ключа **нет**:
  он покрывает **все опыты своего владельца** и только их;
- два разных `403` (лечатся по-разному): `Scope not authorized` — ключ сделан не
  на том API System (нужен новый ключ, перебор опытов бесполезен);
  `UnauthorizedAccess … universe` — опыт чужой для ключа (пробуем следующего
  кандидата). Пасс в обоих случаях не создаётся — перебор безопасен;
- права правятся **у существующего ключа**, строка ключа при этом не меняется;
  JWT внутри ключа живёт **1 час** (после — новый ключ);
- **имя/иконка бизнесу не важны**, важны **цена** и факт **«в продаже»**. Имя —
  наше и заодно реклама: `RobloxBank` и вариации (кириллица проходит модерацию;
  мат Roblox заменяет на `#####`).

**Егресс.** С RF-хоста `apis.roblox.com` молча висит (сеть Roblox
`128.116.0.0/16`), поэтому создание идёт через **SG-мост** — там же, где и весь
остальной Roblox-трафик.

### Фаза 0 — доказательство осуществимости ✅ (05.09.2026, повтор 06.09.2026)
Живой прогон: create → «в продаже» → сверка. Пасс создан ботом-скриптом,
покупаемый, ровно за указанный номинал. Клиент в Studio не нажал ничего.
Повтор 06.09 на двух аккаунтах ключами владельца: `KrytishVadim4ick` (universe

### Фаза 1 — база (движок) ✅ ЭТА ЗАДАЧА — ДОРМАНТ
Движок создания, **не подключённый к клиентскому флоу**:

- `bots/shared/roblox.ts`: `createGamePassForUserDirect()` (+ `createGamePassDirect`,
  `resolveUniverseCandidatesDirect`, `safeGamePassName`, `BRAND_GAMEPASS_NAMES`).
  Резолв опыта (universeId → placeId → ник), создание одним POST, подстраховочный
  PATCH, перебор кандидатов при `403`. Имён в `BRAND_GAMEPASS_NAMES` с 07.09.2026
  **25, а не 8** (`c3d72e3`): имя пасса — единственная наша бесплатная реклама на
  чужом опыте, одинаковое у всех выглядит штампом. Добавлены обращения, обещания
  («робуксы без обмана», «выгодный курс») и латинские варианты для игр на
  английском; тест держит длину 3–50 и бренд в каждом варианте.
- `bots/shared/bridge.ts`: роут `POST /create-gamepass` (за `x-validator-key`).
  Ключ проходит транзитом, **не логируется и не возвращается**.
- `src/lib/roblox-gamepass-create.ts`: клиент RF Web → мост (`createGamePassViaBridge`)
  с различимыми ошибками (`not_authorized`, `no_universe`, `bad_price`, …).
- `scripts/roblox/create-gamepass.mjs`: ops-скрипт для боевого прогона (на SG).
- Тесты `bots/shared/__tests__/gamepass-create.test.ts` (сеть замокана).

**Не входит:** хранение ключа, админ-кнопка, изменение инструкции, автозапуск.

### Фаза 2 — персистентность и след в заказе ✅ (06.09.2026)
**Решение владельца: ключи НЕ стираем.** Ключ ограничен геймпассами своего
владельца и бессрочен (если покупатель не выбрал дату истечения), а нужен он нам
дважды: чинить уже созданный пасс без покупателя и создавать пасс сразу на
следующем заказе постоянного клиента.

- `RobloxApiKey` (миграция `20260906_roblox_api_key`): значение под AES-256-GCM
  (конверт доставки WB, назначение `roblox-api-key`), HMAC — только для
  дедупликации, рядом след: ник, заказ, исход, сколько пассов создано.
  Работа с хранилищем — `src/lib/roblox-api-key-store.ts`; расшифровка только на
  сервере, наружу не отдаётся ничего.
- След в заказе, чтобы админ видел, ЧТО именно он выкупает:
  `AUDIT_GAMEPASS_AUTOCREATED` на каждый пасс (лента событий TWA и веб-админки),
  строка в `adminNote` («🔑 Пасс создан по API-ключу покупателя: ID · цена»),
  маркер **🔑 ПАСС СОЗДАН ПО API-КЛЮЧУ** в карточке выкупа Telegram (признак
  берётся из событий заказа, а не со слов клиента).
- Осталось: админ-действие «поправить пасс по сохранённому ключу» и чистилка
  строк — обе после обкатки.
- **Подтвердить реальную покупаемость end-to-end**: один раз выкупить созданный
  пасс и убедиться, что робуксы дошли, — до включения в массовый флоу.

### Фаза 3 — инструкция V2: свой раздел «как сделать ключ» + проверка на месте ✅ (06.09.2026)
**Решено 06.09.2026 (владелец).** Ключ вводится **в самой инструкции**, ровно как
сейчас вводится ник: покупатель вставляет ключ в поле → играет анимация проверки
→ на бэкенде идёт реальная проверка ключа и создание пасса → человек видит
вердикт «готово / не вышло, вот что поправить».

Состав:
**Кадры нарезаны 06.09** из двух записей владельца: ПК (`public/guide/wb-key-pc-*.jpg`,
8 кадров) и телефон (`wb-key-m-*.jpg`, 9 кадров). Ключи на кадрах замазаны.
Макет раздела (телефон + ПК + анимация проверки) — артефакт «Ключ за 5 шагов».

Что вскрылось при нарезке: если ползунок **Experience Restrictions выключен**
(наш путь), Roblox перед выпуском показывает окно **«Important Security Warning —
Unrestricted Experience Access»** с галочкой *I understand the security risks* —
без неё `Save & Generate Key` не срабатывает. Это отдельный шаг инструкции.
Кадр есть только мобильный: десктопная запись шла через ползунок.

- **Раздел инструкции «Ключ за N шагов»** — по образцу раздела про геймпасс:
  свои кадры под телефон и под ПК (Create → лупа → `API Extensions` → синяя
  `Create API Key` → имя → `Select API System` → `pass` → **game-passes** →
  операции `game-pass:read` + `game-pass:write` → `Save & Generate Key` →
  `Copy Key To Clipboard`). Вход — **только через лупу**: страницы ключей нет в
  боковом меню, а прямая ссылка на телефоне уводит в приложение. Случай «ключи
  уже есть» не рисуем (кто дошёл до второго ключа — дорогу знает).
- **Поле ввода ключа + анимация проверки** (как `phase: scanning` у ника) и
  вердикт: создан пасс на N R$ / что именно поправить.
- **Роут** `POST /api/roblox/gamepass-create` → `createGamePassViaBridge` (ключ
  транзитом, не логируется, не хранится), рейт-лимит по IP, за флагом.
- **Вердикты покупателю** по машинному коду движка: `bad_key` (ключ протух —
  живёт час — или скопирован не целиком), `bad_scope` (выбран не тот API System),
  `not_authorized` (ключ от другого аккаунта), `no_universe` (нет опубликованной
  игры), остальное — «попробуй ещё раз / создай пасс руками».
- После успеха созданный пасс сразу подставляется в план заказа — покупатель
  жмёт «Подтвердить», как после обычной проверки ника.

Ключ стал третьей дверью в развилке ботов — той же, что на сайте. Подробности
и границы — `docs/bots.md`, раздел «Ветка “сделаем за тебя”»; макет —

- Весь квест перенесён в TG и VK целиком, а не только ключ: разбор плана

  переэкспортирует), экраны и кнопки (`gamepass-quest.ts`), создание и след
  (`gamepass-autocreate.ts`), вердикты (`gamepass-create-messages.ts` — тоже
  переехал), флаг (`gamepass-autocreate-flag.ts` — тоже переехал).
- Ключ приходит текстом; в TG бот удаляет сообщение сам, в VK просит удалить
  (сообщество чужие сообщения удалять не умеет).
- Создание идёт `createGamePassForUserRouted`: мост первым, прямой путь —

- **Права ключа различаются точнее (07.09.2026).** `403 Scope not authorized`
  приходит и на «выбран legacy», и на «отмечена одна операция из двух». После
  отказа движок пробует тем же ключом ПРОЧИТАТЬ пассы: получилось — значит нет
  только `game-pass:write`, и вердикт говорит про одну галочку, а не про новый
  ключ (`bad_scope_write`). На успешном пути лишних запросов нет.
- **Шаг инструкции про права переписан** (приёмка владельца): права не
  появляются сами после выбора системы — их добавляют в отдельной пустой рамке
  со стрелочкой (на ПК справа от названия `game-passes`, на телефоне под ним).
  Это самое неочевидное место ветки, и теперь оно расписано по шагам с
  ориентиром «готово выглядит так: в рамке две плашки».

### Фаза 3.5 — «квест»: одна инструкция вместо двух ✅ (06.09.2026)

Раздел про ключ не приклеен сбоку, а стал одной из трёх дверей общего маршрута
(`GamepassCheck`): **ник → проверка → что нашли → выбор способа → ветка → заказ**.

- **Выбор способа — отдельный экран.** Пока три способа лежали секциями под
  результатом, до них не долистывали. Порядок дверей (решение владельца):
  1) «Создам сам (инструкция)», 2) «Сделайте за меня» (ключ, бейдж НОВОЕ,
  «минута»), 3) «Он у меня уже есть» (Pass ID).
- **Шаги идут по одному** (`GuideSteps layout="paged"`), с прогрессом «шаг N из
  M» и ссылкой «показать все шаги списком». Читателю `/guide` без заказа
  по-прежнему отдаётся список целиком.
- **Переключатель подробности:** «📸 Пошагово» (по умолчанию — кадр на каждое
  действие) и «🎬 Супер подробно» (добавляет видео шага целиком и общие планы
  страницы). Раньше видео и все ракурсы показывались всем и всегда.
- **Тупиков нет:** из ключа всегда открыта дверь в обычную инструкцию, из
  инструкции — в ключ и в Pass ID, из Pass ID — в обе. Вердикт ключа ведёт на
  тот шаг, где ошибка (`bad_scope` → шаг с правами, `bad_key` → шаг выпуска).
- **Карточка результата не показывает того, чего нет:** список — только реально
  найденные пассы, а нужное вынесено в блок «что нужно сделать».
- Макет, по которому собрано: `docs/wb-guide-quest-mockup.html`.

### Фаза 3.75 — ключ в личном кабинете ✅ (07.09.2026)

Ключ перестал быть частью аварийного сценария и стал настройкой аккаунта.

- **Карточка «Ключ для геймпассов»** в `/dashboard` рядом с ником (это две
  половины одного действия: «кому робуксы» и «кто создаст геймпасс»).
  Компонент — `src/components/customer-roblox-key.tsx`, стили — блок `key*` в
  `dashboard.module.css`. Внутри: поле ключа, анимация проверки в три строки,
  вердикт, свёрнутая инструкция из 6 шагов с кадром того самого шага про права и
  ссылкой на полную инструкцию.
- **Ник спрашивается один раз** (приёмка владельца 07.09.2026, `b09c9e0`). Он
  уже есть в профиле, и второе такое же поле рядом читалось как ошибка формы.
  Вместо поля — строка «Ключ для аккаунта @nick — в его игре и создадим
  геймпасс» со ссылкой «другой аккаунт»; само поле появляется, только когда ник
  действительно негде взять, и рядом сказано, зачем он нужен.
- **Принятый ключ называет аккаунт сам.** Проверка возвращает канонический ник
  от Roblox и аватар; кабинет показывает карточку «ключ работает на этом
  аккаунте — робуксы придут сюда», боты добавляют аккаунт в сообщение об успехе.
  Вывод честный: кандидаты-опыты резолвятся ИЗ ника, и ключ авторизован на одном
  из них — значит владелец ключа и есть владелец этого ника. Канонический ник
  уходит в хранилище и в уведомление админам: по нему потом ищется сохранённый
  ключ на заказе, и регистр не должен разъезжаться.
- **Проверка НЕ создаёт пасс.** `verifyGamePassKeyDirect` (мост:
  `POST /verify-gamepass-key`) проверяет обе операции безопасно: чтение — GET
  списка пассов, запись — PATCH **заведомо несуществующего** пасса (создать он
  не может по определению, а Roblox проверяет права раньше наличия). Поэтому
  «принят» здесь значит «сработает на заказе», а не «строка похожа на ключ».
- **Роут** `src/app/api/account/roblox-key/route.ts` (GET / POST / DELETE):
  только своя сессия, рейт-лимит, флаг; неудачные попытки в базе не оседают;
  ключ не возвращается ни одним ответом.
- **Уведомление админам** по образцу карточки входа: «покупатель привязал ключ»
  с ником и числом выполненных заказов. Смысл — такой заказ можно закрыть, не
  дожидаясь, пока человек создаст геймпасс.
- **Создаём СВОЙ набор.** `createTargetsFor` — эталонная пара под номинал
  (`SPLIT_PLANS`), а не остаток от того, что лежит на аккаунте. Разбор плана
  экономит ручной труд покупателя; с ключом руками никто ничего не делает, и
  единственное, что важно, — удобство выкупа. Живой прогон 07.09.2026 (TST2000)
  дал «2838 + 20» вместо «2143 + 715» ровно потому, что план засчитал лежавший
  на аккаунте пасс на 20 R$.
- **Ключ используется автоматически.** `createPassesWithStoredKey` берёт
  **свой** ключ покупателя (фильтр по `userId`) и создаёт недостающие пассы по
  одному нажатию: в ботах это первая дверь развилки «✨ Создать за меня».
  Без этого хранение ключей было бы обещанием без исполнения.

### Фаза 4.5 — вход в ветку по ссылке и заказ с «нечего создавать» ✅ (07.09.2026)
- **`?stage=key` вместо мёртвого якоря.** Кнопка «📸 те же шаги с картинками» в
  обоих ботах вела на `…/guide?source=wb&skip=1&code=…#key`. Якоря `#key` на
  странице нет и не было: человек, ушедший за ключом, попадал в начало проверки
  ника — ровно в тот экран, из которого только что вышел. Теперь ветку открывает
  query-параметр (`guideUrlFor(code, nick, "key")`); старый якорь тоже
  принимается — кнопки живут в переписке дольше кода. Намерение не срабатывает на
  входе: до проверки нет ни аккаунта, ни плана, поэтому оно ждёт первого
  результата и тратится один раз.
- **Ветка перестала требовать «есть что создавать».** Она висела на
  `targetsToCreate(plan).length > 0`, а заказ, который не выкупается ИМЕННО
  из-за одного крупного пасса (`plan.kind === "ready"`), — главный клиент
  метода: у него `toCreate` пуст, и к ключу его не подпускало ни на сайте, ни в
  боте (живой случай PCMVDH4: пасс на 2858 закрывает весь номинал 2000).
  Карточка результата на время ветки молчит — «создавать ничего не нужно» прямо
  над формой ключа читается как спор страницы с самой собой; после создания
  возвращается ради «Подтвердить заказ». Дверь «создам сам» из ключа при пустом
  наборе показывает справочные шаги, а не пустой экран.
- **В ботах развилки для такого заказа по-прежнему нет** (`questResultScreen`
  при `ready` рисует «Подтвердить заказ»): туда покупатель попадает ссылкой или

- Держат тесты `src/__tests__/key-stage-entry.test.ts` и проверка ссылки в

## Границы и риски
- **Скрытый/неопубликованный плейс** этим не лечится: `create` требует
  опубликованный experience (по нику он не резолвится — нужен явный
  universeId/placeId, т.е. ссылка на опыт).

  на **все опыты владельца**, не на один).
  Хранить шифрованно, разово, удалять. Детали — `docs/security.md`.
- **Точность цены** — плюс: `request.Price` ставит ровно номинал, уходит fat-finger.

## Ключ из кабинета доделывает ЖИВОЙ заказ (07.09.2026)

До этой правки `POST /api/account/roblox-key` только сохранял ключ и отвечал
«его следующий заказ можно закрыть без ожидания». Владелец 07.09.2026 про живой
случай: *«привязал ключ… а у него с живым висящим заказом не создался гп, не
спарсился ник, ничего кроме уведа не произошло»*. Так и было: заказ `JS6NQB9`
ждал геймпасс ровно в ту минуту, когда покупатель привязывал ключ.

Теперь принятый ключ сразу отрабатывает по заказу в `AWAITING_GAMEPASS`:

1. набор считается `createTargetsFor(amount)` — **эталонный под номинал**, а не
   «чего не хватает на аккаунте» (правило общее с ботами: руками тут никто
   ничего не делает, и подстраиваться под мелочь значит получать пассы,
   неудобные для выкупа); у сайтового заказа набор всегда из одного пасса;
2. пассы создаются, след пишется тот же, что у ветки ключа в инструкции
   (`AUDIT_GAMEPASS_AUTOCREATED` + строка в `adminNote` + маркер 🔑 в карточке);
3. ник ложится в заказ как **вероятный** (`noteProbableNickByCode`) —
   подтверждённым он становится на подтверждении заказа, а не на привязке ключа;
4. кабинет показывает «геймпасс для заказа X уже создан — подтверди» со ссылкой
   в **его собственный** коридор;
5. уведомление админам называет заказ и созданные цены, а при отказе — код
   ошибки Roblox и маркер 🟠.

**Заказ автоматически не оформляется.** Последний экран — геймпасс, номинал,
ник и «подтвердить» — остаётся за покупателем: это единственное место, где
расхождение «ник в заказе ≠ владелец пасса» ещё ловится глазами.

Ядро вынесено в `src/lib/gamepass-key-create.ts` (`createPassesWithKey`): одна и
та же операция нужна инструкции, кабинету и одно-нажатию в квесте, и порядок
побочных эффектов у неё обязан быть один.

## «Создать сейчас» сохранённым ключом — теперь и на сайте (07.09.2026)

Боты умели это с 07.09 (`createPassesWithStoredKey` → дверь «✨ Создать
сейчас»), а сайт просил ключ заново у того же покупателя, который привязал его в
кабинете десять минут назад.

- `GET /api/roblox/gamepass-create?code=…&nick=…` → `{ stored: boolean }`;
- `POST` с `{ useStored: true, code, nick, targets }` создаёт пассы без ключа в теле.

**Кто владелец ключа, решает КОД заказа.** Заказ по коду знает своего
покупателя, а `loadRobloxApiKeyForUser` берёт ключ строго этого покупателя и
строго на этот ник. «По нику» брать нельзя: чужой ник стал бы способом создать
геймпасс на чужом аккаунте. В квесте эта дверь показывается первой — и на
карточке результата, и на экране выбора способа.

Инварианты: `src/__tests__/gamepass-stored-key.test.ts`.
