# TWA — админка в Telegram Web App

`/twa` — панель менеджера внутри Telegram. Целевые устройства: iPhone 14/15 Pro Max +
MacBook 16". Дизайн — iOS-эстетика, минимальный контентный шрифт 14px.

## Аутентификация — `src/lib/twa-auth.ts`

1. `validateInitData(initData)` — проверяет HMAC подписи Telegram (`HMAC-SHA256`, ключ
   от `TG_TOKEN`), отклоняет старше 24 ч, извлекает `userId`/`firstName`.
2. `isAdmin(userId)` — проверка по `ADMIN_IDS`.
3. `signTwaToken` → JWT (`role: twa-admin`, TTL 12 ч), `verifyTwaToken` при каждом запросе.
4. `extractTwaUser(req)` — читает `Authorization: Bearer` и верифицирует.

**Все `/api/twa/*` роуты вызывают `extractTwaUser` в начале** (кроме `auth` — точка входа —
и `debug` — за `ADMIN_SECRET`).

> ⚠️ **Известный риск:** `api/twa/auth` имеет fallback-путь (Path 2), доверяющий `userId`
> из тела запроса без initData. Telegram ID не секретны → потенциальный обход. См.
> [security.md](security.md#twa-auth).

## Вкладки заказов (`OrdersScreen` + `api/twa/orders`)

Виртуальные фильтры (`buildTabWhere`), а не просто статусы:

| Вкладка | Фильтр | Сортировка | Цена |
|---------|--------|------------|------|
| Все | всё (кроме `isTest`) | новые сверху | чистые |
| К выкупу | PENDING+IN_PROGRESS, не direct, не avito, не favorite | старые сверху | грязные (чистые) |
| Прямой | direct, активные статусы | старые сверху | грязные |
| Авито | `orderSource=AVITO`, активные | старые сверху | грязные |
| Новые | AWAITING_GAMEPASS < 40 ч | новые сверху | чистые |
| Ошибка | ERROR | старые сверху | грязные |
| Ждут ссылку | AWAITING_GAMEPASS ≥ 40 ч | 5 свежих, дальше старые сверху | чистые |
| Готово | COMPLETED (аккордеон по куки-аккаунту) | новые сверху | чистые |
| Избранное | isFavorite | новые сверху | чистые |

**«Ждут ссылку» — гибридная сортировка** (`fetchAwaitingLinkHybrid`): первые 5 карточек —
самые свежие (только что перевалили порог 40 ч, клиент ещё «тёплый»), с 6-й — весь хвост от
самого старого к новому. Собирается на сервере двумя запросами (голова desc + хвост asc с
`id notIn`), чтобы порядок переживал пагинацию; между головой и хвостом в UI — разделитель.
При активном поиске — обычный `createdAt asc`.

Счётчики/суммы — один `$queryRaw` с `FILTER (WHERE …)`, кэш 30 с (`cachedCounts`), сбрасывается
при любой мутации. Помимо `counts` отдаёт `sums` (BUYOUT / DIRECT / AVITO / AWAITING_LINK /
NEW / ERROR — суммы `amount` по всей категории) и `oldest` (BUYOUT — `MIN(pendingAt)`,
AWAITING_LINK — `MIN(createdAt)` — возраст очереди). На append-страницах (`skipCounts=1`)
клиент сохраняет прежние `counts`/`sums`/`oldest`. Отдельный ключ `counts.INTENTS` — число
живых заявок прямых заказов (DirectIntent PENDING < 24 ч); бейдж вкладки «Прямой» на клиенте =
`DIRECT + INTENTS`.

### Заявки прямых заказов (вкладка «Прямой»)

Заявка (`DirectIntent`, «⏳ Ожидаем реквизиты») — прямой заказ из бота ДО отправки
реквизитов; раньше жила только в TG-карточках админов. Теперь на вкладке «Прямой» (без
поиска) сверху рендерится секция **«⏳ Заявки · ожидают реквизиты (N)»** (`IntentsSection`,
`GET /api/twa/intents`): карточка показывает платформу, юзера (тап — контакт), возраст,
сумму R$ → ₽, бонус, ник, ссылку на геймпасс и бейдж «🔄 ×N» повторного клиента.

Кнопки = TG-карточке заявки (`POST /api/twa/intents`, транзакции и тексты клиенту — зеркало
sqi:/spi:/cai: из `bots/tg/handlers.ts`):
- **📷 QR (СБП)** (`send-qr`) — создаёт заказ `DIR-…` в `PAYMENT_PENDING`
  (`paymentDetails: "СБП QR"`), гасит заявку (CONSUMED), сбрасывает бонус/скидку юзера и шлёт
  клиенту QR: TG — фото ссылкой `/api/sbp-qr?t=<HMAC>` через мост, VK — upload сырыми байтами.
- **💳 Реквизиты** (`send-details`) — то же, но текст реквизитов вводится в карточке и уходит
  клиенту сообщением (`paymentDetails` = текст).
- **❌** (`reject`, двухтапное подтверждение) — заявка `CANCELLED` + «Заявка отклонена» клиенту.

Тост честный: канал доставки (TG/VK) или «создан, но сообщение НЕ доставлено». Заявки старше
24 ч авто-помечаются `EXPIRED` (как в TG). Скрин оплаты после этого принимает бот: TG — по
DB-fallback (userId + `PAYMENT_PENDING`), VK — целиком DB-driven.

Заказы `AWAITING_PAYMENT`/`PAYMENT_PENDING` во вкладке «Прямой» вместо кнопок выкупа получают
плашку «💳 Ждём оплату…» + отмену (выкуп до подтверждения оплаты сервер всё равно отвергнет;
оплату подтверждает менеджер по скрину в TG-боте).

### 🚫 Недостижимые VK-клиенты (бейдж в карточке)

VK-логин на сайте создаёт юзера без диалога с сообществом → бот писать не может (VK 901).
Enrich-батч (`/api/twa/orders/enrich`) для живых заказов чисто-VK-юзеров проверяет
`messages.isMessagesFromGroupAllowed` (`src/lib/vk-reach.ts`, кэш 1 ч, ≤12 свежих проверок за
запрос, VK_TOKEN+VK_GROUP_ID) и возвращает `vkUnreachable`; карточка показывает красную плашку
**«🚫 Бот не может написать (VK)»** со ссылкой на профиль — писать только с личного аккаунта.

### Дашборды

- **Вкладка «Все»** — сетка тап-карточек по категориям (`MiniDashboard`, 2 колонки, пустые
  скрыты): количество, сумма по всей категории и возраст очереди (⏳, цвет `ageColor`).
  Крупная цифра — то, чем оперирует менеджер в категории: К выкупу/Ошибка — грязные (чистые),
  Ждут ссылку/Новые — чистые (грязные), Прямой/Авито — только грязные. Тап — переход во вкладку.
- **Внутри «К выкупу» и «Ждут ссылку»** — та же карточка своей категории на всю ширину
  (не кликабельна).

### «Требуют внимания» (вкладка «Все»)

По умолчанию «Все» показывает не хронологическую ленту, а серверную подборку `ATTENTION`
(виртуальная вкладка в `buildTabWhere`, не чип): всё, где нужно действие менеджера.
Правила (константы в `route.ts`): `ERROR` (все); «К выкупу» с `pendingAt` старше **12 ч**;
прямые в `AWAITING_PAYMENT`/`PAYMENT_PENDING`; «Ждут ссылку» старше **5 дней**. Избранное
исключено. Сортировка по серьёзности (`attentionRank`: ошибка → подвисший выкуп → ждёт оплату →
старая ссылка), внутри группы старые сверху. Отдаётся одним куском до 50 позиций (без
пагинации, `pages: 1`).

Карточки в подборке ведут себя как в родной вкладке заказа (кнопки действий, формат суммы —
`viewTab = orderToTab(order)`), плюс бейдж категории как на «Все». После «Выкуплено»/отклонения
карточка уходит из подборки; «Ошибка» — остаётся. Полная хронологическая лента — по кнопке
**«Все заказы →»** (обратно — «⚠ Внимание (N)»).

**Два таймера на карточке.** `⏱` — возраст заказа от `createdAt`. `🛒` — время в очереди
«К выкупу» от `pendingAt` (момент перехода в `PENDING`, когда пришла ссылка на геймпасс).
Второй таймер показывается только для заказов в `PENDING`/`IN_PROGRESS`. Оба цвета — по
`ageColor` (зелёный <2ч → жёлтый → оранжевый → красный >24ч). Есть и в списке «К выкупу»
на экране «Аккаунт» (`BuyoutOrderCard`).

Карточка заказа со статусом `COMPLETED` показывает строку **«💳 Выкуп: {аккаунт}»**
(`purchaserUsername`, `null` → «Ручные») — видно во вкладке «Все» и в результатах поиска.
Во вкладке «Готово» аккаунт уже в шапке аккордеона, поэтому строка там не дублируется.
`purchaserUsername` пишется при серверном выкупе (`purchase`) и сливе; ручной `complete` его
не пишет (остаётся «Ручные»).

## Действия (`POST /api/twa/orders`, поле `action`)

`create-avito` (дедуп: если на геймпасс уже есть активный заказ — AWAITING_GAMEPASS /
PENDING / IN_PROGRESS — вернёт **409** с данными заказа; UI показывает подтверждение и
повторяет запрос с `force: true`; COMPLETED/REJECTED не блокируют — повторный выкуп легален),
`set-note`, `toggle-favorite`, `set-error`, `move-to` (перевод между разделами из
«Ждут ссылку»/«Избранное»; цели — все разделы кроме «Все» и текущего: К выкупу / Прямой /
Авито / Новые / Ошибка / Ждут ссылку / Готово / Избранное; заметка обязательна; AVITO ставит
`orderSource=AVITO`, DONE — тихий `COMPLETED` с фиксацией `purchaseRate` и БЕЗ уведомления
клиенту, FAVORITES — только флаг `isFavorite`, статус не трогает), `complete`, `reject`,
`purchase` (реальный серверный выкуп через `.ROBLOSECURITY` cookie из `GlobalSettings`),
`edit-avito`, `set-source`, `purchase-script` (генерит JS для ручного выкупа в консоли),
`search-users`, `rebind-order` (перепривязка заказа к другому юзеру, транзакция
`WbOrder + WbCode`, аудит в `adminNote`; уведомление новому юзеру — **в стиле обычной
активации кода** («✅ Код X активирован…» + личная инструкция; для AV-/DIR- — без кода),
роут ждёт отправку и возвращает `notified` (tg/vk/null) → тост в TWA честный, как у 📎),
`attachable-orders` (список заказов без геймпасса: AWAITING_GAMEPASS / REJECTED / ERROR,
опциональный `query`), `attach-gamepass` (ручная привязка геймпасса к заказу — см.
«Привязка геймпасса к заказу» ниже), `gpwatch-notify` (см. «GP-watch в карточке» ниже),
`gp-live-check` (безордерный: `orderIds[]` → живая цена ГП из product-info с кэшем 10 мин +
`reusedIn` — код COMPLETED-заказа с тем же геймпассом; питает бейджи карточек очереди).

### Гейт неоплаченных прямых заказов (`paidAt`, 2026-07-06)

`WbOrder.paidAt` проставляется при подтверждении оплаты (`pay_ok:` в TG-карточке, оба
флоу — с геймпассом и legacy). DIR-заказ без `paidAt` **исключён из всех путей выкупа**:

- **Сервер** (`api/twa/orders`): `complete` / `purchase` / `purchase-script` /
  `attach-gamepass` → **409** «💳 не оплачен»; `move-to` → 409 при целях PENDING/COMPLETED
  (Избранное/Ошибка/Ждут ссылку — можно).
- **`/api/twa/roblox-account/purchase`** (экран «Поиск и выкуп»): action `purchase` теперь
  принимает `gamepassId` и отвергает покупку (409), если геймпасс привязан к неоплаченному
  DIR-заказу — раньше роут не проверял статус заказа вообще.
- **Автовыкуп** (`bots/tg/auto-workers.ts`): `NOT (isDirectOrder AND paidAt=null)` в выборке.
- **Экран «Аккаунт»**: неоплаченные DIR не попадают в очередь, счётчики пачки и «⚡ Выкупить
  всё» — вместо этого свёрнутая секция **«💳 Ждём оплату · N»** (карточки без кнопки выкупа).

Бэкфилл миграции `20260706_add_paid_at`: DIR в PENDING/IN_PROGRESS/COMPLETED получили
`paidAt = updatedAt` (эти статусы в штатном флоу достижимы только через pay_ok).

Все действия, кроме `create-avito`, `search-users` и `attachable-orders`, требуют `orderId` —
guard стоит после этих блоков. **Не добавлять безордерные action'ы ниже guard'а**: клиент получит 400
«orderId required», а RebindModal молча глотает не-ok ответы и показывает «Никого не найдено»
(так сломался поиск при первом релизе перепривязки — фикс 2026-07-02).

## Аккаунт-выкуп (`BossrobuxScreen`)

- **Баланс** куки-аккаунта: `1 570 R$ (1 099 чистых)` — `floor(balance * 0.7)`.
- **Cookie** `.ROBLOSECURITY` хранится в `GlobalSettings`, задаётся через `/setcookie` (бот)
  или кнопку в TWA. Ник куки-аккаунта кэшируется в `robloxAccountName`. Это аккаунт-**донор**
  (с него покупаем).
- **«К выкупу»**: параллельно грузит DIRECT + BUYOUT + AVITO. Прямые и Авито — **обязательные**
  (всегда в пачке), WB — **оптимизированное подмножество** через 0/1 DP-knapsack
  (`optimizeWbSubset`, target `[budget-143, budget]`) под баланс аккаунта.
  **Неоплаченные DIR** (`paidAt=null`) в очередь не попадают — секция «💳 Ждём оплату»
  (см. «Гейт неоплаченных прямых заказов» выше).
- **Честная карточка выкупа (2026-07-06):** после загрузки очереди клиент дёргает
  `gp-live-check` — карточка показывает «⚠️ фактическая цена пасса X ≠ расчётной Y»
  (расчётная = `ceil(amount/0.7)` может врать, если клиент выбрал старый пасс),
  «⛔ не на продаже» и «♻️ уже выкупался в &lt;код&gt;» (донор может уже владеть пассом —
  Roblox не продаст вторую копию). Прямой флоу ботов при выборе пасса с ценой ≠ расчётной
  теперь предупреждает и клиента (строка в «Итого», TG+VK), не только админскую карточку.
- **«⚡ Выкупить всё»**: клиентский цикл по выбранной пачке через существующий серверный
  `purchase` (action в `api/twa/orders`), с рандомной паузой 2–8 c между покупками, прогрессом
  и кнопкой «Стоп». Авто-стоп при нехватке баланса / протухшем cookie. По завершении — отчёт
  (что куплено, суммы, ошибки) в `PurchaseBatch` + Telegram менеджеру.
  **Запись батча прогрессивная (2026-07-05):** `api/twa/purchase-batch` actions
  `start` (батч с `finishedAt=null` до первой покупки) → `item` (после каждой покупки,
  keepalive) → `finish` (финализация + отчёт, keepalive + await). Раньше батч писался одним
  fire-and-forget fetch'ем в конце — закрытие TWA сразу после пачки (смена cookie-аккаунта)
  убивало запрос, отчёт терялся («пришёл 1 раз, а акков было 3»). Батчи без `finish`
  финализирует **свипер TG-бота** (`bots/tg/crons.ts`, каждые 10 мин, порог 15 мин) — отчёт
  приходит админам с пометкой «восстановлен». Легаси-action `save` (всё одним запросом)
  остаётся фолбэком, когда `start` не долетел.
- **История покупок** — аккордеон по `purchaserUsername` (куки-аккаунт, с которого выкуплено).
- **Дедуп в поиске** (2026-07-03): `/api/twa/roblox-account/purchase` (actions
  `search-by-username` + `resolve-gamepass`) сверяет найденные геймпассы с БД
  (`findExistingOrders`, активные статусы без REJECTED) и прикладывает
  `existingOrder: { wbCode, status, orderSource }` к каждому. Карточка результата показывает
  бейдж «📦 уже в заказе <код> · <статус>»; кнопки «Авито» и покупки при активном заказе
  требуют подтверждения (сервер отвечает 409 → UI спрашивает → повтор с `force: true`).

### Привязка геймпасса к заказу (📎 в «Поиск и выкуп»)

Сценарий: бот проспал геймпасс клиента (или заказ отклонён/в ошибке), но менеджер знает ник —
находит геймпасс сам через «Поиск и выкуп» и привязывает его к существующему заказу, не гоняя
клиента по новой.

- На каждой карточке результата поиска — кнопка **📎** → модалка `AttachOrderModal`:
  список заказов в статусах `AWAITING_GAMEPASS` / `REJECTED` / `ERROR` (50 последних,
  `action: "attachable-orders"`). Поиск — **серверный** (debounce 350 мс, `query` от 2
  символов, ищет по коду ВБ / нику / имени / robloxUsername / `adminNote` — в заметке
  живут «вероятные» ники `[НИК? дата]` из раннего захвата — по всей БД): старые заказы
  за пределами первых 50 находятся именно через него, клиентский фильтр — лишь мгновенное
  сужение уже загруженного списка. У каждого заказа — сверка требуемой цены
  `ceil(amount / 0.7)` с ценой геймпасса (✓ зелёная / ⚠️ оранжевая + плашка
  предупреждения, привязать можно и при расхождении — решает менеджер).
- Подтверждение → `action: "attach-gamepass"` (`orderId` + `gamepassId`): пишет канонический
  `gamepassUrl`, статус → `PENDING`, `pendingAt` = now (если заказ не был в PENDING),
  чистит `rejectionReason`, дописывает аудит `[GP-ATTACH дата] url (вручную из TWA)` в
  `adminNote`. Разрешён и повторный вызов на `PENDING`-заказе (замена ссылки, `pendingAt`
  сохраняется).
- Клиент получает то же уведомление, что и от бота: «🎉 Отлично, геймпасс принят!» + код ВБ
  (`notifyGamepassAttached`, TG или VK; номер заявки из текста убран 2026-07-03 — клиентские
  сообщения идентифицируются кодом ВБ, не номером заказа). Отправка **не** fire-and-forget: роут ждёт
  результат, `tgPost`/`vkPost` возвращают фактический успех, и тост менеджеру честный —
  «привязан, клиент уведомлён (TG/VK)» либо «привязан, но уведомление НЕ доставлено — напиши
  клиенту вручную» (типовой случай недоставки: VK error 901 — юзер логинился VK-ом на сайте,
  но никогда не писал сообществу; проверить можно `messages.isMessagesFromGroupAllowed`).

### Слив остатка (`DrainSection` + `api/twa/drain`)

Консолидация «хвоста» баланса донора (напр. 98 R$, которые ничем не выкупить) на аккаунт-**приёмник**
(«мой акк»): цена геймпасса на приёмнике ставится = балансу донора, донор его покупает.

- Второй cookie — `GlobalSettings.drainCookie` (+ `drainAccountName`), геймпасс приёмника —
  `drainGamepassId`. Оба задаются в блоке «⚙️ Настройка» секции «Слив остатка».
- **Автообновление (2026-07-05):** кнопка `↻` рядом с «⚙️ Настройка» перечитывает балансы;
  `donorBalanceAfter`/`drainBalanceAfter` из ответа слива применяются в UI сразу, затем
  полный refetch.
- **Учёт в истории (2026-07-05):** успешный слив пишет `DrainEvent` (донор, приёмник,
  сумма, `source: manual|auto`). GET `/api/twa/drain?events=1` — лёгкий режим только с
  историей сливов (без походов в Roblox). «История покупок» показывает сливы: итог по
  аккаунту = выкупы + сливы, строка «💧 из них слив: N R$» в сводке и в шапке группы,
  строки сливов в раскрытом аккордеоне.
- **Автосписок геймпассов приёмника.** GET `/api/twa/drain` отдаёт `gamepasses[]` аккаунта
  приёмника (`GET apis.roblox.com/game-passes/v1/users/{userId}/game-passes?count=50` по
  `drainCookie`). В «⚙️ Настройка» под ручным вводом ID — тап-список (имя · цена · off если не
  продаётся, ✓ у выбранного); тап = `set-gamepass` с этим ID. Убирает ручной ввод и защищает
  от «подставил чужой геймпасс».
- ⚠️ **Фикс 2026-07-02:** `set-gamepass` писал `drainProductId` в `Int`-колонку, а у новых
  геймпассов ProductId > 2.1 млрд → `ValueOutOfRange` → роут падал немым 500 → в TWA «Ошибка
  сети». Теперь productId не кэшируем (берём из `product-info` при сливе), а POST-роут обёрнут
  в try/catch и возвращает текст ошибки JSON-ом вместо голого 500. `product-info` с прод-
  контейнера доступен (HTTP 200, ~0.4 c) — проблема была не в сети.
- Поток (`action: "drain"`): читаем баланс донора → меняем цену геймпасса приёмника
  (`setGamepassPrice`) → **поллим `product-info`, пока цена не подтвердится** (задержка
  распространения у Roblox) → донор покупает геймпасс той же механикой, что обычный выкуп.
- ✅ **SPIKE закрыт (верифицировано вживую 2026-07-03).** Рабочая смена цены геймпасса:
  1. геймпасс → `placeId` (GET `apis.roblox.com/game-passes/v1/game-passes/{id}/details`) →
     `universeId` (GET `apis.roblox.com/universes/v1/places/{placeId}/universe`);
  2. **`PATCH apis.roblox.com/game-passes/v1/universes/{universeId}/game-passes/{gpId}`**,
     тело — **multipart/form-data** с полями `IsForSale` + `Price` (с заглавной),
     заголовок `X-CSRF-TOKEN`, успех = **204**.
  Грабли: запись **universe-scoped** (сначала резолвим universe); тело обязано быть form-data —
  JSON / merge-patch / json-patch дают **415**; `Content-Type` руками не ставить (fetch сам
  добавит boundary); старый `POST .../game-passes/{id}/details` мёртв (теперь GET-only → 404
  на запись), как и legacy `roblox.com/game-pass/update`. `setGamepassPrice` возвращает
  `via: "universes-patch"`. Комиссия Roblox 30% и pending-заморозка робуксов на приёмнике — как
  у любой продажи геймпасса.
