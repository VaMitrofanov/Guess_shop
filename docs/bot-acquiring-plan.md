# Официальная оплата Т‑Банка в TG- и VK-ботах

> Вопрос владельца 28.07.2026: «эквайринг получен — можно ли продублировать его в ботов,
> чтобы при выборе пака не слать реквизиты вручную, а показывать официальную платёжку?»
>
> **Ответ: да, технически это правильный и недорогой шаг.** Второй интеграции с банком не
> нужно: `Init` уже возвращает `PaymentURL` — обычную HTTPS-ссылку, которую бот отдаёт
> кнопкой. Весь проверенный контур (подпись, webhook, идемпотентность, возвраты, outbox)
> переиспользуется как есть. Работа — не в платёжном ядре, а в трёх местах: чек, согласие
> с офертой и авторизация вызова из бота.
>
> Статус: **план, реализация не начата.** Ждёт решения владельца по §6.

---

## 1. Зачем — цифры, а не ощущения

Сейчас прямой заказ оплачивается вручную: админ жмёт «Отправить QR (СБП)», покупатель
переводит точную сумму и присылает **скриншот**, админ глазами сверяет и подтверждает.

Замер по БД на 28.07.2026:

| Метрика | Значение |
|---|---|
| Прямых заказов (`orderSource=DIRECT`) всего | 34 |
| Из них `COMPLETED` | **3** |
| Застряли в `AWAITING_PAYMENT` / `PAYMENT_PENDING` | **9** |
| За 60 дней: DIRECT TG / VK | 26 / 7 |

Конверсия прямых заказов ≈ **9 %**, и четверть висит именно на шаге оплаты. Ручной СБП-QR —
самое узкое место воронки: покупатель уходит в банк, возвращается, ищет скриншот, ждёт
админа. Официальная платёжка убирает три из четырёх шагов и снимает ручную сверку.

Дополнительно это закрывает фискальный разрыв: **переводы по статическому СБП-QR сейчас
идут мимо ККТ**. Чек по ним не формируется. Перевод прямых заказов на эквайринг делает их
такими же фискально чистыми, как оплату на сайте.

## 2. Что уже готово и переиспользуется без изменений

Это главная причина, почему задача дешёвая:

| Компонент | Файл | Почему подходит как есть |
|---|---|---|
| `Init` с чеком | `src/lib/tinkoff.ts` → `initCanonicalTinkoffPayment` | Возвращает `paymentUrl`; канал вызова ему безразличен |
| Webhook | `src/app/api/webhooks/tinkoff/route.ts` | Проверяет подпись/terminal/сумму; **не содержит ни одной ссылки на `SITE`/`WEB`** — источник заказа ему не важен |
| Возвраты | `src/app/api/twa/payments/refund/route.ts` | Работает от внутреннего `orderId`, дефект чека U7 закрыт |
| Outbox | `bots/shared/payment-outbox.ts` | Топики `payment.confirmed`, `payment.refund.recorded` уже доставляются в TG |
| Цены | `bots/shared/retail-pricing.ts` | `retail-direct-v2` — **один модуль на TG, VK и сайт**. Динамическая цена и клиентский курс совпадают во всех каналах |
| Пользователь | `User` в Prisma | Клиент бота — уже полноценный `User` (371 TG + 218 VK), поэтому rollout-гейт по `User.id` применим напрямую |
| Kill switch | `SITE_ACQUIRING_ENABLED` | Аварийное выключение работает и для ботов |

## 3. Что придётся сделать — четыре настоящих препятствия

### 3.1 🔴 Чеку нужен email или телефон, а у клиентов бота их нет

`buildCanonicalReceipt` (`src/lib/tinkoff.ts:162`) кладёт в чек **только `Email`**.
По 54-ФЗ электронный чек нужно отправить на email **или** телефон — одно из двух обязательно.

Замер по БД: из **589** клиентов ботов email есть у **0**. Всего в базе 5 адресов, и все —
веб-аккаунты.

Значит, в поток бота добавляется **один обязательный шаг**: спросить email или телефон
перед оплатой и сохранить в `User`. Варианты:

- **email** — минимальная правка: `buildCanonicalReceipt` уже умеет только его;
- **телефон** — привычнее аудитории бота (дети/подростки часто без почты), но требует
  расширить `buildCanonicalReceipt` полем `Phone` и добавить нормализацию в `+7XXXXXXXXXX`.

Рекомендация: **принимать оба, требовать одно**, и запоминать в профиле, чтобы спрашивать
только на первом заказе. Это решение владельца — см. §6, вопрос О1.

### 3.2 🔴 Ядро заказа жёстко помечено как веб

`createCanonicalWebOrder` (`src/lib/canonical-web-order.ts`) проставляет константы:

- `platform: "WEB"` (строка 204),
- `orderSource: "SITE"` (строка 222),
- `publicOrderId` вида `WEB-…` (строка 97).

Если вызвать её из бота как есть, заказы из TG/VK станут неотличимы от сайтовых: сломается
аналитика, admin-фильтр по источнику и отчёты по прибыли. Нужно параметризовать эти три
значения (`TG`/`VK`, `DIRECT`, префикс `TG-`/`VK-`), **не трогая** остальную транзакцию —
резервирование quote, бонусы и запись согласия должны остаться общими.

### 3.3 🔴 Согласие с офертой нужно собрать в боте

Сейчас `agreedToTerms` приходит из чекбокса на сайте, а `ConsentEvidence` хранит версию
оферты, IP и user-agent. У бота IP покупателя нет.

Нужен эквивалент: явная кнопка «Согласен с офертой» перед первой оплатой + запись
`ConsentEvidence` с каналом (`TG`/`VK`), `tgId`/`vkId` и версией оферты вместо IP.
Без этого оплата в боте юридически слабее оплаты на сайте.

### 3.4 🟡 Боту нужен авторизованный способ вызвать `Init`

`POST /api/orders/create` требует **сессию next-auth** (строки 59–66) — у бота её нет.
Нужен отдельный роут (например `POST /api/bot/orders/create`) с серверной аутентификацией
бота. В репозитории уже есть рабочий образец такой схемы — HMAC на общем секрете
(`TWA_LINK_SECRET`, `bots/shared/twa-link.ts`); её и следует повторить, а не изобретать новую.

Роут обязан **переиспользовать** `siteAcquiringDecision`, лимитер и валидацию геймпасса —
иначе появится вторая, более слабая дверь к деньгам.

## 4. Как это выглядит для покупателя

```
Покупатель в боте:  выбирает пакет 1000 R$ → 995 ₽ (курс 0,995 ₽/R$)
Бот (первый заказ): «Куда прислать чек?» → email/телефон
                    «Согласен с офертой?» → [Согласен]
Бот → сайт:         POST /api/bot/orders/create (HMAC бота)
Сайт → Т‑Банк:      Init (сумма из retail-direct-v2, Receipt, NotificationURL)
Сайт → бот:         paymentUrl
Бот → покупателю:   [💳 Оплатить 995 ₽]  ← официальная платёжка Т‑Банка
Покупатель:         платит картой/СБП, чек приходит на email/телефон
Т‑Банк → webhook:   CONFIRMED (подпись проверена)
Outbox → бот:       карточка админу + сообщение покупателю «оплата принята»
```

Скриншот, ручная сверка и кнопка «Отправить QR» из потока исчезают.

Технические замечания по кнопке:

- **TG** — inline-кнопка с `url`, платёжка открывается во встроенном браузере. Рядом
  обязательно дублировать ссылку текстом: 3DS-редиректы в in-app WebView иногда обрывают
  возврат, и покупателю нужен путь «открыть в обычном браузере».
- **VK** — inline-клавиатура помнит лимиты: **≤10 кнопок, ≤6 рядов, ≤5 в ряду**, иначе VK
  молча отвечает «Произошла ошибка» (это уже ломало прямые заказы 04.07).
- **`SuccessURL`/`FailURL`** сейчас ведут на `/payment/status`. Для бота лучше добавить
  deep link обратно в диалог (`t.me/RobloxBankBot?start=paid_<order>`), чтобы покупатель
  не оставался в браузере.

## 5. Почему не «родные» платежи Telegram

У Telegram есть `sendInvoice` со своими провайдерами. Этот путь **не рекомендуется**:

1. Он создаёт **второй фискальный контур** — чек уходит через `provider_data` Telegram, а
   не через наш `Receipt`. Решение владельца от 16.07 прямо гласит: фискальный контур
   выбирается **один** (сервис «Чеки» Т‑Банка), параллельная касса не подключается.
2. Возвраты пошли бы мимо `/v2/Cancel` и мимо `PaymentRefund` — вся логика U7 и защита от
   двойного возврата не применились бы.
3. VK такого механизма всё равно не даёт, то есть один канал остался бы на `PaymentURL` —
   пришлось бы поддерживать два способа приёма денег вместо одного.

`PaymentURL` работает одинаково в TG, VK и вебе и переиспользует уже принятый в бою контур.

## 7. Порядок работ, когда будет «го»

Оценка — при условии, что §6 закрыт. Шаги строго последовательные.

| Шаг | Суть | Критерий приёмки |
|---|---|---|
| Б1 | Параметризовать `createCanonicalWebOrder` (platform/source/префикс) | Веб-заказ по-прежнему `WEB-…`/`SITE`; тест на оба источника |
| Б2 | `Phone` в `buildCanonicalReceipt` + нормализация (если О1 = телефон) | Контракт-тест: чек валиден и с email, и с телефоном |
| Б3 | Сбор контакта и согласия в TG-боте, запись `ConsentEvidence` | Повторный заказ контакт не переспрашивает |
| Б4 | `POST /api/bot/orders/create` с HMAC-аутентификацией бота | Запрос без подписи → 401; гейт и лимитер применяются |
| Б5 | Кнопка «Оплатить» в TG + deep link возврата | Заказ доходит до `PAYMENT_PENDING` с `paymentUrl` |
| Б6 | Сообщение покупателю из outbox по `payment.confirmed` | Оплата → покупатель получает подтверждение без участия админа |
| Б7 | Owner-E2E в TG: оплата → чек → возврат | Суммы UI = quote = Init = чек = БД; возврат даёт корректный чек |
| Б8 | То же для VK (с учётом лимитов клавиатуры) | Прямой заказ в VK оплачивается официальной платёжкой |
| Б9 | Убрать/спрятать «Отправить QR (СБП)» по решению О2 | В потоке остаётся один способ оплаты |

**Волна 2 сайта (F4–F7) идёт раньше:** F4 (тупик чекаута после неудачного `Init`) — это
общий дефект платёжного ядра, и в боте он проявится точно так же. Чинить его дважды не надо.

## 8. Риски

| Риск | Митигация |
|---|---|
| Вторая дверь к `Init` слабее первой | Роут бота обязан вызывать тот же `siteAcquiringDecision`, лимитер и валидацию геймпасса |
| Чек уходит на чужой/опечатанный контакт | Подтверждение контакта в боте перед первой оплатой; показать его в карточке заказа |
| Несовершеннолетний покупатель платит картой | Гейт B5 (возрастная политика) общий с сайтом и остаётся открытым |
| 3DS в TG WebView обрывает возврат | Дублировать ссылку текстом + deep link возврата в бот |
| Заказы бота смешаются с сайтовыми в отчётах | Шаг Б1 обязателен и идёт первым |
