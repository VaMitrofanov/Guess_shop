Продуктовая модель (фиксация владельца, 2026-07-10): **таблица = БД заказов Антона**.

соответствие (валидность ГП, цена vs номинал) — что расходится, **не выкупается, а
помечается в таблице** (`статус=«ошибка»` + причина в комментарии). Выкупилось →
`готово`; `в ожидании` = геймпасс готов к проверке и выкупу.

## Зафиксированные правила Антона

- Валюта баланса партнёра — только `USDT`.
- Цена задачи хранится в грязных `R$` (`priceRobux` / `purchasePriceRobux`), но ledger
  списывается в `USDT`.
- Формула списания: `round(priceRobux * robuxRateUsdtPer1000 / 1000, 2)`.
- Текущий курс Антона: `5.05 USDT / 1000 R$`; курс хранится в `Partner.robuxRateUsdtPer1000`
  и меняется action `set-rate`.
- Стартовый платёж: `150 USDT`.
- Выкуп по XLSX `selected-roblox-orders-2026-07-09 10_31_39 (1).xlsx`: 8 строк,
  `19 106 R$` грязными = `96.49 USDT`.
- Текущий расчётный остаток после стартового выкупа: `53.51 USDT`.

## Текущий партнёрский поток

Первый реальный кейс — партнёр **«Антон»**.

Текущий MVP-процесс:

1. Антон переводит деньги в крипте.
2. Антон заполняет строки геймпассов в Google-таблице (или отдаёт `.xlsx`).
3. На его деньги команда покупает cookie-аккаунты.
4. Менеджер жмёт **«Синхронизировать»** в TWA (**«Аккаунт» → `Антон`**) — сервер тянет
   строки `в ожидании` из таблицы в задачи; либо загружает `.xlsx`, либо заводит задачу вручную.
5. Менеджер выкупает каждый геймпасс через общий donor-cookie или вручную помечает задачу
   как **«Готово»**.
6. Успешный выкуп/«Готово» автоматически пишет `готово` в колонку `D` строки Google Sheet;
   при ошибке причина уходит в `E`, а строка остаётся `в ожидании` для повторной попытки.

Цель следующего этапа: batch-выкуп только по задачам партнёра и отдельный отчёт партнёру,
чтобы «Антон» стал самодостаточным партнёрским рабочим местом.

## Что уже готово в продукте

Текущая система уже покрывает большую часть **операционного ядра** будущего B2B-модуля:

- TWA-аутентификация и админский UI уже есть.
- `BossrobuxScreen` умеет искать геймпассы по нику/ID/URL и покупать их через cookie.
- Серверный purchase-flow уже умеет:
  проверять cookie, получать CSRF, делать покупку, возвращать актуальный баланс.
- Есть live-check цены/доступности и дедуп по уже использованным геймпассам.
- Есть пакетные покупки и история по cookie-аккаунтам.
- Есть ручное создание заказов и операционный UX для менеджера.
- Shared helper `src/lib/roblox-buyout.ts` уже содержит resolve геймпасса и покупку через
  `.ROBLOSECURITY`, чтобы B2B не копировал retail purchase-код.
- В Prisma добавлены `Partner`, `PartnerBuyoutTask`, `PartnerLedgerEntry` и отдельные enum-ы
  партнёрского контура.
- Есть TWA route `GET/POST /api/twa/partners/[slug]/tasks` для server-MVP:
  создать задачу, загрузить `.xlsx`, синхронизировать Google Sheets, пополнить ledger,
  сменить курс, отменить задачу, отметить готовой, купить через cookie.
- XLSX upload принимает первый лист файла, парсит `ГП/GP`, `Ник`, `Номинал`, создаёт задачи
  `externalSource=XLSX_UPLOAD`, ограничивает файл `5 MB` и `300` строк, а повторную загрузку
  того же файла/строки/геймпасса пропускает по idempotency.
- Google Sheets sync (`action=sync-google-sheets` + opportunistic sync на GET с TTL 60 с)
  сканирует date-листы боевой таблицы, импортирует строки `в ожидании` в
  `PartnerBuyoutTask` (`externalSource=GOOGLE_SHEETS`), резолвит геймпасс, идемпотентен по
  `partnerId+externalSource+externalRowId`, а write-back пишет `готово` в `D` / ошибку+причину в `D`+`E`.
- Каждый прогон sync пишет `PartnerImportRun` (счётчики created/updated/failed/skipped +
  диагностика фильтра по листам) для статуса в TWA и защиты от параллельных sync.

Вывод: для **внутреннего B2B-модуля** база уже сильная. Не хватает не механики выкупа, а
**отдельного контекста партнёра**: импорт задач, учёт его денег, статусы строк, отчётность,
изоляция от клиентских заказов.

## Что пока не готово

Этап 5.5 (П1–П9) **полностью закрыт** 2026-07-10. Оставшееся:

- отдельная аналитика и отчёт партнёру;
- production-hardening race-condition между ручным и batch-выкупом (одиночный выкуп уже
  защищён атомарным `READY/FAILED -> PURCHASING`, sync — TTL + `PartnerImportRun status=RUNNING`);
- серверный durable-batch (аналог retail `purchase-batch` со свипером) — клиентская
  оркестрация уже обкатана (П4);
- серверные агрегатные счётчики при >100 задач (сейчас считается по срезу `take: 100`);
- обобщение из single partner `anton` в полноценный multi-partner SaaS.

## Архитектурная позиция

### Что делать правильно

Раздел **«Антон»** надо строить как первый instance **generic partner flow**, даже если
в интерфейсе он пока будет называться конкретно `Антон`.

### Что делать не надо

Не стоит запихивать это в `WbOrder` через костыли вроде:

- фиктивных `wbCode`;
- пустых `userId`;
- `orderSource=MANUAL` для партнёрских задач;
- ручных заметок вместо нормальных статусов.

`WbOrder` сейчас заточен под розничный коридор: WB-коды, боты, уведомления клиенту,
состояния `AWAITING_GAMEPASS/PENDING/COMPLETED`. Для партнёра это другой bounded context.

### Этап 3. Сделать серверный API партнёрского контура

Статус: сделан server route под первого партнёра (`[slug]` = `anton`):

- `GET /api/twa/partners/[slug]/tasks` — состояние партнёра, задачи, summary, последние
  ledger-записи, `googleSync` (статус/lastSyncAt/latestRun) и `importRuns`; opportunistic
  Google Sheets sync (TTL 60 с) с 2026-07-10 (Этап 5.6) не блокирует ответ — планируется
  в фон через `after()`, в ответе флаг `syncScheduled`.
- `POST /api/twa/partners/[slug]/tasks` с `action=create-task` — ручное создание задачи по
  ID/URL геймпасса.
- `action=import-xlsx` — ручная загрузка `.xlsx` с колонками `ГП/GP`, `Ник`, `Номинал`.
- `action=sync-google-sheets` — принудительный (`force`) Google Sheets sync + write-back.
- `action=ledger-topup` — пополнение партнёрского баланса в USDT.
- `action=set-rate` — смена курса партнёра (`USDT / 1000 R$`) для следующих списаний.
- `action=cancel-task` — отмена незавершённой задачи.
- `action=mark-done` — ручное закрытие задачи с отдельным списанием ledger + write-back `готово`.
- `action=purchase-task` — покупка через общий Roblox cookie-helper с переходом
  `READY/FAILED -> PURCHASING -> DONE/FAILED` + write-back `готово`/ошибки.

Требования к API:

- idempotent sync;
- атомарный переход `READY -> PURCHASING -> DONE/FAILED`;
- защита от двойного выкупа одной и той же строки;
- запись фактической цены и cookie-аккаунта;
- честные ошибки, если cookie протух, пасс не продаётся или AlreadyOwned.

MVP route не обращается к `WbOrder`. Денежный учёт идёт через `PartnerLedgerEntry` в USDT;
перед ручным закрытием и покупкой R$-цена задачи конвертируется по текущему курсу партнёра,
проверяется USDT-баланс, а повторное `BUYOUT`-списание по задаче блокируется.

Важно по cookie: отдельного donor-cookie для Антона пока нет. Покупка использует общий
`.ROBLOSECURITY` из `GlobalSettings.robloxCookie`, тот же источник, что и экран `Свои`.
Если понадобится отдельный donor-аккаунт партнёра, это надо добавить отдельным полем/настройкой,
не смешивая с ledger и задачами партнёра.

путь импорта в ту же модель `PartnerBuyoutTask`. Ниже — исходный контракт и план, по которому
собрана реализация; пункты плана считать выполненными, если явно не отмечено иначе.

Боевой контракт Google Sheets для Антона (обновлён **2026-07-10**; колонки `A:E` после
удаления столбца `B` и миграции П9):

- `spreadsheetId`: `1jzWZZ_AeM0IMyHaljaLBei0hu_zDwktiysbgGt324rs`;
- `sheetName` не фиксируется: каждый лист = отдельная дата, sync должен сканировать листы
  с датами, а не привязываться к одному табу;
- импортировать только строки, где колонка `C` не пустая, а колонка `D` ровно
  `в ожидании`;
- маппинг колонок (после П9): `A` = ник, `B` = GP/gamepass id или URL, `C` = номинал/цена,
  `D` = статус (чипы `в ожидании` / `готово` / `ошибка`), `E` = **«комментарий»** —
  причина ошибки/предупреждение по строке;
- чип `ошибка` в `D` автоматически подсвечивает строку красным (условное форматирование
  на стороне таблицы, коду делать ничего не надо — важно писать значение ровно `ошибка`);
- source fields: `nickname -> A`, `gamepass -> B`, `amount -> C`;
- write-back при успешном выкупе: `готово` в `D`, `E` очищается, и **той же атомарной
  операцией** на `A:D` строки ставится `addProtectedRange` (Этап 5.8: сотрудники не
  могут править/удалять выполненную строку; редакторы — владелец + сервисный аккаунт);
- write-back при **row-level ошибке** (невалидный/несуществующий ГП, «не продаётся»,
  ошибка покупки со стороны Roblox): `ошибка` в `D` + причина в `E`; строка выходит из
  фильтра `в ожидании`, пока Антон её не исправит и не вернёт `D` в `в ожидании`;
- **временные** ошибки (сеть/Roblox API недоступен) и **внутренние** (протухший cookie,
  нехватка Robux на доноре, нехватка USDT-баланса партнёра) чип `ошибка` НЕ ставят:
  `D` остаётся `в ожидании` (для ретрая), причина — только комментарием в `E`
  (а «cookie не задан» в таблицу не пишется вовсе);
- расхождение цены (номинал `C` vs live-цена ГП) — **ошибка строки** (решение владельца
  2026-07-10, ужесточение первоначального «предупреждение, не ошибка»): задача становится
  `FAILED`, write-back ставит `D=«ошибка»` + `E=«Цена ГП: Y R$, в таблице X R$»`. Антон
  правит `C` (или цену ГП) и возвращает `D` в `в ожидании` — строка реимпортируется и
  задача снова `READY`. Купить mismatch-задачу из TWA по-прежнему можно через confirm;
- pending-строка с пустым номиналом `C` игнорируется **только** если по ней нет ни задачи,
  ни ГП в `B` (шаблонные строки с предвыставленным чипом `в ожидании` — их на листе ~70).
  Если задача есть или в `B` есть ГП — это ошибка строки: `FAILED` + `D=«ошибка»` +
  `E=«Пустой номинал в колонке C»` (раньше такие строки молча пропускались и задача
  «зомбировалась» со старыми данными);
- удаление строки Антоном = удаление заказа: и очистка ячеек `A:C` (чип `D` может остаться
  предвыставленным), и физическое исчезновение строки из скана **удаляют задачу из TWA
  полностью** (guard: при существующих ledger-записях задача не удаляется, а отменяется
  с заметкой). Уточнение П10 (2026-07-10): невыкупленная `CANCELLED` без ledger при
  пропаже строки тоже удаляется; `DONE` при пропаже строки сохраняет списание и получает
  бейдж «удалена из таблицы». `PURCHASING` не трогаем; очищенная строка выполненной задачи
  не получает повторный write-back `готово` — Антон мог очистить её под переиспользование;
- отмена задачи менеджером из TWA пишется в таблицу: `D=«ошибка»` + `E=«Отменено
  менеджером»`. Возврат `D` в `в ожидании` после успешного write-back реанимирует задачу
  (явный повторный заказ); если write-back упал, отмена дописывается следующим sync.

Целевой UX автообновления: Антон меняет строки в Google Sheet, менеджер открывает или
обновляет вкладку `Аккаунт -> Антон`, сервер подтягивает свежие строки, нормализует их в
`PartnerBuyoutTask`, и TWA показывает уже готовые задачи для выкупа. Клиентский TWA не должен
ходить в Google напрямую: Google API живёт только на сервере, а интерфейс работает с задачами
из БД.

#### План реализации Google Sheets sync

1. **Google Sheets client**
   - Добавить серверный helper `src/lib/google-sheets.ts`.
   - Читать `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON` и создавать service-account client только
     на сервере.
   - Поддержать операции:
     `listSheets(spreadsheetId)`, `readSheetRows(spreadsheetId, sheetTitle, range)`,
     `writeCells(spreadsheetId, updates[])`.
   - Не логировать JSON credentials, private key, access token и полный raw response Google.
   - Возвращать короткие typed-ошибки: нет env, нет доступа к таблице, rate limit,
     некорректная структура листа.

2. **Выбор листов**
   - Использовать `spreadsheets.get` и брать все видимые tabs.
   - Не зависеть от `Partner.googleSheetTab`: у Антона каждый лист = дата.
   - На первом релизе сканировать все листы; если таблица разрастётся, добавить фильтр
     "последние N листов" или курсор по `PartnerImportRun`.
   - Сохранять в `sheetRaw` `spreadsheetId`, `sheetTitle`, `rowNumber`, `range`, исходные
     значения `A:E` и время sync.

3. **Парсинг строк**
   - Читать диапазон минимум `A:F`.
   - Пропускать заголовки/пустые строки.
   - Брать в импорт только строки, где:
     `D` не пустая и `E.trim().toLowerCase() == "в ожидании"`.
   - Маппинг:
     `A -> robloxUsername` или исходная partner info,
     `C -> gamepassId/gamepassUrl`,
     `D -> priceRobux`,
     `E -> sourceStatus`,
     `F -> sourceError`.
   - `D` парсить как грязную цену в R$; пробелы, `R$`, `rbx`, запятые и неразрывные пробелы
     надо нормализовать до числа.
   - `C` принимать как чистый ID, URL `game-pass`, URL `gamepasses` или текст с ID внутри.
   - Невалидную строку не превращать в READY-задачу: записать диагностическую ошибку в `E`
     и сохранить/обновить задачу как `FAILED` или оставить без задачи, если нет стабильного
     идентификатора геймпасса.

4. **Идентичность и идемпотентность**
   - `externalSource = GOOGLE_SHEETS`.
   - Базовый `externalRowId`: `${spreadsheetId}:${sheetTitle}:${rowNumber}`.
   - В `sheetRaw` дополнительно хранить `gamepassRaw`, `gamepassId`, `rowHash`.
   - Повторный sync той же строки обновляет существующую задачу, а не создаёт дубль.
   - Если в строке до выкупа поменяли `C` или `D`, задача может обновиться только в статусах
     `NEW`, `READY`, `FAILED`. Для `PURCHASING`, `DONE`, `CANCELLED` менять цену/геймпасс
     нельзя: это уже операционное событие, требующее ручной проверки.
   - Если строку перенесли на другой лист или другую строку, это новая внешняя строка.
     Автоматически "склеивать" переносы по одному gamepassId нельзя без отдельного product
     rule, иначе можно случайно потерять повторный выкуп того же пасса.

5. **Создание готовых данных для выкупа**
   - Для валидной строки sync должен резолвить gamepass через `resolveGamepass`.
   - В задачу писать `gamepassId`, `gamepassUrl`, `productId`, `sellerId`, `sellerName`,
     `priceRobux`, `purchasePriceRobux`, `robloxUsername`/source info.
   - Если live-price Roblox отличается от `D`, задача остаётся видимой, но получает ошибку
     или warning в `error`/`note`; покупать такую задачу можно только после ручного решения
     или явного правила допуска.
   - Статус валидной задачи: `READY`. Статус строки с ошибкой парсинга/резолва: `FAILED`
     с текстом, понятным оператору и пригодным для записи в `E`.
   - На импорт задача не списывает USDT. Ledger списывается только при `purchase-task` или
     `mark-done`, как сейчас.

6. **Точка запуска sync**
   - Добавить серверный action `sync-google-sheets` в
     `POST /api/twa/partners/[slug]/tasks`.
   - Добавить opportunistic sync в `GET /api/twa/partners/anton/tasks`: если таблица
     подключена и последний sync старше короткого TTL (например 30-60 секунд), сервер
     запускает sync перед ответом или сразу после ответа через bounded background promise.
   - В TWA добавить кнопку `Синхронизировать` и авто-refresh при входе во вкладку `Антон`.
   - Клиентский polling делать осторожно: не чаще TTL, с отображением `lastSyncAt`,
     `syncInProgress`, `imported/updated/failed`.
   - Если Google недоступен, GET всё равно должен вернуть последние задачи из БД и отдельный
     блок ошибки sync, а не ломать весь экран.

7. **Журнал sync**
   - Для первого релиза можно хранить метаданные в `Partner.notes` или в `sheetRaw`, но
     правильнее добавить `PartnerImportRun`:
     `partnerId`, `source`, `startedAt`, `finishedAt`, `status`, `spreadsheetId`,
     `sheetCount`, `rowCount`, `createdCount`, `updatedCount`, `failedCount`, `error`.
   - `PartnerImportRun` нужен для отладки, защиты от параллельных sync и честного статуса
     в TWA.
   - Параллельные sync одного партнёра должны блокироваться advisory lock или короткой
     DB-блокировкой на `PartnerImportRun status=RUNNING`.

8. **Write-back в Google Sheet**
   - После успешного `purchase-task` или `mark-done` писать `готово` в колонку `D` той же
     строки (`sheetTitle + rowNumber` из `sheetRaw`) и очищать/оставлять `E` по принятому
     правилу. Предпочтительно очищать старую ошибку только если операция реально успешна.
   - При ошибке покупки писать короткую причину в `E`; `D` оставить `в ожидании`, чтобы
     строка продолжала попадать в sync после исправления.
   - Write-back должен быть best-effort, но durable: если покупка прошла, а запись в Google
     не прошла, задача остаётся `DONE`, получает `note/error` про pending write-back, а
     повторный sync/write-back retry должен дописать `готово`.
   - Нельзя перезаписывать `E=готово` ошибкой от старого запуска. Перед записью ошибки
     проверять, что внутренняя задача ещё не `DONE`.

9. **TWA-изменения**
   - Блок Google Sheets должен показывать не только `Подключено`, но и `lastSyncAt`,
     результат последнего sync, количество строк `READY/FAILED/DONE` из Google и кнопку
     `Синхронизировать`.
   - Список задач должен визуально отличать source `GOOGLE_SHEETS` от `XLSX_UPLOAD` и
     `MANUAL`.
   - В карточке задачи показывать `sheetTitle:rowNumber` и, если возможно, ссылку на строку
     Google Sheet.
   - После sync TWA должен обновлять список задач без перезагрузки всего приложения.
   - Ошибки строк показывать рядом с задачами и в summary, чтобы оператор видел, что именно
     надо поправить в таблице.

10. **Проверки перед продом**
    - Таблица без доступа сервисного аккаунта -> понятная ошибка, старые задачи доступны.
    - Пустая таблица -> 0 imported, без падения.
    - Несколько date-листов -> строки со всех листов попадают в задачи.
    - Повторный sync -> дублей нет.
    - Изменение `B/C` до выкупа -> READY-задача обновляется.
    - Изменение `B/C` после DONE -> задача не мутирует, появляется ручной warning.
    - Успешная покупка -> задача DONE, ledger списан один раз, `D=готово`.
    - Ошибка покупки -> ledger не списан, задача FAILED, `E` заполнена.
    - Google write-back падает после успешной покупки -> задача DONE сохраняется, retry
      дописывает `готово`.
    - Двойной тап `Купить` и параллельный batch -> только один переход в `PURCHASING/DONE`.

Что подключено для Google Sheets:

- `spreadsheetId` таблицы известен;
- service-account JSON заведён в env `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`;
- env `ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` заведён;
- таблица расшарена на service-account email;
- правило чтения/записи статусов зафиксировано и реализовано в коде.

Серверный клиент — `src/lib/google-sheets.ts` (service-account JWT → OAuth token с кэшем,
`listGoogleSheets` / `readGoogleSheetRows` / `batchUpdateGoogleSheetValues`, typed
`GoogleSheetsError`, credentials не логируются). Сам sync/parse/idempotency/write-back —
в `syncPartnerGoogleSheets` / `writeBackPartnerTask` внутри роута `[slug]/tasks`.

`GET /api/twa/partners/[slug]/tasks` при upsert партнёра заполняет `Partner.googleSheetId`
и `Partner.googleSheetUrl` из `ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` (статус подключения),
планирует фоновый opportunistic sync (TTL 60 с, `after()`; см. Этап 5.6) и отдаёт
`googleSync`/`importRuns` в TWA.

#### П1. Автообновление экрана «Антон» — P0

Сервер уже готов (opportunistic sync на GET с TTL 60 с), не хватает клиента:

- разделить в `PartnerAntonSection` первичную загрузку (skeleton «Загружаю…») и фоновый
  refresh: фоновый не показывает скелетон, не сбрасывает заполняемые формы и busy-операции;
- вынести «обновлено N мин назад» (из `lastSyncAt`) в шапку раздела, а не только в блок
  Google Sheets;
- опционально (если polling начнёт упираться в латентность): перенести opportunistic sync
  на after-response bounded background promise, чтобы GET не ждал скан всех листов.

#### П2. Расхождения и ошибки — наверх — P0 — ✅ сделано 2026-07-10

Было: mismatch писался строкой в `note` («Номинал из Sheets: X R$, цена GP: Y R$») и
рисовался серым 13px — оператор его не видел.

Реализовано:

#### П3. Реконсиляция ручных статусов из таблицы — P0 — ✅ сделано 2026-07-10

Было: sync импортировал только строки `D=”в ожидании”`; смена `D` руками никак не влияла
на уже созданные задачи. Реализован recon-проход в sync: для каждой прочитанной строки с
задачей `GOOGLE_SHEETS + externalRowId` в статусе `NEW/READY/FAILED`:

- `D=”готово”` вручную → задача закрывается: `DONE` + `sheetRaw.closedFromSheet=true`,
  **без автосписания USDT** (движение денег из ячейки, которую редактирует сам партнёр, не
  делаем); в списке бейдж «из таблицы»; `doneRobux` в summary считается **без**
  `closedFromSheet`. Быстрое действие «Списать» на таких задачах — **отложено владельцем**
  (2026-07-10), вернёмся позже;
- `D=”ошибка”` (новый чип): если задача уже `FAILED` — это наш же write-back, не трогаем;
  если `NEW/READY` — ручная пометка, задача становится `FAILED` с текстом из `E`
  и `sheetRaw.errorFromSheet=true`;
- `D` = другой статус или очищен → `CANCELLED` + note «Строка вышла из ожидания:
  статус „X”» + `sheetRaw.cancelledFromSheet=true`;
- возврат `D` в `в ожидании` **реанимирует** задачу, отменённую реконсиляцией
  (`cancelledFromSheet`), обычным импортом; ~~ручные отмены из TWA остаются отменёнными~~
  **изменено П8**: отмена менеджера теперь тоже реанимируется, если её write-back дошёл
  до таблицы (`cancelledByManager` + `cancelWriteBackAt`) — Антон видел отмену и явно
  вернул строку в работу. Без успешного write-back отмена остаётся финальной (защита от
  race, когда Google был недоступен);
- строка исчезла из скана → **задача удаляется из TWA полностью** (изменено П8; раньше —
  `CANCELLED` «Строка удалена из таблицы»), но **только** если скан полный (guard: не
  срабатывает при обрезке `GOOGLE_MAX_SHEETS` / `GOOGLE_MAX_ROWS_PER_SHEET`; ошибка чтения
  листа роняет весь прогон до recon-фазы). Guard денег: при существующих ledger-записях
  задача не удаляется, а отменяется с заметкой.
  Если исчез целый лист (удалён/скрыт/переименован) — задачи НЕ трогаются, ставится
  конфликт-метка «Лист не найден — проверь вручную»;
- защита от сдвига нумерации (вставка/удаление строк выше): перед закрытием/отменой
  `gamepassId` из `C` сверяется с задачей; при несовпадении строка не трогается, в
  `sheetRaw.conflict` пишется «строка сместилась…» (warning-блок в карточке, счётчик
  «конфликты» в сводке);
- обратный случай покрыт как и раньше: внутренний `DONE` + `E` вернули в «в ожидании» →
  sync пере-пишет `готово` (существующий skip-путь);
- итоги реконсиляции пишутся в `diagnostics.reconciliation` у `PartnerImportRun`
  (closed/failed/cancelled/deleted/revived/conflicts) и видны в TWA строкой «Из таблицы»
  в блоке Google Sheets.

#### Приёмка (чек-лист живой проверки)

- Антон ставит `готово` в `D` руками → в течение TTL задача закрывается (`DONE`)
  **без** списания USDT, с бейджем «из таблицы» (✅ П1 — silent-refresh 75 с).
- Мы ставим `ошибка` в `D` write-back'ом → строка у Антона красная, причина в `E`;
  Антон исправляет и возвращает `в ожидании` → задача реанимируется в `READY`.
- Антон добавляет строку в таблицу → задача появляется в открытом TWA сама (✅ П1).
- Расхождение `C` vs live-цены видно warning-блоком в карточке и счётчиком в сводке;
  задача `FAILED`, строка у Антона красная (`D=«ошибка»`, причина в `E`); покупка такой
  задачи требует подтверждения; после исправления `C` и возврата `D` в `в ожидании`
  задача снова `READY` (П8).
- Антон очищает/удаляет строку → задача исчезает из TWA полностью; очищенная строка
  `DONE`-задачи не получает обратно `готово` (П8).
- Менеджер жмёт «Отмена» в TWA → в строке Антона `D=«ошибка»` + `E=«Отменено менеджером»`;
  возврат `D` в `в ожидании` реанимирует задачу (П8).
- Pending-строка с пустым `C`, но с ГП/задачей → `FAILED` + `D=«ошибка»`, зомби со старым
  `sheetRaw` не остаётся (П8).
- «Выкупить всё» покупает только пачку под баланс, «Стоп» не теряет купленное, отчёт
  сходится с write-back'ами в таблице и ledger-списаниями (✅ П4).
- `DONE`-задачи не раздувают экран: активный список короткий, история пагинирована,
  счётчики сводки верны при >100 задач (✅ П5; серверные агрегаты — когда задач >100).
- Ни одного текста <14px в карточках (проверка на iPhone 15 Pro Max; ✅ П6).
- Удаление строки из листа не отменяет чужую задачу при сдвиге нумерации (конфликт
  помечается, а не закрывается молча).
- Повторный sync без изменений в таблице не передвигает задачи в списке
  (`updatedAt` не трогается, в items — `Без изменений`).

#### Ультра-ревью логики/воркфлоу/UX (2026-07-10) — найденные баги и тупики

Статус: **всё закрыто 2026-07-11** (кроме №13 — принятый риск). Как закрывалось:
№1 и №2 — Этапом 5.7 (B2 и A3); №3–№9, №11 — пачкой фиксов 11.07 (см. «Итог» после
списка); №10 — в Блоке E 5.7; №12 — частично 5.7 B1 (счётчики статусов и «Выкуплено»
переведены на DB-агрегаты, `reservedUsdt`/`mismatches`/`conflicts` пока по срезу 100).
Ниже — исходные формулировки находок.

1. **[HIGH · тупик воркфлоу] Переиспользование строки после `DONE` молча «выполняет» новый
   заказ.** В sync ветка «строка `в ожидании` + существующая задача `DONE`» безусловно
   пере-пишет `D=«готово»` и очистит `E`, не сверяя содержимое строки (`route.ts`, ветка
   `existing?.status === "DONE"`). Сценарий: Антон очищает строку выполненного заказа
   (задача `DONE` намеренно не удаляется — «под переиспользование»), вписывает туда **новый**
   заказ и ставит `в ожидании` → ближайший sync ставит новому заказу `готово`; он никогда
   не будет выкуплен, а у Антона выглядит выполненным. Тихая потеря заказа. Фикс: в
   `DONE`-ветке сверять `rowHash`/`gamepassId` со старым `sheetRaw`; при расхождении —
   конфликт-метка (или новая задача), а не write-back `готово`.
2. **[MEDIUM · зомби] Очистка строки с `D=«ошибка»` оставляет вечную `FAILED`-задачу.**
   `rowCleared`-ветка пропускает строки с `D=«готово»/«ошибка»`, а реконсиляция для
   `ошибка`+`FAILED` ничего не делает. Если Антон очистил `A:C` строки-ошибки, не сбросив
   чип `D`, задача остаётся в активном списке и в счётчике «Проблемы» навсегда (лечится
   только возвратом `D` в `в ожидании`). Фикс: при пустых `A:C` и `D=«ошибка»` удалять
   задачу так же, как при пустом/`в ожидании` `D`.
3. **[MEDIUM · UX-тупик] Залипание фильтра задач.** Чипы `Все/Ошибки/Расхождения` рендерятся
   только при `errorCount>0 || mismatchCount>0`. Если фильтр активен, а счётчик обнулился
   (silent-refresh закрыл ошибки), чипы исчезают, фильтр остаётся: «Нет активных задач»,
   история скрыта, сбросить нечем (только перезаход). Фикс: авто-сброс `taskFilter` при
   обнулении соответствующего счётчика.
4. **[MEDIUM] Во время батча UI не блокируется.** `doPartnerBulk` не выставляет `busy`:
   кнопки `Купить/Готово/Отмена` в карточках активны (двойная покупка защищена атомарным

10. **[LOW · UX] В ledger-строке не видна дата, если есть комментарий**

11. **[LOW] XLSX-тост считает «Создана с ошибкой» как created** — «+N» в тосте включает

12. **[INFO] Summary по срезу `take: 100`** — известное ограничение (см. «Что пока не готово»).
13. **[INFO] Гонка двух параллельных sync** возможна (TTL/RUNNING-гейт не атомарен), но

    `DONE`-задача архивируется (см. C2), создаётся новая задача по строке.

#### Блок C — правка строк без удаления (правила 4–6)

  - Строка `D=«ошибка»` без задачи → создаётся задача первым же sync (FAILED или READY
    по итогам проверки), дальше hash-гейт как обычно.
  - Перепроверка — только при смене `rowHash` (не грузим Google/Roblox на каждый прогон).

### Этап 5.8. Защита выполненных строк: `addProtectedRange` — ✅ реализовано 2026-07-11

Новые вводные владельца (2026-07-11): в таблице работает внутренний **Google Apps Script**,
который следит за живыми сотрудниками и запрещает им менять статусы в `D` руками. Но
onEdit-триггеры **не срабатывают на изменения через API** — значит, бот обязан сам ставить
системную защиту на строки, которые он выполнил. Требование:

- **заказ выполнен (`готово`)** — бот одним `batchUpdate` делает два действия:
  1. пишет `готово` в `D`;
  2. ставит `addProtectedRange` на ячейки `A:D` этой строки (`warningOnly: false`),
     редакторы диапазона — **только владелец таблицы и сервисный аккаунт бота**;
- **заказ не выполнен (`ошибка`)** — только `D=«ошибка»`, без защиты; живые сотрудники
  могут вернуть статус в `в ожидании` для перепроверки (Apps Script это разрешает).

Что уже совпадает с текущим поведением и не меняется:

- `D=«ошибка»` + причина в `E` — реализовано (write-back `kind=error`). «Больше ничего
  делать не нужно» трактуем как «не ставить защиту»; комментарий в `E` **оставляем** —
  без причины сотруднику нечего исправлять (открытое решение О4);
- возврат `ошибка` → `в ожидании` уже реанимирует/перепроверяет строку (П3/C1);
- Apps Script наших API-записей не видит (onEdit не срабатывает) — конфликтов нет,
  менять его не нужно.

| 2 | durable-ретрай в sync («в ожидании» при `DONE`-задаче, contentHash совпал → восстановление `готово`) | тоже ставит/чинит защиту (это и есть канал ретрая `protectPending`) |
| 3 | B1-реконсиляция: ручное `готово` на активной задаче (`DONE` + списание) | после списания залочить строку — **предлагается, О1** |
| 4 | B1-импорт: строка `готово` без задачи (`DONE` + списание) | залочить при импорте — **предлагается, О1** |
| 5 | B2-архив: строку переиспользовали под новый заказ (правит владелец — сотрудникам залоченная строка недоступна) | при архивировании `DONE`-задачи снять её protectedRange по сохранённому id, чтобы новая задача жила обычным циклом — **предлагается, О2** |

Обоснование О1: инвариант «`DONE` = списано = залочено». Ручное `готово` списывает
USDT (5.7 B1) — если такие строки не лочить, у сотрудников остаётся окно правки уже
оплаченной строки (номинала/ника), которое требование как раз закрывает.

Реализация флаша (уточнение против первоначального плана): значения остались на
`values:batchUpdate`, а все защиты прогона применяются **вторым** структурным
`batchUpdate` (`applyPartnerProtectionOps`) — максимум 2 запроса на прогон вместо 1,
зато без рефакторинга всех values-write-back'ов; квота Google (60 write-req/мин) не
страдает. Перед добавлением флаш читает существующие защиты таблицы: защита без
записанного id «лечится» (id дописывается задаче — страховка после чисток БД),
дубль не создаётся; `deleteProtectedRange` шлётся только для реально существующего id
(иначе валился бы весь батч). Дополнительная точка (сверх плана): ветка
«строка `готово` + задача `DONE`» дочиняет защиту при отсутствующем
`protectedRangeId` — это и авто-бэкфилл старых строк, и ретрай упавшего
`addProtectedRange`, без отдельного флага `protectPending`.

  оператор запускает `anton-reset-20260711.mjs --apply` → force-sync** (пересоздаст

#### Риски и граничные случаи

- **Права SA**: ставить protectedRange может редактор файла — SA уже редактор (пишет
  `D`/`E`). Редакторы защиты должны иметь edit-доступ к самому файлу (владелец — ок).
- **Лимит protectedRange на лист** официально не документирован. Текущий масштаб
  (~30 строк × 31 лист-дата) проблем не создаст, но нагрузочная проверка на копии
  таблицы (200+ защит на листе) включена в приёмку.
- **Удаление строки владельцем** удаляет и её защиту (диапазон схлопывается вместе со
  строкой) — семантика A2/П10 не меняется.
- **Сотрудник не сможет удалить строку** с защищёнными ячейками — Google блокирует
  удаление строк, пересекающих чужую защиту. Это дополнительно укрепляет A2 (историю
  выкупов теперь не потерять случайным удалением).
- **`E` остаётся редактируемой** у всех — требование ограничивает диапазон `A:D`,
  а `E` нужна боту как канал комментариев.
- Реконсиляция 5.7 (C2 «изменено после выкупа», B2 rowHash-гейт) остаётся как
  **defense-in-depth**: владелец по-прежнему может править залоченные строки, и его
  правки должны корректно отражаться в TWA.

#### Решения владельца (2026-07-11, все приняты по предложенному)

- **О1 ✅**: строки ручного `готово` (Блок C, п.3–4) лочатся — единый инвариант
  `DONE` = списано = залочено.
- **О2 ✅**: при B2-архиве (переиспользование строки владельцем) защита старого
  выкупа снимается.
- **О3 ✅**: email владельца подтверждён; значение — в env
  `GOOGLE_SHEETS_PROTECTED_EDITORS` (Coolify Web) и HANDOFF, не в репозитории.
- **О4 ✅**: причина ошибки в `E` продолжает писаться («больше ничего» из требования
  = «без защиты», а не «без комментария»).

#### Приёмка

- Успешный выкуп из TWA → в таблице `D=«готово»`, `E` пуста, `A:D` строки под защитой
  (сотрудник не может править и удалить строку, владелец — может), всё одним
  `batchUpdate` (виден один batch в Apps Script → нет ложных срабатываний).
- Ошибка выкупа (row-level) → `D=«ошибка»` + причина в `E`, защиты нет; сотрудник
  возвращает `в ожидании` → строка перепроверяется (C1).
- Повторный force-sync / durable-ретрай не создаёт дублей защит
  (`protectedRangeId`-гейт).
- Ручное `готово` (если принято О1) → задача `DONE` со списанием, строка залочена.
- Переиспользование строки владельцем (B2, если принято О2) → старая защита снята,
  новая задача живёт обычным циклом.
- Упавший `addProtectedRange` (Google 5xx) → задача `DONE`, `готово` записано,
  `protectPending`; следующий sync или `anton-protect-done-rows.mjs` дочиняет защиту.
- Нагрузочная проверка на копии таблицы: 200+ защит на листе, чтение/запись/скорость
  sync не деградируют.

Оценка: ~0.5–1 день разработки + живая проверка на копии таблицы и на бою.

#### Справка: как это работает сейчас (ответы на вопросы 3–4)

- **Выкуп (вопрос 3).** Обе стороны — «Свои» и «Антон» — покупают через **один общий
  donor-cookie** `GlobalSettings.robloxCookie` (id=`global`): retail-роут
  `roblox-account/purchase` и партнёрский `partners/[slug]/tasks` читают одно и то же
  поле, покупка идёт через общий helper `purchaseGamepassWithCookie`
  (`src/lib/roblox-buyout.ts`). Вставили cookie в TWA один раз — работает на оба
  контура. Различие только в **деньгах и учёте**: `purchase-task` Антона делает
  атомарный claim `READY/FAILED→PURCHASING`, проверяет его USDT-баланс, после покупки
  создаёт `BUYOUT`-списание в его ledger по курсу на момент покупки и пишет
  `готово`+защиту в таблицу; покупки «Свои» ledger Антона не трогают. Нюанс:
  **Robux списываются с одного донор-аккаунта** в обоих контурах — балансовая
  конкуренция retail vs партнёр существует by design; отдельный донор под Антона —
  будущая опция (см. примечание в Этапе 3).
- **Курс (вопрос 4).** Курс — одно текущее значение `Partner.robuxRateUsdtPer1000`
  (сейчас 5.05), меняется action `set-rate`. Списание считается **в момент операции**
  (`purchase-task` / `mark-done` / ручное `готово` из таблицы):
  `round(priceRobux × rate / 1000, 2)` USDT фиксируется в `PartnerLedgerEntry.amount`.
  То есть выкупленные заказы **уже зафиксированы** по курсу на момент выкупа, а смена
  курса влияет только на будущие списания — ровно требуемая семантика. Пробел — в
  **отчётности**: курс сделки хранится только текстом в `comment`
  («…× 5.05 USDT / 1000 R$»), истории смен курса нет вообще. «Когда какой курс был и
  сколько по нему куплено» сейчас можно достать только парсингом комментариев.

#### Блок C — ошибка со скрина (пункт 1): квота Google Sheets API — ✅

Скрин показал `FAILED`-ран sync с сырой ошибкой Google: *«Quota exceeded for quota
metric 'Read requests' and limit 'Read requests per minute per user'»*. Причина:
прогон sync читал ~31 лист-дату **отдельными** `values.get` (1 `listSheets` + N

Фикс:

- `batchGetGoogleSheetValues()` в `src/lib/google-sheets.ts` — все листы читаются
  одним `values:batchGet` (чанки по 30 ranges против раздувания URL; маппинг ответа
  по индексу — Google нормализует формат range в ответе); прогон стоит **2 read-запроса
  вместо 1+N**;
- 429/`RESOURCE_EXHAUSTED` в `googleFetch` теперь отдаётся по-русски: «Квота Google
  Sheets исчерпана (минутный лимит запросов) — повтори через минуту» (раньше сырой
  английский текст квоты попадал прямо в TWA);
- упавший ран и так пишет `finishedAt` → TTL-гейт 60 с не даёт фоновым sync
  «долбить» квоту после ошибки.

### Этап 5.11. Права статусов таблицы: матрица переходов и защита строк (план 2026-07-11, ждёт согласования)

Владелец сформулировал 5 правил доступа к статусу `D` (2026-07-11, ночь). Роли:
**бот** (сервисный аккаунт: write-back + защиты; «ты» в формулировках владельца),
**владелец** (таблицы), **остальные** — живые редакторы (сотрудники; таблица Антону
пока не передана).

Правила дословно:

1. стоит «готово» → менять могут только бот и владелец;
2. стоит «ошибка» → менять могут все: бот/владелец — на «в ожидании» и «готово»,
   остальные — **только** на «в ожидании»;
3. стоит «в ожидании» → менять могут только бот и владелец;
4. бот/владелец поставили «готово» → заказ попадает в «выполненные» TWA, строка
   закрыта от изменений для всех, кроме бота и владельца;
5. бот/владелец сменили «готово» на «в ожидании»/«ошибка» → строка открывается
   для редактирования всем.

Трактовка (подтвердить у владельца): правила 1–3 — про смену **чипа статуса `D`**;
правила 4–5 — про лок/анлок **всей строки** (`A:D`). Ячейки `A:C` у строк
«в ожидании» и «ошибка» остаются правимыми всеми — это нужно текущей семантике
(C1: исправление ошибки, C3: правка pending-строки).

#### Матрица переходов чипа `D`

| `D` сейчас | бот и владелец | остальные |
|---|---|---|
| «готово» | → «в ожидании», → «ошибка» (правило 5) | нельзя (правило 1) |
| «ошибка» | → «в ожидании», → «готово» | только → «в ожидании» (правило 2) |
| «в ожидании» | → «готово», → «ошибка» | нельзя (правило 3) |

Что уже закрыто текущей реализацией:

- правило 1 и 4 — ✅ 5.7 B1 (DONE + списание) + 5.8 (`addProtectedRange A:D`,
  редакторы — владелец + SA): сотрудник физически не может править/удалять
  строку «готово». Только приёмка;
- правило 2, часть «строка-ошибка открыта всем» — ✅ строки `ошибка` не защищаются;
- переходы самого бота (pending→готово/ошибка при выкупе и write-back,
  ошибка→в ожидании в C1-автовозврате) — ✅ уже соответствуют матрице.

Чего не хватает: лок чипа `D` на строках «в ожидании» (правило 3), разблокировка
при снятии «готово» (правило 5), и value-level ограничение «остальные: только
ошибка→в ожидании» (правило 2).

#### Слои enforcement

1. **`protectedRange` (бот, жёсткий слой)** — бинарная защита «может/не может»:
   - «готово» → лок `A:D` (есть, 5.8);
   - «в ожидании» → **новое**: лок только ячейки `D` у строк **с задачей**;
   - «ошибка» → без защиты (write-back «ошибка» снимает D-лок).
2. **Apps Script (владелец, мягкий слой)** — правила, зависящие от значения
   («остальные могут ставить только „в ожидании“»), защитой не выражаются.
   Это зона Apps Script владельца: скрипт должен разрешать сотрудникам ровно один
   переход `ошибка → в ожидании` и откатывать остальное. Также **только Apps Script
   прикрывает строки без задач** (шаблонные ~70/лист с предвыставленным чипом и
   свежие строки до первого sync): D-лок бота появляется только после импорта
   строки в задачу (окно до 60 с TTL).
3. **Sync-семантика (бот)** — реакция на то, что всё же прошло в таблицу
   (Блок B и О3).

#### Блок A — лок чипа `D` на «в ожидании» (правило 3)

- При создании/реимпорте pending-задачи ставить `addProtectedRange` на ячейку `D`
  (отдельный description-префикс, напр. «Статус под ботом (строка N)»;
  `pendingProtectedRangeId` в `sheetRaw`).
- Переходы: write-back «ошибка» → снять D-лок; выкуп/«готово» → снять D-лок,
  поставить `A:D` (существующий путь); C1-автовозврат «ошибка»→«в ожидании» →
  вернуть D-лок.
- Все операции — через существующий флаш `applyPartnerProtectionOps` (батчево,
  1 структурный `batchUpdate` на прогон; квота write не страдает). Лечение/дедуп
  по снапшоту защит — как в 5.8 (префикс description различает pending- и

- Счётчики `diagnostics.protection` расширить: `pendingLocked / pendingUnlocked`.
- Бэкфилл: расширить `anton-protect-done-rows.mjs` (или отдельный скрипт) —

- Масштаб: ~30 заказов на лист-день → до ~30 D-локов + ~30 `A:D`-локов на лист;

#### Блок B — разблокировка при снятии «готово» (правило 5)

Сейчас возврат «готово»→«в ожидании» без правок строки авто-восстанавливается

Меняем семантику: чип «готово» мог снять только владелец (сотруднику мешает лок) —

- бот больше не восстанавливает «готово» автоматически;
- снимает `A:D`-защиту (`deleteProtectedRange` по сохранённому id) — строка

- дальнейшая судьба задачи и денег — по решению **О2**;

по-прежнему набирается планом под баланс) и `mark-done` больше не возвращают «Недостаточно
баланса партнёра». Ручная кнопка «Купить» и «Готово» срабатывают всегда, ledger уходит в
минус, отрицательный баланс подсвечивается в hero-дашборде («⚠️ Баланс в минусе… нужно
пополнение»). Кнопка «Купить» на клиенте и раньше не была балансо-зависимой
(`canPurchase = READY|FAILED`).

#### ⚠️ Операционный готча: защита строк блокирует service account (2026-07-12)

Симптом в TWA (блок Google Sheets): `Invalid data[0]: You are trying to edit a protected cell
or object…; защита строк: Invalid requests[0].addProtectedRange: You are trying to edit a
protected cell or object…`. Это **не баг кода** — write-back падает, потому что на листе есть
**защищённый диапазон, в редакторах которого нет сервисного аккаунта** бота (обычно её ставит
внутренний Apps Script владельца «против ручных правок статусов» из Этапа 5.8, либо ручная
защита листа/колонок `D:E`). Google блокирует SA и на запись значения (`готово`/`ошибка` в
`D`/`E`), и на `addProtectedRange`. **Сам выкуп при этом проходит** (деньги списаны, задача
`DONE` в боте) — падает только зеркалирование статуса в таблицу.

Важно: **защищённый диапазон блокирует и API-записи**, а не только ручные — исходное допущение
Этапа 5.8 («Apps Script API-записи не видит») верно лишь для `onEdit`-триггеров, но НЕ для
`Protection`/`addProtectedRange`. Собственные локи бота уже включают SA + владельца
(`getGoogleProtectionEditors` = `client_email` + `GOOGLE_SHEETS_PROTECTED_EDITORS`), поэтому
проблема — только во **внешних** (ручных/скриптовых) защитах без SA.

Что делать владельцу (в таблице): **Данные → Защищённые листы и диапазоны** → для защит,
накрывающих строки задач или колонки `D:E` (или защиту всего листа), **добавить e-mail
сервисного аккаунта** (`…@…iam.gserviceaccount.com`, на который таблица уже расшарена) в
редакторы — или снять защиту. Если защиты ставит Apps Script — в скрипте вызвать
`protection.addEditor(<SA email>)` (или не защищать `D:E`). Пока SA не редактор — статусы в
таблицу зеркалиться не будут, хотя бот всё выкупает и считает корректно.

### Этап 6. Батч-выкуп

Текущая механика batch-покупок уже есть и её надо переиспользовать.

Но для партнёра нужно добавить:

- выбор только задач партнёра;
- лимит по его балансу;
- отдельный отчёт батча;
- массовый write-back в Google Sheet;
- остановку батча без потери уже купленных строк.

### Этап 7. Учёт денег партнёра

Статус: базовый ledger сделан. Антон платит в крипте (`USDT`), другой валюты для него
не используется.

Иначе быстро появятся вопросы без ответа:

- сколько он завёл;
- сколько уже потрачено;
- сколько осталось;
- какой батч что списал;
- где ошибка, а где корректировка.

Это критично, если направление реально пойдёт в B2B SaaS.

### Этап 8. Отчётность и аудит

Нужен отдельный отчёт по партнёру:

- сколько строк импортировано;
- сколько выкуплено;
- сколько в ошибке;
- сумма потраченных R$ и USDT;
- какие cookie-аккаунты использовались;
- история пополнений/списаний.

Минимум отчёт должен быть доступен внутри TWA. Потом можно думать о внешнем кабинете.

### Этап 9. Hardening

Перед прод-использованием проверить:

- дедуп импорта;
- двойной тап по кнопке `Купить`;
- race condition между ручным и пакетным выкупом;
- падение Google API;
- падение Roblox purchase API;
- write-back в таблицу после успешного выкупа;
- восстановление после частично завершённого батча.

## Рекомендуемый порядок релиза

Самый прагматичный путь такой:

1. Вынести shared buyout-service — частично сделано (`resolve` + `purchase`).
2. Добавить `Partner` + `PartnerBuyoutTask` + `PartnerLedgerEntry` — сделано.
3. Сделать server MVP `Антон` для ручных задач и ledger — сделано.
4. Сделать экран `Антон` внутри «Аккаунт» с ручным созданием/покупкой задач — сделано.
5. Добавить ручную загрузку `.xlsx` строк партнёра — сделано.
6. Добавить Google Sheets sync и write-back статуса `Готово` — сделано (2026-07-10).
7. Довести batch purchase только по задачам партнёра.
8. Уже после этого обобщать интерфейс из `Антон` в полноценный `Partners`.

## Оценка идеи

На текущем состоянии проекта это выглядит **хорошей и реалистичной следующей веткой**:

- ядро выкупа уже написано;
- TWA уже является рабочим операционным центром;
- менеджерский UX уже существует;
- путь до первого B2B-MVP короткий по сравнению с построением всего с нуля.

Но это пока **не SaaS в полном смысле**, а скорее **partner-ops module**.
Чтобы это стало SaaS, нужно не просто добавить экран, а отделить партнёрскую модель данных,
импорт, ledger и отчётность от розничного WB-контура.
