# B2B / Partner Buyout

Статус на **2026-07-10**: реализован **TWA/server MVP** для первого партнёра
`anton`/«Антон»: Prisma-модели, shared buyout-helper, TWA API задач и экран `Антон`
внутри «Аккаунта» (`Свои | Антон`). Ledger Антона переведён в **USDT-only**, курс
фиксируется в карточке партнёра как `5.05 USDT / 1000 R$` и может меняться из TWA.
Есть ручная загрузка `.xlsx` с колонками `ГП/GP`, `Ник`, `Номинал` и — **новое 2026-07-10** —
**рабочий Google Sheets sync + write-back**: сервер сканирует date-листы боевой таблицы,
импортирует строки `в ожидании` в `PartnerBuyoutTask`, а успешный выкуп пишет `готово`
в колонку `E` (ошибку — в `F`). Прогоны фиксируются в `PartnerImportRun`. **Batch-выкуп**
и полноценный **партнёрский отчёт** ещё не готовы.

## Зафиксированные правила Антона

- Валюта баланса партнёра — только `USDT`.
- Цена задачи хранится в грязных `R$` (`priceRobux` / `purchasePriceRobux`), но ledger
  списывается в `USDT`.
- Формула списания: `round(priceRobux * robuxRateUsdtPer1000 / 1000, 2)`.
- Текущий курс Антона: `5.05 USDT / 1000 R$`; курс хранится в `Partner.robuxRateUsdtPer1000`
  и меняется action `set-rate`.
- Стартовый платёж: `150 USDT`.
- Выкуп по XLSX `selected-roblox-orders-2026-07-09 10_31_39 (1).xlsx`: 8 строк,
  `19 106 R$` грязными = `96.49 USDT`.
- Текущий расчётный остаток после стартового выкупа: `53.51 USDT`.

## Текущий партнёрский поток

Первый реальный кейс — партнёр **«Антон»**.

Текущий MVP-процесс:

1. Антон переводит деньги в крипте.
2. Антон заполняет строки геймпассов в Google-таблице (или отдаёт `.xlsx`).
3. На его деньги команда покупает cookie-аккаунты.
4. Менеджер жмёт **«Синхронизировать»** в TWA (**«Аккаунт» → `Антон`**) — сервер тянет
   строки `в ожидании` из таблицы в задачи; либо загружает `.xlsx`, либо заводит задачу вручную.
5. Менеджер выкупает каждый геймпасс через общий donor-cookie или вручную помечает задачу
   как **«Готово»**.
6. Успешный выкуп/«Готово» автоматически пишет `готово` в колонку `E` строки Google Sheet;
   при ошибке причина уходит в `F`, а строка остаётся `в ожидании` для повторной попытки.

Цель следующего этапа: batch-выкуп только по задачам партнёра и отдельный отчёт партнёру,
чтобы «Антон» стал самодостаточным партнёрским рабочим местом.

## Что уже готово в продукте

Текущая система уже покрывает большую часть **операционного ядра** будущего B2B-модуля:

- TWA-аутентификация и админский UI уже есть.
- `BossrobuxScreen` умеет искать геймпассы по нику/ID/URL и покупать их через cookie.
- Серверный purchase-flow уже умеет:
  проверять cookie, получать CSRF, делать покупку, возвращать актуальный баланс.
- Есть live-check цены/доступности и дедуп по уже использованным геймпассам.
- Есть пакетные покупки и история по cookie-аккаунтам.
- Есть ручное создание заказов и операционный UX для менеджера.
- Shared helper `src/lib/roblox-buyout.ts` уже содержит resolve геймпасса и покупку через
  `.ROBLOSECURITY`, чтобы B2B не копировал retail purchase-код.
- В Prisma добавлены `Partner`, `PartnerBuyoutTask`, `PartnerLedgerEntry` и отдельные enum-ы
  партнёрского контура.
- Есть TWA route `GET/POST /api/twa/partners/[slug]/tasks` для server-MVP:
  создать задачу, загрузить `.xlsx`, синхронизировать Google Sheets, пополнить ledger,
  сменить курс, отменить задачу, отметить готовой, купить через cookie.
- XLSX upload принимает первый лист файла, парсит `ГП/GP`, `Ник`, `Номинал`, создаёт задачи
  `externalSource=XLSX_UPLOAD`, ограничивает файл `5 MB` и `300` строк, а повторную загрузку
  того же файла/строки/геймпасса пропускает по idempotency.
- Google Sheets sync (`action=sync-google-sheets` + opportunistic sync на GET с TTL 60 с)
  сканирует date-листы боевой таблицы, импортирует строки `в ожидании` в
  `PartnerBuyoutTask` (`externalSource=GOOGLE_SHEETS`), резолвит геймпасс, идемпотентен по
  `partnerId+externalSource+externalRowId`, а write-back пишет `готово` в `E` / ошибку в `F`.
- Каждый прогон sync пишет `PartnerImportRun` (счётчики created/updated/failed/skipped +
  диагностика фильтра по листам) для статуса в TWA и защиты от параллельных sync.

Вывод: для **внутреннего B2B-модуля** база уже сильная. Не хватает не механики выкупа, а
**отдельного контекста партнёра**: импорт задач, учёт его денег, статусы строк, отчётность,
изоляция от клиентских заказов.

## Что пока не готово

В текущем B2B MVP ещё отсутствуют:

- batch-выкуп только по задачам партнёра;
- отдельная аналитика и отчёт партнёру;
- production-hardening race-condition между ручным и batch-выкупом (одиночный выкуп уже
  защищён атомарным `READY/FAILED -> PURCHASING`, sync — TTL + `PartnerImportRun status=RUNNING`);
- обобщение из single partner `anton` в полноценный multi-partner SaaS.

Уже сделано (было в этом списке): связь строки Google Sheet с внутренней задачей и
автоматическая обратная запись статуса `готово`/ошибки в таблицу.

## Архитектурная позиция

### Что делать правильно

Раздел **«Антон»** надо строить как первый instance **generic partner flow**, даже если
в интерфейсе он пока будет называться конкретно `Антон`.

### Что делать не надо

Не стоит запихивать это в `WbOrder` через костыли вроде:

- фиктивных `wbCode`;
- пустых `userId`;
- `orderSource=MANUAL` для партнёрских задач;
- ручных заметок вместо нормальных статусов.

`WbOrder` сейчас заточен под розничный коридор: WB-коды, боты, уведомления клиенту,
состояния `AWAITING_GAMEPASS/PENDING/COMPLETED`. Для партнёра это другой bounded context.

## Рекомендуемая модель MVP

Для первого релиза достаточно отдельного B2B-контура с тремя сущностями. На 2026-07-09
эта модель уже добавлена в Prisma миграцией `20260709_add_partner_buyout`.

### `Partner`

- `id`
- `slug` (`anton`)
- `name`
- `isActive`
- `notes`
- `ledgerCurrency` (`USDT` для Антона)
- `robuxRateUsdtPer1000` (`5.05` сейчас)
- `googleSheetId`
- `googleSheetTab`
- `googleSheetUrl`

### `PartnerLedgerEntry`

Фиксирует деньги партнёра. Для Антона ledger ведётся только в `USDT`; R$ остаются ценой
геймпасса на задаче.

- `id`
- `partnerId`
- `type` (`TOPUP`, `BUYOUT`, `ADJUSTMENT`, `REFUND`)
- `amount`
- `currency`
- `reference`
- `comment`
- `createdBy`
- `createdAt`

### `PartnerBuyoutTask`

Одна строка/один геймпасс из внешнего источника партнёра: ручная задача, `.xlsx` upload или
будущий Google Sheets sync.

- `id`
- `partnerId`
- `externalRowId`
- `externalSource` (`MANUAL`, `XLSX_UPLOAD`, `GOOGLE_SHEETS`)
- `status` (`NEW`, `READY`, `PURCHASING`, `DONE`, `FAILED`, `CANCELLED`)
- `robloxUsername`
- `gamepassId`
- `gamepassUrl`
- `productId`
- `sellerId`
- `priceRobux`
- `sheetRaw`
- `purchaseAccountName`
- `purchaseBatchId`
- `completedAt`
- `error`
- `note`
- `createdAt`
- `updatedAt`

Минимальная инварианта: одна внешняя строка = одна внутренняя задача; повторный импорт/sync
не создаёт дублей. Для `.xlsx` бинарный файл не хранится, в `sheetRaw` остаются только
метаданные файла, номер строки и исходные значения строки.

## Где размещать в TWA

По текущей структуре TWA отдельный нижний таб под `Антон` выглядит слабее, чем
**вложенный режим внутри экрана «Аккаунт»**:

- нижняя навигация уже плотно занята;
- по смыслу это тот же buyout workspace;
- reuse `BossrobuxScreen` и purchase-логики будет проще;
- менеджеру удобнее переключаться между **«Свои / Антон»**, чем между разными корневыми табами.

Рекомендуемый UX:

- в `BossrobuxScreen` добавить верхний segmented control:
  **`Свои` | `Антон`**
- `Свои` = текущая логика без изменений;
- `Антон` = отдельный список задач партнёра, отдельные сводки, отдельный отчёт.

## Детальный план выполнения

### Этап 0. Зафиксировать продуктовые правила

Статус: частично сделано для Антона.

Уже зафиксировано:

- баланс партнёра считаем в `USDT`;
- курс хранится в `Partner.robuxRateUsdtPer1000`;
- `Готово` = геймпасс куплен или вручную подтверждён менеджером, по задаче есть
  `DONE` и USDT-списание;
- неуспешный выкуп не списывает баланс, задача остаётся `FAILED`/`READY`.

Ещё нужно определить перед Google Sheets sync:

- точные названия колонок в боевой таблице;
- строка идентифицируется по row number, отдельному id или ссылке на геймпасс;
- можно ли у одной строки менять геймпасс после импорта;
- нужен ли partial-success для батча;
- нужен ли возврат/корректировка, если выкуп не состоялся после ручного списания.

Статус: частично сделано. `src/lib/roblox-buyout.ts` уже содержит:

Поиск по нику и дедуп прошлых покупок пока остаются в retail/TWA-контуре. Следующий шаг —

### Этап 2. Добавить B2B-схему в Prisma

Статус: сделано для MVP. Миграции добавляют:

- `Partner`
- `PartnerLedgerEntry`
- `PartnerBuyoutTask`
- `PartnerImportRun` (миграция `20260710_partner_google_sheets_sync`, 2026-07-10) — журнал

Индексы нужны минимум по:

- `externalRowId`
- `gamepassId`

### Этап 3. Сделать серверный API партнёрского контура

Статус: сделан server route под первого партнёра (`[slug]` = `anton`):

- `GET /api/twa/partners/[slug]/tasks` — состояние партнёра, задачи, summary, последние
  ledger-записи, `googleSync` (статус/lastSyncAt/latestRun) и `importRuns`; попутно запускает
  opportunistic Google Sheets sync с TTL 60 с.
- `POST /api/twa/partners/[slug]/tasks` с `action=create-task` — ручное создание задачи по
  ID/URL геймпасса.
- `action=import-xlsx` — ручная загрузка `.xlsx` с колонками `ГП/GP`, `Ник`, `Номинал`.
- `action=sync-google-sheets` — принудительный (`force`) Google Sheets sync + write-back.
- `action=ledger-topup` — пополнение партнёрского баланса в USDT.
- `action=set-rate` — смена курса партнёра (`USDT / 1000 R$`) для следующих списаний.
- `action=cancel-task` — отмена незавершённой задачи.
- `action=mark-done` — ручное закрытие задачи с отдельным списанием ledger + write-back `готово`.
- `action=purchase-task` — покупка через общий Roblox cookie-helper с переходом
  `READY/FAILED -> PURCHASING -> DONE/FAILED` + write-back `готово`/ошибки.

Требования к API:

- idempotent sync;
- атомарный переход `READY -> PURCHASING -> DONE/FAILED`;
- защита от двойного выкупа одной и той же строки;
- запись фактической цены и cookie-аккаунта;
- честные ошибки, если cookie протух, пасс не продаётся или AlreadyOwned.

MVP route не обращается к `WbOrder`. Денежный учёт идёт через `PartnerLedgerEntry` в USDT;
перед ручным закрытием и покупкой R$-цена задачи конвертируется по текущему курсу партнёра,
проверяется USDT-баланс, а повторное `BUYOUT`-списание по задаче блокируется.

Важно по cookie: отдельного donor-cookie для Антона пока нет. Покупка использует общий
`.ROBLOSECURITY` из `GlobalSettings.robloxCookie`, тот же источник, что и экран `Свои`.
Если понадобится отдельный donor-аккаунт партнёра, это надо добавить отдельным полем/настройкой,
не смешивая с ledger и задачами партнёра.

### Этап 4. Интеграция с Google Sheets

Статус: **реализовано 2026-07-10** (`action=sync-google-sheets` + opportunistic sync на GET,
write-back в `E/F`, журнал `PartnerImportRun`). Ручной `.xlsx` upload остаётся как запасной
путь импорта в ту же модель `PartnerBuyoutTask`. Ниже — исходный контракт и план, по которому
собрана реализация; пункты плана считать выполненными, если явно не отмечено иначе.

Боевой контракт Google Sheets для Антона зафиксирован:

- `spreadsheetId`: `1jzWZZ_AeM0IMyHaljaLBei0hu_zDwktiysbgGt324rs`;
- `sheetName` не фиксируется: каждый лист = отдельная дата, sync должен сканировать листы
  с датами, а не привязываться к одному табу;
- импортировать только строки, где колонка `D` не пустая, а колонка `E` ровно
  `в ожидании`;
- маппинг колонок: `A` = ник/инфа, `C` = GP/gamepass id или URL, `D` = номинал/цена,
  `E` = статус, `F` = комментарий по ошибке;
- source fields: `nickname -> A`, `gamepass -> C`, `amount -> D`;
- write-back: при успешном выкупе записать `готово` в `E`; при ошибке записать текст
  ошибки в `F`, а `E` оставить или вернуть в `в ожидании`.

Целевой UX автообновления: Антон меняет строки в Google Sheet, менеджер открывает или
обновляет вкладку `Аккаунт -> Антон`, сервер подтягивает свежие строки, нормализует их в
`PartnerBuyoutTask`, и TWA показывает уже готовые задачи для выкупа. Клиентский TWA не должен
ходить в Google напрямую: Google API живёт только на сервере, а интерфейс работает с задачами
из БД.

#### План реализации Google Sheets sync

1. **Google Sheets client**
   - Добавить серверный helper `src/lib/google-sheets.ts`.
   - Читать `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON` и создавать service-account client только
     на сервере.
   - Поддержать операции:
     `listSheets(spreadsheetId)`, `readSheetRows(spreadsheetId, sheetTitle, range)`,
     `writeCells(spreadsheetId, updates[])`.
   - Не логировать JSON credentials, private key, access token и полный raw response Google.
   - Возвращать короткие typed-ошибки: нет env, нет доступа к таблице, rate limit,
     некорректная структура листа.

2. **Выбор листов**
   - Использовать `spreadsheets.get` и брать все видимые tabs.
   - Не зависеть от `Partner.googleSheetTab`: у Антона каждый лист = дата.
   - На первом релизе сканировать все листы; если таблица разрастётся, добавить фильтр
     "последние N листов" или курсор по `PartnerImportRun`.
   - Сохранять в `sheetRaw` `spreadsheetId`, `sheetTitle`, `rowNumber`, `range`, исходные
     значения `A/C/D/E/F` и время sync.

3. **Парсинг строк**
   - Читать диапазон минимум `A:F`.
   - Пропускать заголовки/пустые строки.
   - Брать в импорт только строки, где:
     `D` не пустая и `E.trim().toLowerCase() == "в ожидании"`.
   - Маппинг:
     `A -> robloxUsername` или исходная partner info,
     `C -> gamepassId/gamepassUrl`,
     `D -> priceRobux`,
     `E -> sourceStatus`,
     `F -> sourceError`.
   - `D` парсить как грязную цену в R$; пробелы, `R$`, `rbx`, запятые и неразрывные пробелы
     надо нормализовать до числа.
   - `C` принимать как чистый ID, URL `game-pass`, URL `gamepasses` или текст с ID внутри.
   - Невалидную строку не превращать в READY-задачу: записать диагностическую ошибку в `F`
     и сохранить/обновить задачу как `FAILED` или оставить без задачи, если нет стабильного
     идентификатора геймпасса.

4. **Идентичность и идемпотентность**
   - `externalSource = GOOGLE_SHEETS`.
   - Базовый `externalRowId`: `${spreadsheetId}:${sheetTitle}:${rowNumber}`.
   - В `sheetRaw` дополнительно хранить `gamepassRaw`, `gamepassId`, `rowHash`.
   - Повторный sync той же строки обновляет существующую задачу, а не создаёт дубль.
   - Если в строке до выкупа поменяли `C` или `D`, задача может обновиться только в статусах
     `NEW`, `READY`, `FAILED`. Для `PURCHASING`, `DONE`, `CANCELLED` менять цену/геймпасс
     нельзя: это уже операционное событие, требующее ручной проверки.
   - Если строку перенесли на другой лист или другую строку, это новая внешняя строка.
     Автоматически "склеивать" переносы по одному gamepassId нельзя без отдельного product
     rule, иначе можно случайно потерять повторный выкуп того же пасса.

5. **Создание готовых данных для выкупа**
   - Для валидной строки sync должен резолвить gamepass через `resolveGamepass`.
   - В задачу писать `gamepassId`, `gamepassUrl`, `productId`, `sellerId`, `sellerName`,
     `priceRobux`, `purchasePriceRobux`, `robloxUsername`/source info.
   - Если live-price Roblox отличается от `D`, задача остаётся видимой, но получает ошибку
     или warning в `error`/`note`; покупать такую задачу можно только после ручного решения
     или явного правила допуска.
   - Статус валидной задачи: `READY`. Статус строки с ошибкой парсинга/резолва: `FAILED`
     с текстом, понятным оператору и пригодным для записи в `F`.
   - На импорт задача не списывает USDT. Ledger списывается только при `purchase-task` или
     `mark-done`, как сейчас.

6. **Точка запуска sync**
   - Добавить серверный action `sync-google-sheets` в
     `POST /api/twa/partners/[slug]/tasks`.
   - Добавить opportunistic sync в `GET /api/twa/partners/anton/tasks`: если таблица
     подключена и последний sync старше короткого TTL (например 30-60 секунд), сервер
     запускает sync перед ответом или сразу после ответа через bounded background promise.
   - В TWA добавить кнопку `Синхронизировать` и авто-refresh при входе во вкладку `Антон`.
   - Клиентский polling делать осторожно: не чаще TTL, с отображением `lastSyncAt`,
     `syncInProgress`, `imported/updated/failed`.
   - Если Google недоступен, GET всё равно должен вернуть последние задачи из БД и отдельный
     блок ошибки sync, а не ломать весь экран.

7. **Журнал sync**
   - Для первого релиза можно хранить метаданные в `Partner.notes` или в `sheetRaw`, но
     правильнее добавить `PartnerImportRun`:
     `partnerId`, `source`, `startedAt`, `finishedAt`, `status`, `spreadsheetId`,
     `sheetCount`, `rowCount`, `createdCount`, `updatedCount`, `failedCount`, `error`.
   - `PartnerImportRun` нужен для отладки, защиты от параллельных sync и честного статуса
     в TWA.
   - Параллельные sync одного партнёра должны блокироваться advisory lock или короткой
     DB-блокировкой на `PartnerImportRun status=RUNNING`.

8. **Write-back в Google Sheet**
   - После успешного `purchase-task` или `mark-done` писать `готово` в колонку `E` той же
     строки (`sheetTitle + rowNumber` из `sheetRaw`) и очищать/оставлять `F` по принятому
     правилу. Предпочтительно очищать старую ошибку только если операция реально успешна.
   - При ошибке покупки писать короткую причину в `F`; `E` оставить `в ожидании`, чтобы
     строка продолжала попадать в sync после исправления.
   - Write-back должен быть best-effort, но durable: если покупка прошла, а запись в Google
     не прошла, задача остаётся `DONE`, получает `note/error` про pending write-back, а
     повторный sync/write-back retry должен дописать `готово`.
   - Нельзя перезаписывать `E=готово` ошибкой от старого запуска. Перед записью ошибки
     проверять, что внутренняя задача ещё не `DONE`.

9. **TWA-изменения**
   - Блок Google Sheets должен показывать не только `Подключено`, но и `lastSyncAt`,
     результат последнего sync, количество строк `READY/FAILED/DONE` из Google и кнопку
     `Синхронизировать`.
   - Список задач должен визуально отличать source `GOOGLE_SHEETS` от `XLSX_UPLOAD` и
     `MANUAL`.
   - В карточке задачи показывать `sheetTitle:rowNumber` и, если возможно, ссылку на строку
     Google Sheet.
   - После sync TWA должен обновлять список задач без перезагрузки всего приложения.
   - Ошибки строк показывать рядом с задачами и в summary, чтобы оператор видел, что именно
     надо поправить в таблице.

10. **Проверки перед продом**
    - Таблица без доступа сервисного аккаунта -> понятная ошибка, старые задачи доступны.
    - Пустая таблица -> 0 imported, без падения.
    - Несколько date-листов -> строки со всех листов попадают в задачи.
    - Повторный sync -> дублей нет.
    - Изменение `C/D` до выкупа -> READY-задача обновляется.
    - Изменение `C/D` после DONE -> задача не мутирует, появляется ручной warning.
    - Успешная покупка -> задача DONE, ledger списан один раз, `E=готово`.
    - Ошибка покупки -> ledger не списан, задача FAILED, `F` заполнена.
    - Google write-back падает после успешной покупки -> задача DONE сохраняется, retry
      дописывает `готово`.
    - Двойной тап `Купить` и параллельный batch -> только один переход в `PURCHASING/DONE`.

Что подключено для Google Sheets:

- `spreadsheetId` таблицы известен;
- service-account JSON заведён в env `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`;
- env `ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` заведён;
- таблица расшарена на service-account email;
- правило чтения/записи статусов зафиксировано и реализовано в коде.

Серверный клиент — `src/lib/google-sheets.ts` (service-account JWT → OAuth token с кэшем,
`listGoogleSheets` / `readGoogleSheetRows` / `batchUpdateGoogleSheetValues`, typed
`GoogleSheetsError`, credentials не логируются). Сам sync/parse/idempotency/write-back —
в `syncPartnerGoogleSheets` / `writeBackPartnerTask` внутри роута `[slug]/tasks`.

`GET /api/twa/partners/[slug]/tasks` при upsert партнёра заполняет `Partner.googleSheetId`
и `Partner.googleSheetUrl` из `ANTON_GOOGLE_SHEETS_SPREADSHEET_ID` (статус подключения),
затем запускает opportunistic sync с TTL 60 с и отдаёт `googleSync`/`importRuns` в TWA.

### Этап 5. Экран `Антон` в TWA

Статус: MVP сделан в `BossrobuxScreen`.

Что есть:

- верхний переключатель `Свои | Антон` внутри экрана «Аккаунт»;
- `Антон` показывает USDT-баланс, потрачено, текущий курс, выкупленные R$,
  количество задач и статус ready/buying/done;
- есть блок Google Sheets: статус подключения, `lastSyncAt`, итог последнего `PartnerImportRun`
  (created/updated/failed), диагностика фильтра (прочитано / прошло / отсев по `D` и `E` /
  топ статусов `E`), кнопка `Синхронизировать`;
- есть блок ручной загрузки `.xlsx` для файлов с колонками `ГП/GP`, `Ник`, `Номинал`;
- есть форма смены курса `USDT / 1000 R$`;
- ручное создание задачи по ID/URL геймпасса с ником и заметкой;
- ручное пополнение ledger в USDT;
- список задач партнёра со статусами, R$-ценой, USDT-стоимостью по текущему курсу,
  бейджем источника (`Manual`/`XLSX`/`Google sheetTitle:row`), отметкой write-back `E/F`,
  ошибкой/заметкой и датами;
- действия по задаче: `Купить`, `Готово`, `Отмена`;
- последние ledger-операции.

Что ещё не сделано в UI:

- `Выкупить выбранное` / batch;
- отдельный отчёт партнёра;
- прямая ссылка на конкретную строку Google Sheet из карточки задачи.

Важно: `Антон` не должен попадать в обычные вкладки заказов и не должен ломать текущий
ритейл-фокус менеджера.

### Этап 6. Батч-выкуп

Текущая механика batch-покупок уже есть и её надо переиспользовать.

Но для партнёра нужно добавить:

- выбор только задач партнёра;
- лимит по его балансу;
- отдельный отчёт батча;
- массовый write-back в Google Sheet;
- остановку батча без потери уже купленных строк.

### Этап 7. Учёт денег партнёра

Статус: базовый ledger сделан. Антон платит в крипте (`USDT`), другой валюты для него
не используется.

Иначе быстро появятся вопросы без ответа:

- сколько он завёл;
- сколько уже потрачено;
- сколько осталось;
- какой батч что списал;
- где ошибка, а где корректировка.

Это критично, если направление реально пойдёт в B2B SaaS.

### Этап 8. Отчётность и аудит

Нужен отдельный отчёт по партнёру:

- сколько строк импортировано;
- сколько выкуплено;
- сколько в ошибке;
- сумма потраченных R$ и USDT;
- какие cookie-аккаунты использовались;
- история пополнений/списаний.

Минимум отчёт должен быть доступен внутри TWA. Потом можно думать о внешнем кабинете.

### Этап 9. Hardening

Перед прод-использованием проверить:

- дедуп импорта;
- двойной тап по кнопке `Купить`;
- race condition между ручным и пакетным выкупом;
- падение Google API;
- падение Roblox purchase API;
- write-back в таблицу после успешного выкупа;
- восстановление после частично завершённого батча.

## Рекомендуемый порядок релиза

Самый прагматичный путь такой:

1. Вынести shared buyout-service — частично сделано (`resolve` + `purchase`).
2. Добавить `Partner` + `PartnerBuyoutTask` + `PartnerLedgerEntry` — сделано.
3. Сделать server MVP `Антон` для ручных задач и ledger — сделано.
4. Сделать экран `Антон` внутри «Аккаунт» с ручным созданием/покупкой задач — сделано.
5. Добавить ручную загрузку `.xlsx` строк партнёра — сделано.
6. Добавить Google Sheets sync и write-back статуса `Готово` — сделано (2026-07-10).
7. Довести batch purchase только по задачам партнёра.
8. Уже после этого обобщать интерфейс из `Антон` в полноценный `Partners`.

## Оценка идеи

На текущем состоянии проекта это выглядит **хорошей и реалистичной следующей веткой**:

- ядро выкупа уже написано;
- TWA уже является рабочим операционным центром;
- менеджерский UX уже существует;
- путь до первого B2B-MVP короткий по сравнению с построением всего с нуля.

Но это пока **не SaaS в полном смысле**, а скорее **partner-ops module**.
Чтобы это стало SaaS, нужно не просто добавить экран, а отделить партнёрскую модель данных,
импорт, ledger и отчётность от розничного WB-контура.
