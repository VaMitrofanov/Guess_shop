# B2B / Partner Buyout

Статус на **2026-07-09**: частично реализован **server MVP** для первого партнёра
`anton`/«Антон»: Prisma-модели, shared buyout-helper и TWA API задач. Экран `Антон`,
Google Sheets sync/write-back, batch-выкуп и партнёрский отчёт ещё не готовы.

## Текущий партнёрский поток

Первый реальный кейс — партнёр **«Антон»**.

Текущий процесс полностью ручной:

1. Антон переводит деньги в крипте.
2. Антон заполняет Google-таблицу своими геймпассами, которые нужно выкупить.
3. На его деньги команда покупает cookie-аккаунты.
4. Менеджер вручную выкупает каждый геймпасс через TWA, сейчас только во вкладке
   **«Аккаунт»**.
5. После выкупа менеджер вручную помечает строку в таблице как **«Готово»**.

Цель: добавить в TWA отдельный режим/раздел **«Антон»** для выкупа сторонних геймпассов
на партнёрские деньги, не смешивая это с WB/DIRECT/AVITO-потоком.

## Что уже готово в продукте

Текущая система уже покрывает большую часть **операционного ядра** будущего B2B-модуля:

- TWA-аутентификация и админский UI уже есть.
- `BossrobuxScreen` умеет искать геймпассы по нику/ID/URL и покупать их через cookie.
- Серверный purchase-flow уже умеет:
  проверять cookie, получать CSRF, делать покупку, возвращать актуальный баланс.
- Есть live-check цены/доступности и дедуп по уже использованным геймпассам.
- Есть пакетные покупки и история по cookie-аккаунтам.
- Есть ручное создание заказов и операционный UX для менеджера.
- Shared helper `src/lib/roblox-buyout.ts` уже содержит resolve геймпасса и покупку через
  `.ROBLOSECURITY`, чтобы B2B не копировал retail purchase-код.
- В Prisma добавлены `Partner`, `PartnerBuyoutTask`, `PartnerLedgerEntry` и отдельные enum-ы
  партнёрского контура.
- Есть TWA route `GET/POST /api/twa/partners/anton/tasks` для ручного server-MVP:
  создать задачу, пополнить ledger, отменить задачу, отметить готовой, купить через cookie.

Вывод: для **внутреннего B2B-модуля** база уже сильная. Не хватает не механики выкупа, а
**отдельного контекста партнёра**: импорт задач, учёт его денег, статусы строк, отчётность,
изоляция от клиентских заказов.

## Что пока не готово

В текущем B2B MVP ещё отсутствуют:

- связь строки Google Sheet с внутренней задачей;
- автоматическая обратная запись статуса в таблицу;
- полноценный экран `Антон` в TWA;
- batch-выкуп только по задачам партнёра;
- отдельная аналитика и отчёт партнёру;
- production-hardening Google API, Roblox ошибок и race-condition между ручным и batch-выкупом;
- обобщение из single partner `anton` в полноценный multi-partner SaaS.

## Архитектурная позиция

### Что делать правильно

Раздел **«Антон»** надо строить как первый instance **generic partner flow**, даже если
в интерфейсе он пока будет называться конкретно `Антон`.

### Что делать не надо

Не стоит запихивать это в `WbOrder` через костыли вроде:

- фиктивных `wbCode`;
- пустых `userId`;
- `orderSource=MANUAL` для партнёрских задач;
- ручных заметок вместо нормальных статусов.

`WbOrder` сейчас заточен под розничный коридор: WB-коды, боты, уведомления клиенту,
состояния `AWAITING_GAMEPASS/PENDING/COMPLETED`. Для партнёра это другой bounded context.

## Рекомендуемая модель MVP

Для первого релиза достаточно отдельного B2B-контура с тремя сущностями. На 2026-07-09
эта модель уже добавлена в Prisma миграцией `20260709_add_partner_buyout`.

### `Partner`

- `id`
- `slug` (`anton`)
- `name`
- `isActive`
- `notes`

### `PartnerLedgerEntry`

Фиксирует деньги партнёра.

- `id`
- `partnerId`
- `type` (`TOPUP`, `BUYOUT`, `ADJUSTMENT`, `REFUND`)
- `amount`
- `currency`
- `reference`
- `comment`
- `createdBy`
- `createdAt`

### `PartnerBuyoutTask`

Одна строка/один геймпасс из таблицы партнёра.

- `id`
- `partnerId`
- `externalRowId`
- `externalSource` (`GOOGLE_SHEETS`)
- `status` (`NEW`, `READY`, `PURCHASING`, `DONE`, `FAILED`, `CANCELLED`)
- `robloxUsername`
- `gamepassId`
- `gamepassUrl`
- `productId`
- `sellerId`
- `priceRobux`
- `sheetRaw`
- `purchaseAccountName`
- `purchaseBatchId`
- `completedAt`
- `error`
- `note`
- `createdAt`
- `updatedAt`

Минимальная инварианта: одна строка таблицы = одна внутренняя задача; повторный sync не
создаёт дублей.

## Где размещать в TWA

По текущей структуре TWA отдельный нижний таб под `Антон` выглядит слабее, чем
**вложенный режим внутри экрана «Аккаунт»**:

- нижняя навигация уже плотно занята;
- по смыслу это тот же buyout workspace;
- reuse `BossrobuxScreen` и purchase-логики будет проще;
- менеджеру удобнее переключаться между **«Свои / Антон»**, чем между разными корневыми табами.

Рекомендуемый UX:

- в `BossrobuxScreen` добавить верхний segmented control:
  **`Свои` | `Антон`**
- `Свои` = текущая логика без изменений;
- `Антон` = отдельный список задач партнёра, отдельные сводки, отдельный отчёт.

## Детальный план выполнения

### Этап 0. Зафиксировать продуктовые правила

Нужно определить до кода:

- какие именно колонки в Google Sheet обязательны;
- строка идентифицируется по row number, отдельному id или ссылке на геймпасс;
- можно ли у одной строки менять геймпасс после импорта;
- что считать статусом **«Готово»**;
- нужен ли partial-success для батча;
- в чём считаем баланс партнёра: `USDT`, `RUB`, `R$` или просто факт внесённого бюджета;
- нужен ли возврат/корректировка, если выкуп не состоялся.

Без этого БД и sync-логика будут поплывшими.

### Этап 1. Вынести shared Roblox-buyout service

Статус: частично сделано. `src/lib/roblox-buyout.ts` уже содержит:

- `resolveGamepass`
- `purchaseGamepassWithCookie`

Поиск по нику и дедуп прошлых покупок пока остаются в retail/TWA-контуре. Следующий шаг —
дотянуть helper до полного shared engine, чтобы и retail, и `Антон` ходили через один слой.

### Этап 2. Добавить B2B-схему в Prisma

Статус: сделано для MVP. Миграция добавляет:

- `Partner`
- `PartnerLedgerEntry`
- `PartnerBuyoutTask`
`PartnerImportRun` пока не добавлен, потому что Google Sheets sync ещё не реализован.

Индексы нужны минимум по:

- `partnerId + status`
- `partnerId + updatedAt desc`
- `externalRowId`
- `gamepassId`

### Этап 3. Сделать серверный API партнёрского контура

Статус: сделан один MVP route под первого партнёра:

- `GET /api/twa/partners/anton/tasks` — состояние партнёра, задачи, summary, последние ledger-записи.
- `POST /api/twa/partners/anton/tasks` с `action=create-task` — ручное создание задачи по
  ID/URL геймпасса.
- `action=ledger-topup` — пополнение партнёрского баланса в R$.
- `action=cancel-task` — отмена незавершённой задачи.
- `action=mark-done` — ручное закрытие задачи с отдельным списанием ledger.
- `action=purchase-task` — покупка через общий Roblox cookie-helper с переходом
  `READY/FAILED -> PURCHASING -> DONE/FAILED`.

Требования к API:

- idempotent sync;
- атомарный переход `READY -> PURCHASING -> DONE/FAILED`;
- защита от двойного выкупа одной и той же строки;
- запись фактической цены и cookie-аккаунта;
- честные ошибки, если cookie протух, пасс не продаётся или AlreadyOwned.

MVP route не обращается к `WbOrder`. Денежный учёт идёт через `PartnerLedgerEntry`; перед
ручным закрытием и покупкой проверяется баланс партнёра, а повторное списание по задаче
блокируется.

### Этап 4. Интеграция с Google Sheets

Нормальный сценарий для Антона требует не copy-paste, а sync с таблицей.

Минимум нужен one-way import:

- читать конфиг таблицы партнёра;
- забирать строки;
- создавать/обновлять `PartnerBuyoutTask`;
- игнорировать уже завершённые/закрытые задачи по правилу idempotency.

Следом нужен write-back:

- после успешного выкупа писать в таблицу `Готово`;
- желательно дописывать время, цену и аккаунт-выкупщик;
- при ошибке писать понятный технический статус, а не молча оставлять строку висеть.

Если нужно быстрее запуститься, можно сделать 2 фазы:

1. MVP: ручной `Sync` по Google Sheets API без автообновления.
2. V2: авто-sync + write-back + журнал импортов.

### Этап 5. Экран `Антон` в TWA

В `BossrobuxScreen` или рядом с ним добавить B2B-режим с такими блоками:

- верхняя сводка:
  баланс партнёра, задач `NEW/READY/DONE/FAILED`, потрачено за сегодня;
- actions:
  `Синхронизировать`, `Обновить`, `Выкупить выбранное`, `Открыть отчёт`;
- список задач:
  строка таблицы, ник, геймпасс, цена, статус, ошибка, кто выкупал;
- карточка задачи:
  `Проверить`, `Купить`, `Отметить готово`, `Повторить`, `Открыть строку`.

Важно: `Антон` не должен попадать в обычные вкладки заказов и не должен ломать текущий
ритейл-фокус менеджера.

### Этап 6. Батч-выкуп

Текущая механика batch-покупок уже есть и её надо переиспользовать.

Но для партнёра нужно добавить:

- выбор только задач партнёра;
- лимит по его балансу;
- отдельный отчёт батча;
- массовый write-back в Google Sheet;
- остановку батча без потери уже купленных строк.

### Этап 7. Учёт денег партнёра

Даже если сейчас Антон просто «скидывает на крипту», внутри системы нужен ledger.

Иначе быстро появятся вопросы без ответа:

- сколько он завёл;
- сколько уже потрачено;
- сколько осталось;
- какой батч что списал;
- где ошибка, а где корректировка.

Это критично, если направление реально пойдёт в B2B SaaS.

### Этап 8. Отчётность и аудит

Нужен отдельный отчёт по партнёру:

- сколько строк импортировано;
- сколько выкуплено;
- сколько в ошибке;
- сумма потраченных R$;
- какие cookie-аккаунты использовались;
- история пополнений/списаний.

Минимум отчёт должен быть доступен внутри TWA. Потом можно думать о внешнем кабинете.

### Этап 9. Hardening

Перед прод-использованием проверить:

- дедуп импорта;
- двойной тап по кнопке `Купить`;
- race condition между ручным и пакетным выкупом;
- падение Google API;
- падение Roblox purchase API;
- write-back в таблицу после успешного выкупа;
- восстановление после частично завершённого батча.

## Рекомендуемый порядок релиза

Самый прагматичный путь такой:

1. Вынести shared buyout-service — частично сделано (`resolve` + `purchase`).
2. Добавить `Partner` + `PartnerBuyoutTask` + `PartnerLedgerEntry` — сделано.
3. Сделать server MVP `Антон` для ручных задач и ledger — сделано.
4. Сделать экран `Антон` внутри «Аккаунт» с ручным созданием/покупкой задач.
5. Добавить Google Sheets sync и write-back статуса `Готово`.
6. Довести batch purchase только по задачам партнёра.
7. Уже после этого обобщать интерфейс из `Антон` в полноценный `Partners`.

## Оценка идеи

На текущем состоянии проекта это выглядит **хорошей и реалистичной следующей веткой**:

- ядро выкупа уже написано;
- TWA уже является рабочим операционным центром;
- менеджерский UX уже существует;
- путь до первого B2B-MVP короткий по сравнению с построением всего с нуля.

Но это пока **не SaaS в полном смысле**, а скорее **partner-ops module**.
Чтобы это стало SaaS, нужно не просто добавить экран, а отделить партнёрскую модель данных,
импорт, ledger и отчётность от розничного WB-контура.
